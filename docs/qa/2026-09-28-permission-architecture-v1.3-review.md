## 3. 详细发现

### V13-01 [P1] 组织默认语义与全局算法冲突

**设计定位**

- 第 47～53 行：功能权限跨组织、角色、账户执行全局 deny veto 和 allow 并集。
- 第 57 行：字段权限跨全部主体层级取最严格。
- 第 59 行：组织配置只是默认，存在角色或账户配置时不继承该维度。

**失败场景**

组织规则拒绝 `requirement.view`，角色规则允许：

- 按第 51 行，全局 deny 得到拒绝；
- 按第 59 行，存在角色配置后组织默认不继承，应得到允许。

字段权限同样冲突：组织配置 `hidden`、账户配置 `editable` 时，第 57 行得到 hidden，第 59 行却要求忽略组织规则。

文档还没有定义组织树祖先规则是否向子组织成员继承。用户属于父、子或多个组织时，可得到不同实现结果。

**最低修订要求**

1. 删除跨三个维度共用的“组织默认”泛化描述。
2. 分维度定义参与计算的组织候选集合：仅直接组织、主组织、全部所属组织，还是包含祖先。
3. 明确功能和字段算法是否始终包含组织规则；若包含，不再称为可被角色/账户遮蔽的默认。
4. 增加以下真值表：组织 deny + 角色 allow、组织 allow + 账户 deny、组织 hidden + 账户 editable、多组织冲突、父子组织冲突。

### V13-02 [P1] 多态主体外键和软删除约束不可实现

**设计定位**

- 第 69～72 行：三个规则表使用 `subject_type + subject_id` 指向 user、role 或 organization。
- 第 76～78 行：要求 `subject_id` 为外键、主体删除级联、规则支持软删除并具有唯一约束。

**实现证据**

PostgreSQL 普通外键不能根据同一行的 `subject_type`，让一个 `subject_id` 条件引用 `users`、`roles`、`organizations` 三张表。

现有项目关系表使用独立物理外键，例如：
`ipms-backend/database/migrations/2026_08_03_000005_create_role_user_table.php:14-16`。

**失败场景**

1. 不建立 FK 会留下悬空主体。
2. 只关联其中一张表时，相同数值 ID 可能被误认为另一种主体。
3. 普通唯一约束会让软删除规则继续占用唯一键，无法重新创建。
4. “主体删除级联”与软删除并不等价；软删除不会触发数据库级 cascade。
5. 项目删除选择 restrict 或 cascade 被推迟到实现阶段，设计没有唯一答案。

**最低修订要求**

从以下方案中确定一种，不再保留多选项：

1. 三个可空 FK（`user_id/role_id/organization_id`）+ exactly-one XOR CHECK + 活跃行部分唯一索引；或
2. 统一的 `permission_subjects` 主体表；或
3. 按主体拆分规则表。

同时明确：

- 是否真的需要规则软删除；若需要，使用 `UNIQUE ... WHERE deleted_at IS NULL`；
- 每个 FK 的 cascade/restrict/nullOnDelete；
- `granted_by_id` 删除策略；
- 软删除主体时 Resolver 如何排除规则；
- 数据范围项目删除的唯一策略。

### V13-03 [P1] readonly 可在写端点闭包完成前配置

**设计定位**

- 第 92 行要求七类读取通道纳入切换闭包。
- 第 96 行称 `readonly/editable` 无旁路风险，任何资源随时可配置。
- 第 129～134 行又规定按资源依赖闭包切换。

**代码依据**

同一字段可能存在多个独立写入口：

- `ipms-backend/app/Http/Controllers/Api/UserController.php:180-187` 管理员编辑用户；
- 同文件第 251～267 行当前用户更新个人资料；
- `UpdateRequirementRequest`、`UpdateTaskRequest` 等请求类各自定义可写字段，当前没有统一字段写入拦截器。

**失败场景**

管理员将 `user.phone` 配置为 readonly。如果管理员编辑入口已接入字段拦截，但 `/settings/profile` 尚未迁移，用户仍能通过后者修改手机号。

同样的问题适用于创建、更新、批量导入、状态流转、附件/替换及服务层直接写入。

**最低修订要求**

1. 将资源闭包拆为读取闭包与写入闭包。
2. `hidden/masked` 需要读取和写入闭包；`readonly` 至少需要完整写入闭包。
3. 只有 `editable` 可在未迁移资源上提前配置，因为它不增加限制。
4. 写端点依赖矩阵必须覆盖 create/update/bulk/import/workflow/service-side mutation。
5. 增加同字段多入口反向测试。

### V13-04 [P1] 最后超管保护未形成完整治理不变量

**设计定位**

- 第 47～53 行：任何主体的功能 deny 可全局否决。
- 第 109～112 行：最后超管保护只统计有效且绑定 `super_admin` 角色的账户。
- 第 117 行：系统管理仅超管可用。

**失败场景**

最后一名有效超管仍保留角色、处于 active 且未禁用，但账户或组织规则 deny 了用户、角色或权限管理能力。第 109 行的数量检查仍通过，实际却已没有任何人能恢复权限。

文档也没有明确超管是否：

- 绕过功能 deny；
- 绕过数据范围；
- 绕过字段 hidden/masked；
- 仅能通过独立 break-glass 路径恢复治理权限。

不同实现可能在“治理锁死”和“超管读取所有敏感字段”之间产生相反风险。

此外，文档只写 advisory lock，没有明确使用事务级锁。会话级 advisory lock 在连接复用时可能超出预期生命周期。

**最低修订要求**

1. 冻结超管在功能、数据、字段三维度的唯一矩阵。
2. 定义不可配置拒绝的保留恢复权限，或建立独立、强审计的 break-glass 机制。
3. 所有可能让最后超管失去恢复能力的 permission_rules 写入也纳入同一保护路径。
4. 明确使用 `DB::transaction + pg_advisory_xact_lock`；锁、重算、变更、审计、认证 epoch 更新必须在同一连接和事务中提交。
5. 有效超管应按“具备实际恢复能力”判定，而不只按角色、is_active、is_disabled 计数。
6. 增加权限 deny、组织迁移、并发降权和旧会话复用测试。

### V13-05 [P1] 数据范围集合语义不完整

**设计定位**

- 第 55 行定义最高层级覆盖、同层并集。
- 第 70～79 行定义 `all/org_subtree/projects/own/none`，但没有逐模块集合定义和条件约束。

**代码依据**

当前各资源的“本人相关”含义并不相同：

- `RequirementScope` 的 own 可表示直接提交需求；
- `ProjectScope` 通过本人提交的需求推导项目；
- `TaskScope` 当前没有系统用户 own 分支。

因此 `own` 不能在所有模块中用同一简单条件实现。

**失败场景**

1. `own ∪ projects` 在项目、需求、任务、缺陷模块中得到不同集合。
2. `org_subtree` 规则允许 `org_id=NULL`。
3. 非 `org_subtree` 规则却携带 `org_id`。
4. `projects` 没有项目明细时，可能被解释为空集、配置错误或回退默认。
5. 某些模块不支持某个 scope_type，但数据库仍允许写入。

**最低修订要求**

1. 为每个 `module × scope_type` 定义集合函数：
   `S(module, scope_type, actor, org_id, project_ids)`。
2. 明确 all、none、own、org_subtree、projects 在每个模块中的主表条件和关联路径。
3. 不支持的组合必须被 API 和数据库约束拒绝。
4. 增加条件约束：
   - org_subtree 必须且只能带 org_id；
   - projects 必须且只能有项目明细；
   - 明确空 projects 的语义；
   - none/all/own 不得携带无关锚点。
5. 对同层多角色、多组织的集合并集建立跨模块测试。

### V13-06 [P1] 路由能力与资源切换注册表仍缺可执行契约

本项合并 V12-04 与 V12-06 的剩余问题。

#### A. 路由—能力注册表缺少参数解析契约

**设计定位**

- 第 102～105 行要求运行时中间件和测试共同消费权限码或 Policy 方法。
- 第 125～131 行将注册表纳入 Phase A/Phase B。

**代码依据**

`POST /requirements/{id}/tasks` 的 `createTask` Policy 需要 requirement 和 project 两个对象，其中 project_id 来自请求体：
`ipms-backend/routes/api.php:109`；
`ipms-backend/app/Http/Controllers/Api/RequirementController.php:267-275`。

现有路由普遍使用数字 ID，而不是一致的隐式模型绑定。

**失败场景**

中间件知道 Policy 方法名，却无法安全构造参数。实现者可能退化为只检查全局权限码，漏掉项目关系和动作资格；或继续在控制器内授权，使注册表不再是单一事实源。

#### B. 端点—资源依赖矩阵和切换标志没有定义载体

**设计定位**

- 第 85～86 行要求依赖矩阵和“已切换”标志。
- 第 123～134 行要求完成闭包后原子开放配置。
- 四张新表中没有资源切换注册表，实施计划也未定义矩阵文件、所有者、更新和激活机制。

**失败场景**

开发人员手工标记资源已切换，但遗漏 dashboard、导出或嵌套摘要中的一个生产端点，服务端随即允许写入限制配置并造成旁路。

**最低修订要求**

1. 定义版本控制的统一注册表，至少记录：
   - route name/method/path；
   - 功能权限码或 Policy ability；
   - 授权阶段；
   - route-bound 模型解析；
   - 请求体派生模型解析；
   - 多模型 ability 参数；
   - 输出的资源及字段；
   - 读取/写入/导出通道；
   - 是否允许 authenticated-only。
2. 中间件、完整性测试、资源依赖检查和切换激活共同消费该注册表。
3. 对 deferred authorization 明确责任归属和完整性测试，禁止退化为控制器隐藏授权。
4. 定义持久化或版本化的资源切换状态，以及一次原子激活规则：全部注册依赖验证通过后才设置 switched。
5. 回滚必须同步恢复切换状态，旧代码不得忽略已生效的限制配置。
