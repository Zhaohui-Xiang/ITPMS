## 3. 详细发现

### V12-01 [P1] 权限解析优先级互相矛盾，且组织级功能权限无法落库

**设计定位**

- 第 46 行：三级主体作用于每一个权限维度。
- 第 51～65 行：账户覆盖角色、角色覆盖组织；多角色/多组织取并集；任何层级 deny 高于一切 allow。
- 第 82～84 行：功能权限只有 `user_permissions` 与现有角色权限矩阵。
- 第 98 行：字段权限冲突取全局最严格。
- 第 142～147 行：数据库变更没有组织级功能权限表，也没有带 effect 的角色级功能权限表。

**代码依据**

`permission_role` 只保存 `role_id + permission_id`，只能表达“授予”，不能表达角色级 deny：
`ipms-backend/database/migrations/2026_08_03_000004_create_permission_role_table.php:7-15`。

**风险场景**

账户级规则允许 `requirement.view`，角色或组织规则拒绝该权限时：

1. “第一条命中的最高层级”会得到 allow；
2. “任何层级 deny 优先”会得到 deny；
3. 字段维度的“取最严格”又给出第三套算法。

不同开发人员可以据此实现出相反结果，测试也无法确定唯一正确答案。

**最低修订要求**

1. 分别为功能、数据、字段三维度定义明确的解析真值表。
2. 二选一：最高配置层级覆盖低层级，或全局 deny veto；不能同时保留两种语义。
3. 为角色和组织增加能够表达 `allow|deny` 的功能权限规则表；或者明确组织不作用于功能权限，并同步修改三级主体目标。
4. 增加账户/多角色/多组织/类型默认的全组合冲突测试。

### V12-02 [P1] 字段权限存在明确读取旁路

**设计定位**

- 第 100～102 行列出七类泄露通道，却在 v1 主动排除历史、快照、导出和原始 JSON。
- 第 106 行同时定义 `hidden` 为不可读不可写。
- 第 159 行又要求模块批次将包括导出的全部入口接入解析服务。

**代码依据**

- `ipms-backend/app/Http/Controllers/Api/ApiDocumentController.php:124-128` 直接返回模型。
- 同文件第 238～253 行直接从原始字段构造 OpenAPI 导出。
- `ipms-backend/app/Http/Resources/ProjectVersionResource.php:82-109` 输出历史 metadata 和发布快照。

**风险场景**

管理员隐藏接口文档正文后，用户在详情中看不到该字段，但可从导出或版本历史取得原始值。界面提示不能构成保密控制。

**最低修订要求**

1. 不修改历史存储，但所有用户可读取的表现层必须执行字段过滤。
2. 未完成全通道过滤前，禁止为存在旁路的资源配置 `hidden/masked`，或拒绝受影响用户访问这些端点。
3. 七类通道全部纳入模块切换门禁与反向测试。

### V12-03 [P1] “同一事务”不能保证最后超管不被并发撤销

**设计定位**

- 第 119 行要求最后超管检查与变更在同一事务内。
- 第 120 行只对“禁用”明确撤销会话。
- 第 172、199 行将撤权和最后超管保护列为测试与风险控制项。

**代码依据**

- `ipms-backend/app/Models/User.php:83-86` 通过实时 `super_admin` 角色绑定识别超管。
- `ipms-backend/app/Http/Controllers/Api/AuthController.php:38-50` 登录同时要求 `is_disabled=false` 和 `is_active=true`。

**风险场景**

两个事务均看到两名超管，随后分别禁用或降权其中一人并同时提交，最终可留下零名可登录超管。普通 READ COMMITTED 事务不能锁住“有效超管数量”这个谓词。

另外，文档将有效超管定义为“未禁用”，没有纳入 `is_active`；超管降权也未明确撤销既有会话。

**最低修订要求**

1. 所有可能减少有效超管数量的路径共用 PostgreSQL advisory lock 或锁定专用单例行。
2. 锁内重新统计 `is_active=true AND is_disabled=false` 且绑定超管角色的账户。
3. 覆盖禁用、降权、删除、角色解绑及批量角色同步。
4. 降权同样递增认证 epoch 或撤销会话，并增加并发回归测试。

### V12-04 [P1] 按模块切换没有覆盖跨模块数据生产者

**设计定位**

- 第 132 行以单一模块“授权入口统一”作为配置开放条件。
- 第 149～160 行按需求、任务、缺陷、项目/版本、文档、审计分批切换。
- 第 197 行依赖 UI 配置门禁规避中间态越权。

**代码依据**

- `ipms-backend/app/Http/Resources/TaskResource.php:22-25` 在任务中输出需求标题。
- `ipms-backend/app/Http/Resources/ProjectVersionResource.php:74-79` 在版本中输出需求摘要。
- `ipms-backend/app/Http/Controllers/Api/DashboardController.php:39-78` 同时组合项目、需求、任务、缺陷和版本范围。

**风险场景**

需求模块批次完成并允许配置 `requirement=none` 后，尚未迁移的任务、版本或工作台接口仍可能返回需求标题或统计。

**最低修订要求**

1. 增加“端点－输出资源－权限维度”依赖矩阵。
2. 只有该资源的全部生产端点完成迁移后，才允许写入其配置。
3. 对强耦合模块采用同一切换单元，不能只按控制器目录划分。
4. 切换状态必须在服务端配置写路径和 Resolver 中强制执行，UI 置灰只作为体验层。
5. 验收增加 dashboard、导出、原始 JSON、选项接口和嵌套摘要，不限于当前四通道。

### V12-05 [P1] 新权限表完整性及组织生命周期规则缺失

**设计定位**

- 第 82、88、98 行定义三张新表的逻辑字段。
- 第 84 行缓存失效只列角色与权限配置表写入。
- 第 138～147 行没有外键、唯一约束、检查约束和删除行为。

**代码依据**

现有 `role_user`、`organization_user` 均使用外键和唯一约束；例如：
`ipms-backend/database/migrations/2026_08_03_000007_create_organization_user_table.php:10-18`。

**风险场景**

1. 同一用户和模块存在重复的 `all` 与 `none` 记录，Resolver 无法确定结果。
2. JSON `project_ids` 引用已删除项目，形成不可验证的悬空范围。
3. 用户换组织或组织移动后，仍命中旧组织继承权限缓存。

**最低修订要求**

1. 优先使用带外键的规范化主体关联和项目范围明细表。
2. 定义枚举检查、每个规则键的唯一约束、重复处理、软删除及级联/限制策略。
3. 将 `organization_user` 变化、组织移动/禁用/删除、角色状态及相关成员变化纳入缓存失效和审计。
4. 增加组织迁移、删除、重复规则和缓存命中的回归测试。

### V12-06 [P2] 路由权限覆盖完整性测试无法按当前描述实现

**设计定位**

- 第 113、155 行要求扫描路由表，断言受保护路由挂有权限码或 Policy。

**代码依据**

`ipms-backend/routes/api.php:36` 的业务路由组主要只挂 `auth:sanctum`。大量权限检查位于控制器中的 `Gate::authorize`、`can` 或内联判断，路由表本身没有可供扫描的权限元数据。

**风险场景**

仅扫描路由表时，测试无法判断控制器内部是否调用 Policy：要么把现有安全路由全部误报，要么通过白名单后漏掉新路由。

**最低修订要求**

1. 所有受保护路由声明 `permission`、`can` 或等价的能力元数据；或
2. 建立由运行时授权和完整性测试共同消费的“路由－能力”注册表。
3. 禁止维护只供测试使用、与实际授权脱节的静态白名单。

## 4. 复审后的实施门槛

1. 设计逐项回应 V12-01～V12-06，并更新 PA 回应索引，不得把“已回应”等同于“已闭环”。
2. 在编写 Resolver 前冻结三维度的解析真值表及数据库约束。
3. 字段权限只允许在所有可读出口有强制控制时开放；不可变历史是存储约束，不是跳过读取过滤的理由。
4. 最后超管保护必须以串行化锁和并发测试为验收依据，不能仅以事务包裹为依据。
5. 模块切换必须以端点依赖闭包为单位，并由服务端拒绝提前配置。
6. 路由覆盖测试必须依赖运行时实际使用的声明式授权元数据。
7. 完成修订后再次进行独立静态复审；实现完成后另做代码审计和多角色反向验收。
