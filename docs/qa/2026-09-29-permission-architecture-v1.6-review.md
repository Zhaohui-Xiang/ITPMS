## 4. 详细发现

### V16-01 [P1] 操作资格公式和不可绕过清单在 v1.6 中被删除

**设计定位**

- v1.5 第 80～82 行曾冻结：`操作资格 = 功能权限 ∧ 数据可见 ∧ 动作特定资格`，并列出发布门禁、缺陷复测、版本负责人和强制发布例外等不可配置覆盖项。
- v1.6 当前第 75～80 行的 2.5 已改为“缓存失效与 epoch”。
- 第 99 行仍声称“2.5 业务约束不绕过”，该引用已经指向缓存章节。
- 当前全文不再包含完整操作资格公式和不可绕过清单。

**失败场景**

实现者按 v1.6 独立开发时，只能看到功能、数据、字段三维权限和第 99 行的两个举例，无法确定缺陷复测资格、版本负责人关系、强制发布例外等是否仍为强制业务门禁。某个 Policy 可能把“数据可见”误当成“允许执行动作”，重新引入此前 PA-04 已关闭的问题。

对超管也存在同样歧义：三维权限可以绕过，但哪些动作特定资格不可绕过不再有权威清单。

**最低修订要求**

1. 恢复独立的“操作资格”章节和完整公式。
2. 恢复并维护不可配置覆盖清单，明确超管只能走既定例外流程。
3. 将第 99 行改为有效章节引用。
4. 为每个不可绕过资格建立注册表字段或 Policy 测试矩阵，避免仅依赖叙述。

### V16-02 [P1] epoch 触发范围和缓存命名空间生命周期不完整

**设计定位**

- 第 77～80 行定义 TTL 截断、单行全局 epoch 和数据库触发器。
- 第 78 行只明确六张规则/关系表以及组织、用户“状态字段”触发 epoch。
- 第 79 行又声称组织移动可天然推进 epoch。
- 第 107～113 行的回滚契约没有定义 epoch 在迁移回滚、数据库恢复或重建时不可复用。

**代码依据**

- 当前组织树计算依赖 `organizations.parent_id` 和 `org_type`：`ipms-backend/app/Models/User.php:99-140`。
- `parent_id` 是组织表普通字段：`ipms-backend/database/migrations/2026_08_03_000006_create_organizations_table.php:8-14`。
- 演示环境缓存配置跨 release 共享：`ops/prepare-demo.sh:20-24,39-45`。

**失败场景 A：组织移动未失效**

批量 SQL 修改 `organizations.parent_id`，不触碰第 78 行列出的六张表，也不一定属于“状态字段”。如果触发器未显式监听 parent_id/org_type，旧组织树范围可以继续存活到 300 秒 TTL 结束。

**失败场景 B：epoch 值复用**

Phase A 回滚后重建 `permission_epoch`，或数据库从旧备份恢复但 Redis/文件缓存未同步恢复，epoch 可能重新出现历史值。缓存键仅携带 epoch 时，旧 allow 结果会重新命中。

**最低修订要求**

1. 明确列出 organizations.parent_id、org_type、is_active，以及 users.user_type、is_active、is_disabled 等全部影响授权的字段。
2. 为缓存键增加不可复用的 installation/deployment UUID，或把 epoch 放入永不回退的独立持久命名空间。
3. 数据库恢复、反向迁移和 epoch 重建必须原子更换命名空间或清空全部权限缓存。
4. 增加组织重挂父节点、数据库恢复和 epoch 重建后的反向授权测试。

### V16-03 [P1] data_scopes 数据库完整性和锚点生命周期仍未闭合

**设计定位**

- 第 51 行冻结一主体一模块至多一条规则。
- 第 54～58 行定义 org_id CHECK、明细归属触发器和单事务切换。
- 第 55 行仍把 projects 至少一条明细交给 API 422；延迟触发器只保证“已有明细的父规则必须是 projects”。
- 第 64～71 行规定 audit 不支持 org_subtree/projects，但数据库约束没有冻结 module × scope_type 合法矩阵。
- 第 57 行没有定义作为范围锚点的 data_scopes.org_id 删除策略。

**代码依据**

- 组织存在删除入口：`ipms-backend/app/Http/Controllers/Api/OrganizationController.php:80-90`。
- organizations.parent_id 当前使用级联删除：`ipms-backend/database/migrations/2026_08_03_000006_create_organizations_table.php:8-14`。

**失败场景**

1. 直接 SQL 可提交 `scope_type=projects` 但没有任何明细；虽然运行期为空集，但不满足文档宣称的数据库完整性。
2. `module=audit, scope_type=org_subtree` 可以通过现有同行 CHECK，Resolver 对文档标记“不支持”的组合没有唯一数据库语义。
3. 删除 org_subtree 的锚点组织时：SET NULL 违反 CHECK；CASCADE 删除账户级规则后可能回退到更宽的角色/类型默认；RESTRICT 则会产生未记录的业务阻塞。

**最低修订要求**

1. 用提交时延迟约束保证 projects 创建或切换后至少一条明细；删除最后一条明细必须原子改为 none、删除规则或拒绝。
2. 用数据库 CHECK 冻结 module × scope_type 合法矩阵。
3. data_scopes.org_id 采用明确的 fail-closed 删除语义。建议 ON DELETE RESTRICT，要求先在同一事务把引用规则改为 none 或替换锚点。
4. 增加绕过 API 的直接 SQL、删除最后明细、删除锚点且下层默认 all 的测试。

### V16-04 [P1] 激活摘要缺少跨版本握手，非 HTTP 通道也没有失活门禁

**设计定位**

- 第 90 行将注册表与授权消费者文件纳入摘要。
- 第 93～95 行规定摘要不匹配时中止部署，运行期相关端点返回 503。
- v1.6 删除了 v1.5 中 resource_auth_states 的读/写激活字段表，当前文档没有重新冻结按 build 存储多个有效摘要的状态模型。
- 第 84、90 行把服务层写入口纳入闭包和摘要，但失活行为只定义为“相关端点”返回 503。

**部署依据**

- 当前候选发布先在共享数据库执行迁移并建立 candidate：`ops/prepare-demo.sh:34-51`。
- 正式 current 在后续 promote 阶段才切换：`ops/promote-demo.sh:27-32`。

**失败场景 A：current/candidate 无法同时合法**

候选版本修改了消费者文件，摘要从 A 变为 B。如果数据库仍记录 A，candidate 被预检阻断；若提前改为 B，仍在服务的 current 会检测到不匹配并返回 503；候选失败后回滚到 A 也会再次不匹配。单一摘要无法支持当前两阶段发布和回滚窗口。

**失败场景 B：非 HTTP 写入绕过**

队列任务、调度器、CLI 导入或直接服务调用没有 HTTP 端点可返回 503。如果 stale gate 只挂在路由中间件，这些通道仍可能使用未核验消费者执行读写。

**最低修订要求**

1. resource_auth_states 恢复明确的读/写激活字段，并按 build_id 保存 current/candidate 两组摘要及状态。
2. 定义 prepare、预激活、切流、验证、关闭回滚窗口、废止旧摘要的两阶段协议。
3. 原摘要只能在旧构建回滚窗口关闭后失效。
4. stale gate 放入共享 Resolver/服务边界，对 HTTP、queue、scheduler、CLI、export 统一 fail closed；HTTP 映射 503，后台任务进入可重试失败状态。
5. 增加候选失败回滚和长驻 worker 未重启的演练。

### V16-05 [P1] 最后超管保护缺少启用前置断言和离线恢复路径

**设计定位**

- 第 99～105 行规定三维矩阵、唯一判定、未来变更归零保护和会话撤销。
- 第 127～129 行 Phase A 没有要求启用新中间件前确认至少存在一名有效超管。
- 当前设计没有定义系统已经处于零有效超管时的强审计恢复机制。

**代码依据**

- 登录会拒绝 inactive/disabled 用户：`ipms-backend/app/Http/Controllers/Api/AuthController.php:38-50`。
- 当前管理员 Seeder 对已存在的托管用户只补角色，不恢复 is_active/is_disabled：`ipms-backend/database/seeders/AdminUserSeeder.php:64-78`。

**失败场景**

部署前数据中唯一 super_admin 已停用或禁用。新锁只能阻止后续操作把数量从一降到零，却不能把已经为零的状态恢复。中间件上线后，所有管理入口均不可用，系统进入治理锁死。

**最低修订要求**

1. Phase A 部署前置检查必须断言有效超管数至少为一，否则中止部署。
2. 定义离线、强审计、一次性凭证保护的恢复命令。
3. 恢复命令使用同一 advisory lock，原子修复角色实体、账户状态和角色绑定，并撤销全部相关旧会话。
4. 增加零超管部署阻断和离线恢复演练。

### V16-06 [P1] 维护窗口没有冻结所有写入者，单事实源切换仍可能丢授权

**设计定位**

- 第 60、112、128 行假设“维护模式开”后窗口内无并发写，因此无需增量追平。
- 文档没有冻结停止 HTTP、FPM、队列 worker、scheduler、CLI 和旧构建写入的具体顺序，也没有数据库级旧表写保护。

**部署依据**

- 当前 prepare 脚本在新 release 上对共享数据库执行迁移，再建立 candidate，但没有先停 current：`ops/prepare-demo.sh:34-51`。
- current 直到 promote 时才切换：`ops/promote-demo.sh:27-32`。
- 环境明确使用 Redis queue：`ipms-backend/config/queue.php:22-29`，且连接配置 `after_commit=false`。

**失败场景**

回填结束后、current 切换前，旧 current 或未停止的 worker 继续写 `permission_role`。新代码只读 permission_rules，该增量不会被复制，用户授权在切换后静默丢失。HTTP 维护模式也不能自动停止队列、scheduler 或 CLI。

**最低修订要求**

1. 冻结完整切换顺序：关闭入口，停止并排空 FPM/队列/scheduler，数据库级禁止旧表写入，回填与核对，切换 current，重启全部长驻进程，验证新构建，再开放流量。
2. 对无法完全停写的环境，改用双写 + 增量追平 + 最终校验，不得仅依赖维护模式。
3. 每一步失败必须按能力矩阵执行前向恢复或受控回滚。
4. 更新部署脚本和演练标准后再批准实施。
