## 4. 详细发现

### V14-01 [P1] 数据范围矩阵可能跨项目放行，且数据库约束不可按文档实现

**设计定位**

- 第 72 行：`data_scope_projects` 为空被定义为空集合。
- 第 76～87 行：逐模块定义 `org_subtree/projects`，并要求 `projects` 必须有明细且由 API 422 + DB CHECK 双重拒绝非法组合。
- 第 82 行：Task 经所属 Requirement 的项目集合判断。
- 第 83 行：Defect 使用“同 task 路径”。
- 第 84 行：Document 的 own 条件写为 `uploader=我`。

**代码依据**

- Requirement 是多项目关系：`ipms-backend/app/Models/Requirement.php:54-65`。
- Task 同时有独立 `requirement_id` 和 `project_id`：`ipms-backend/app/Models/Task.php:14-16,29-36`。
- Defect 没有 task 关系，只有独立 `requirement_id` 和 `project_id`：`ipms-backend/app/Models/Defect.php:14-18,26-33`。
- Document 的实际上传人字段为 `uploaded_by_id`：`ipms-backend/app/Models/Document.php:12-15,31-34`。

**失败场景**

需求 R 同时关联可见项目 A 和不可见项目 B，任务 T 的 `project_id=B`、`requirement_id=R`。如果按第 82 行通过 `S(requirement, ...)` 判断，R 因关联 A 而可见，T 随之被错误放行，绕过 B 的项目边界。Defect 复用该路径时存在同样风险，且“同 task 路径”本身无法映射到现有模型。

第 72 行允许 projects 空明细并解释为空集，第 87 行又要求 projects 必须有明细，两者会产生相反的保存结果。并且 PostgreSQL 普通 CHECK 不能检查另一张明细表是否至少存在一行，文档声明的“双重拒绝”无法仅靠 CHECK 实现。

**最低修订要求**

1. Task/Defect 的 `org_subtree` 和 `projects` 直接以各自 `project_id` 为授权锚点，不经 Requirement 的多项目集合传递。
2. Requirement 明确多项目关系的 `EXISTS`/并集语义，避免把一个可见关联扩散到其他项目实体。
3. 修正 Document 字段名，并为每条集合函数写出真实列和关联路径。
4. 在“允许空集”和“拒绝空明细”中选择唯一语义。
5. 若拒绝空明细，使用延迟约束触发器或重构存储模型；不得继续声称普通 DB CHECK 可以约束子表行数。

### V14-02 [P1] 新旧功能权限双数据源缺少原子切换，删除新规则后旧授权可能复活

**设计定位**

- 第 39～41 行：功能 allow 来源明确包含存量 `permission_role`。
- 第 57～71 行：新增 `permission_rules` 作为功能权限规则表。
- 第 145～147 行：Phase A 未定义 `permission_role` 的回填、冻结、停读或退出步骤。
- 第 146 行只概括“缓存失效与 TTL 截断”，没有保留 v1.3 已列明的变更源和事务后失效契约。

**代码依据**

- 当前 `User::hasPermission()` 直接读取角色的 `permission_role` 关系，并缓存 300 秒：`ipms-backend/app/Models/User.php:88-94`。
- `permission_role` 是独立物理表：`ipms-backend/database/migrations/2026_08_03_000004_create_permission_role_table.php:7-16`。

**失败场景**

角色 R 在旧表有 `requirement.view` allow。迁移后管理界面删除 R 的新 allow，期望回退到默认或拒绝；但旧 pivot 仍被第 40 行视为 allow，权限立即复活。若旧代码和新 Resolver 在切换期分别读取两张表，同一用户还会因入口不同得到不同结果。

规则变更、角色绑定或组织成员关系改变后，如果只依赖 300 秒 TTL，deny 和撤权也会在缓存窗口内继续使用旧结果。

**最低修订要求**

1. 冻结唯一事实源：一次性回填 `permission_role`，在同一切换步骤停写、停读旧表；兼容期如必须双读，只允许可证明单调且有截止日期的策略。
2. 定义迁移幂等键、数量/哈希核对、失败回滚和旧表最终删除或只读策略。
3. 注册所有缓存失效源：规则、角色绑定、组织成员关系、组织移动/禁用/删除、账户状态及 expires_at。
4. 变更事务提交后使用权限 epoch/version 或可靠失效机制，验收必须覆盖 deny、解绑和到期的即时生效。

### V14-03 [P1] 切换状态无法表达分阶段门禁，且激活证明会跨版本失效

**设计定位**

- 第 95～97 行：readonly 只要求写入闭包；hidden/masked 要求读取和写入闭包。
- 第 101～115 行：注册表同时驱动运行时、完整性测试、闭包检查和切换激活。
- 第 117 行：状态表只有 `read_closure_done`、`write_closure_done`、单一 `switched_at`；Resolver 仅对 `switched_at` 非空的资源应用配置，未切换资源拒绝全部配置写入。

**失败场景**

资源已完成写闭包但尚未完成读闭包：按第 96 行应允许 readonly、拒绝 hidden/masked；按第 117 行则只有两个选择：

1. 不设置 `switched_at`，readonly 也无法生效；
2. 设置 `switched_at`，hidden/masked 可能在读取闭包未完成时生效并产生旁路。

此外，状态没有注册表摘要、代码版本或依赖版本。资源在 v1 完成闭包并激活后，v2 新增一个输出端点或写入口，旧 `switched_at` 仍然有效，新端点可直接绕过字段限制。

**最低修订要求**

1. 分别记录读取和写入闭包的激活时间、验证者及注册表摘要，不使用一个 `switched_at` 表达两个门禁。
2. Resolver 和配置写路径按 effect 检查门禁：readonly 依赖写闭包；hidden/masked 依赖读写闭包。
3. 激活状态绑定规范化注册表摘要；摘要变化时部署必须重新验证相关资源，未验证则 fail closed 或阻断部署。
4. 对新增路由、输出字段、写入口建立测试，证明历史激活状态不会静默沿用。

### V14-04 [P1] 当前回滚方案会关闭已生效权限限制

**设计定位**

- 第 117 行：代码回滚伴随 `resource_auth_states` 回退，旧代码“不读该表故天然忽略配置”，数据库规则继续保留。
- 第 186 行：将上述步骤列为回滚对策。

**失败场景**

用户字段已配置 hidden，或账户已配置功能 deny。部署回滚到不包含新 Resolver 的旧版本后，旧代码忽略这些规则，敏感字段重新输出、被禁止的操作重新可用。保留数据库配置并不能维持安全属性，反而造成回滚期间的静默越权。

这也直接违反上一轮 V13-06 的批准门槛：“旧代码不得忽略已生效的限制配置”。

**最低修订要求**

1. 定义权限兼容版本下限；存在有效 deny/readonly/hidden/masked 时，禁止回滚到不支持对应 Resolver 的版本。
2. 提供前向兼容的回滚构建，或先以受审计的变更撤销限制配置，再允许回滚；不能把“忽略配置”作为方案。
3. 部署/回滚预检必须读取实际有效规则和目标版本能力矩阵，任一不兼容即中止。
4. 回滚演练验收需证明限制在代码回退前后连续生效。

### V14-05 [P1] 超管治理算法自相矛盾，且保护路径漏掉超管角色实体变更

**设计定位**

- 第 121 行：超管功能权限恒 allow，所有 deny 对超管无效。
- 第 125～129 行：有效超管又要求“未被 deny 保留恢复权限集”，并把针对超管主体的 deny 纳入最后超管保护。
- 第 126 行列举的保护路径没有覆盖超管角色的重命名、删除或系统标志变更。

**代码依据**

- 当前超管身份完全取决于角色代码 `super_admin`：`ipms-backend/app/Models/User.php:83-85`。
- Role 的 `code` 和 `is_system` 均可批量赋值：`ipms-backend/app/Models/Role.php:7-13`。
- 删除角色会级联删除全部用户绑定：`ipms-backend/database/migrations/2026_08_03_000005_create_role_user_table.php:12-16`。

**失败场景**

对唯一超管写入 `user.manage` deny：按第 121 行该 deny 无效，账户仍有恢复能力；按第 128 行该账户不再属于有效超管，操作必须拒绝。同一事务会因实现选择不同得到相反结论。

即使 deny 冲突被修复，若 `super_admin` 角色被重命名、删除或取消系统角色标识，现有身份判定和全部绑定仍可能同时消失，而文档列出的统一锁路径不会拦截。

**最低修订要求**

1. 在以下方案中固定一个：超管恒 allow 且 deny 不进入有效性计算；或允许 deny 约束超管并建立独立、不可被同一权限系统锁死的 break-glass 主体。
2. 恢复能力计算必须调用与运行时 Resolver 相同的判定，不复制一套近似公式。
3. 以不可变标识定义保留超管角色；角色 code、`is_system`、删除和权限集变更全部纳入同一 `pg_advisory_xact_lock` 事务。
4. 增加角色重命名、角色删除、系统标志变更、并发 deny/降权和旧会话复用测试。
