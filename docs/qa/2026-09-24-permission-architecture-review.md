## 3. 详细发现

### PA-01：配置开放早于授权入口统一

- 设计定位：第 155、161-170、174 行，Phase A/B/C 实施顺序。
- 代码依据：`ipms-backend/app/Http/Controllers/Api/ProjectController.php:27` 列表应用 ProjectScope；第 82-83 行详情调用 Policy。`ipms-backend/app/Policies/ProjectPolicy.php:18` 仍根据用户类型、项目成员及供应商组织判定。
- 场景与风险：Phase A 改 Scope，Phase B 开放配置，Phase C 才迁移 Policy。将账户项目范围设为 none 后，列表可能隐藏项目，直接访问详情却仍获旧 Policy 放行；额外授予项目也可能出现列表可见、详情 403。
- 修订要求：将所有读写入口的统一授权纳入配置开放前置条件。可以分阶段开发，但未完成接入的模块不得开放配置或宣称配置已生效。
- 验收要求：同一配置分别验证列表、直接 ID 详情、写接口和关联入口；收紧必须同步拒绝，扩大必须按设计一致生效。

### PA-02：字段过滤没有覆盖全部出口与副本

- 设计定位：第 97-104、156、193 行，FieldFilter 与 Resource 基类收口。
- 代码依据：`ipms-backend/app/Http/Controllers/Api/ApiDocumentController.php:124` 直接返回模型，第 218 行返回历史，第 238-274 行直接构造导出数据。`ipms-backend/app/Http/Resources/TaskResource.php:22` 内嵌需求标题。`ipms-backend/app/Http/Resources/ProjectVersionResource.php:82` 输出历史 metadata，第 101 行输出发布快照。
- 场景与风险：仅在 Resource 基类过滤不能覆盖原始 JSON、导出等通道；即使全部出口接入，隐藏 requirement.title 仍可能通过任务中的需求摘要读取，隐藏发布说明也可能从快照或历史副本读取。
- 修订要求：列明所有 JSON、历史、快照、导出等输出通道；定义嵌套路径、别名和副本到源字段的映射，并按读取者有效权限过滤。不得为过滤展示而修改不可变的历史存储。
- 验收要求：同一隐藏或脱敏字段通过详情、关联摘要、历史、快照及导出读取时均遵守规则，响应不能包含原始值。

### PA-03：数据范围未覆盖关联数据及统计

- 设计定位：第 81、86-88、155 行，模块范围与四个 Scope 改造。
- 代码依据：`ipms-backend/app/Http/Controllers/Api/ProjectVersionController.php:480` 为非系统用户加载全部关联需求，第 498-509 行直接统计任务与缺陷。`ipms-backend/app/Http/Controllers/Api/RequirementController.php:310` 构造项目关联与统计；第 373-395 行仍按供应商类型限制关联项目。
- 场景与风险：用户被设置为仅能看自己的需求，却仍可能从有权查看的版本详情获得其他需求的标题、优先级及统计。跨项目需求的关联数据也未明确按哪个模块范围裁剪。
- 修订要求：建立资源依赖与展示规则，明确项目版本继承何种范围，以及关联列表、统计、门禁结果和其他汇总出口如何应用权限。统计若允许公开，必须明确作为授权例外，而非意外泄露。
- 业务约束：实际发布门禁必须检查完整版本业务数据，不能因为操作者看不到某项严重缺陷就忽略它。门禁计算与面向用户的结果展示应分开处理。
- 验收要求：项目可见但需求 own/none、任务或缺陷范围更窄、跨项目需求等组合均有反向用例；隐藏严重缺陷仍必须阻断实际发布。

### PA-04：数据可见性与操作资格边界不清

- 设计定位：第 62、86-88、170 行，超管全量及 Policy 行级判定收口。
- 代码依据：`ipms-backend/app/Policies/DefectPolicy.php:106` 同时检查复测权限、提交人或成员关系及可见性。`ipms-backend/app/Policies/ProjectVersionPolicy.php:91` 普通版本管理要求内部 IT 项目经理及项目负责人关系，并排除超管普通管理路径。
- 规格依据：`docs/superpowers/specs/2026-08-17-ipms-core-workflow-redesign-design.md:218` 定义带原因的超管强制发布边界，第 239 行保留外键、唯一约束和并发锁。
- 场景与风险：扩大测试人员的只读项目范围，若被直接用于替代项目成员资格，可能意外授予非参与项目的复测能力；“超管全量”也可能被理解成绕过所有业务限制。
- 修订要求：明确功能权限、数据可见性、动作特定资格的组合公式；列出哪些关系约束允许配置替代，哪些业务约束不可覆盖。超管例外必须走独立、可审计的授权路径。
- 验收要求：仅扩大可见范围不能自动取得复测或发布资格；超管仍遵守已确认的例外状态、原因、快照与审计要求。

### PA-05：masked 未定义写入限制

- 设计定位：第 99-105 行，字段访问级别及写入拦截。
- 代码依据：`ipms-frontend/src/components/common/ProfileDialog.vue:71` 将手机号回填表单，第 136 行整表提交。`ipms-backend/app/Http/Controllers/Api/UserController.php:257` 接受普通手机号字符串，第 265 行保存。
- 场景与风险：设计将 masked 排在 readonly 之上，但写入拦截只列 readonly/hidden。应用脱敏后，用户只修改姓名，也可能把手机号展示字符串回写为真实值。
- 修订要求：明确 masked 默认不可写，前端提交数据排除脱敏展示值；需要盲写或替换时单独定义写权限及请求契约。仅禁用控件不能代替请求层约束。
- 验收要求：仅修改其他字段不改变原始敏感值；直接提交脱敏字符串或无权字段被明确拒绝；合法替换走独立授权规则。

### PA-06：超管永久保护妨碍撤权

- 设计定位：第 132、191 行，所有超管不可禁用或降权，以及 admin 账户豁免。
- 代码依据：`ipms-backend/app/Models/User.php:83` 根据角色绑定识别超管；`ipms-backend/app/Policies/ProjectVersionPolicy.php:78` 据此授予强制发布能力。
- 场景与风险：即使还有其他有效超管，离职或失陷超管也无法在管理流程内被禁用或撤销身份；普通权限 deny 无法撤销超管身份所带来的特权。
- 修订要求：只保护最后一名有效且可登录的超管。允许撤销其他超管身份并终止会话；取消基于固定用户名的永久豁免。最后超管校验与变更必须在同一原子操作内完成。
- 验收要求：存在两名有效超管时可安全撤销其中一名；并发撤销不得使有效超管数量降为零；被撤销账户的旧凭证不得继续获得特权。
- 证据性质：设计规则风险，不是本轮已动态复现的运行时缺陷。

### PA-07：禁用缺少既有会话撤销要求

- 设计定位：第 123、129-132 行，用户启用/禁用及安全一致性约束。
- 代码依据：`ipms-backend/app/Http/Controllers/Api/UserController.php:227` 只更新 is_disabled；`ipms-backend/app/Http/Controllers/Api/AuthController.php:38` 在登录时检查禁用状态；`ipms-backend/routes/api.php:36` 认证组与 `ipms-backend/bootstrap/app.php:27` 未配置持续账户状态检查。
- 已有记录：`docs/07-模块体验走查问题清单.md:160` 的 U-1 记录禁用后旧会话仍可读写。本轮只核对记录及源码，未重新动态复现。
- 修订要求：定义禁用提交后的后续请求必须拒绝；撤销旧会话及有效凭证，并明确请求级账户状态检查。重新启用不得使已撤销会话恢复。
- 验收要求：登录后禁用，旧会话读写均失败；重新启用后必须重新认证；普通账户与超管身份变更均覆盖。

### PA-08：三级配置目标与数据模型不一致

- 设计定位：第 39、56-62、79、86、96、142 行；项目日志 D18。
- 事实：data_scopes.subject_type 只有 user/role；功能解析没有组织权限配置；字段规则明确排除组织维度，但总体目标承诺组织/角色/账户三级作用于三个维度。
- 场景与风险：无法配置组织统一规则并向成员继承，后续实现可能将 org_subtree 数据范围误认为组织级授权，导致产品承诺与实际模型不同。
- 修订要求：补组织主体、继承、多组织归属、冲突与覆盖规则；或明确缩减目标并修订 D18。org_subtree 是筛选范围，不等同于组织主体配置。
- 验收要求：若保留三级目标，应覆盖组织默认、角色规则、账户覆盖、多组织冲突以及组织变更后的有效权限。

### PA-09：到期授权与缓存失效不闭合

- 设计定位：第 70-71、131 行，expires_at 与监听写入主动失效。
- 代码依据：`ipms-backend/app/Models/User.php:88` 当前权限布尔值缓存 300 秒。
- 场景与风险：到期前缓存了临时 allow，时间到期不会产生表写入；若只依赖写入事件清缓存，授权可能在到期后继续有效近五分钟。
- 修订要求：定义到期即失效；缓存有效期不得跨越参与判定规则的最近到期时间，或在缓存命中时校验该边界。到期 deny 的移除同样需要正确重新解析。
- 验收要求：使用可控时钟测试 allow/deny 到期前、到期瞬间、到期后及缓存命中场景，不能靠等待固定 TTL 验证。

## 4. 修订后的验收门槛

1. 设计逐项回应 PA-01 至 PA-09，记录采纳方案；存在产品取舍时同步修订决策记录。
2. 明确所有授权维度的解析顺序、默认值、冲突处理和不可覆盖业务约束。
3. 配置开放前统一列表、详情、写入、关联查询及导出等实际执行入口。
4. 增加跨角色、账户覆盖、跨项目、关联字段、到期及撤权的反向测试，而不只验证管理界面可保存配置。
5. 分开验证门禁完整计算与受限展示，防止权限过滤改变业务事实。
6. 保留现有回归测试，但不得把固定测试数量或全绿结果单独视为行为等价证明。
7. 由开发 Agent 修订设计及实施后，再进行独立复审；本报告不构成修复完成或上线批准。
