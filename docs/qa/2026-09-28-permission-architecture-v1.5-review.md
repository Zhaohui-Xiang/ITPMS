## 4. 详细发现

### V15-01 [P1] 缓存 epoch 无法保证到期和级联变更即时生效

**设计定位**

- 第 52 行：`permission_rules` 支持 `expires_at`。
- 第 56 行：主体和项目删除依赖数据库级联。
- 第 63 行：将 expires_at 到期列为缓存失效源，并规定变更事务提交后递增权限 epoch，deny/解绑/到期即时生效。
- 第 138～139 行：Phase A 以 epoch 和到期可控时钟测试作为验收项。

**代码依据**

当前 `User::hasPermission()` 将权限结果缓存 300 秒：`ipms-backend/app/Models/User.php:88-94`。

**失败场景**

角色 allow 在 12:00 到期，用户于 11:59 命中 allow 并写入缓存。自然到达 12:00 时没有数据库变更事务，因此不会执行“提交后递增 epoch”，该 allow 仍可能继续授权到原缓存过期。

第 63 行自称“全量清单”，但没有包含 `data_scope_projects`。项目明细增删以及 FK cascade 发生在数据库层时，也不必然经过应用层 epoch 更新，旧数据范围可能继续被缓存使用。

**最低修订要求**

1. 缓存 TTL 必须截断到参与判定规则中最近的 `expires_at`；或提供可证明准时执行且具备补偿机制的到期事件任务。
2. 将 `data_scope_projects`、FK cascade、批量 SQL 和所有非 Eloquent 写路径纳入失效源。
3. 明确 epoch 是全局还是按用户，并冻结组织移动、角色解绑等多用户变更的原子推进方式。
4. 使用事务 outbox、数据库触发器或等价机制保证“业务变更提交成功但 epoch 未推进”不会发生。
5. 增加过期 allow 的边界时刻测试以及级联删除后的即时反向授权测试。

### V15-02 [P1] data_scopes 条件完整性和类型切换缺少可执行契约

**设计定位**

- 第 50～54 行只明确主体三外键 XOR 和表的概括字段。
- 第 65～78 行依赖 `org_subtree` 的 org_id 锚点和 `projects` 明细。
- 第 78 行只冻结 projects 空明细的 API/运行期语义。
- 第 138 行笼统要求迁移“含全部约束”，但没有列出这些条件约束的实现方式。

**失败场景**

文档没有明确或约束以下非法状态：

1. `org_subtree` 缺少 org_id，或非 `org_subtree` 规则残留 org_id；
2. 非 `projects` 规则仍保留 `data_scope_projects` 明细；
3. scope 从 projects 改为 own/none 时，旧明细未在同一事务清理；
4. scope 从 own 改为 projects 时，主表已提交但明细尚未写入，运行期短暂得到空集；
5. 同一主体和 module 是否允许同时存在多个 scope_type，以及多行之间如何合并。

这些状态会让不同 Resolver 对同一数据库内容得到不同结果，并使“同层并集”究竟针对多主体还是同一主体的多规则无法唯一实现。

**最低修订要求**

1. 冻结一主体一模块一条 scope，或明确允许多 scope 并给出集合合并算法及唯一索引。
2. 用 CHECK 保证 org_id 的“必须且只能”条件。
3. 对明细归属使用延迟约束触发器、拆表或其他可执行方案，保证非 projects 无明细、projects 保存时至少一条明细。
4. scope 类型切换必须在单事务内完成主表和明细变更；任何中间态按 fail closed 处理。
5. 增加数据库约束测试和并发切换测试，而不只依赖 API 422。

### V15-03 [P1] 激活证明未覆盖真实代码依赖，自动失活也未定义真正的 fail closed

**设计定位**

- 第 92～94 行：注册表由运行时、完整性测试、闭包检查和激活共同消费。
- 第 101～105 行：激活摘要只计算“注册表该资源条目”。
- 第 105 行：摘要变化后资源自动失活，称为 fail closed。
- 第 106 行：声称完整性测试可以证明新增路由、输出字段和写入口都已登记。

**失败场景 A：遗漏内容不会改变摘要**

开发人员在 Resource/序列化器中新增敏感输出字段，或在服务层增加写入口，却忘记更新注册表。注册表文本及摘要完全不变，旧激活状态继续有效。路由枚举可以发现新路由，却不能自动证明一个输出字段、导出器或服务层 mutation 已完整声明。

**失败场景 B：失活可能反而关闭限制**

资源已有 hidden/readonly 规则，新版本导致摘要变化。如果“失活”意味着 Resolver 不再应用配置，该字段会恢复 editable/可见，结果是 fail open。真正的 fail closed 只能是阻断部署，或运行时拒绝受影响资源的请求并保持既有限制。

**最低修订要求**

1. 摘要覆盖注册表及全部授权消费者的构建清单：Policy、Resolver、Resource/序列化器、导出器和服务层写入口。
2. 对无法自动发现的语义依赖建立显式 owner、代码审查门禁和按资源反向测试，不能把自声明注册表称为完整性证明。
3. 摘要不匹配时优先中止部署；如允许运行时进入失活态，相关端点必须拒绝服务且不得回退到默认 editable/allow。
4. 冻结部署预检、Resolver 和配置写入的统一错误码、监控告警与重新激活步骤。
5. 增加“只改序列化器/服务实现而不改注册表”的负向测试。

### V15-04 [P1] 超管三维不变量和 is_active 生命周期没有闭合

**设计定位**

- 第 38 行只在功能权限 deny 中排除超管。
- 第 82 行规定操作资格同时依赖功能权限、数据可见和动作特定资格。
- 第 117～121 行将“超管恒 allow”限定在功能 allow/deny，却删除了 v1.4 中“数据范围恒 all、字段权限恒 editable”的明确矩阵。
- 第 119 行把 is_active 纳入有效超管判定，但第 121 行的受锁路径和会话撤销只写“禁用/降权/解绑”等泛化词，没有明确 is_active=false。

**代码依据**

- 当前 ProjectScope 对超管直接返回全表：`ipms-backend/app/Scopes/ProjectScope.php:23-28`。
- 当前 `User::isSuperAdmin()` 只检查角色绑定：`ipms-backend/app/Models/User.php:83-86`。
- 当前请求中间件只拦截 is_disabled，不检查 is_active：`ipms-backend/app/Http/Middleware/EnsureUserIsActive.php:17-37`。
- 登录流程则分别检查 is_disabled 和 is_active：`ipms-backend/app/Http/Controllers/Api/AuthController.php:38-49`。

**失败场景**

如果账户或组织字段规则把超管的管理字段设为 hidden/readonly，或数据范围设为 none，超管即使功能恒 allow，也可能无法读取或修改恢复治理所需对象。不同实现还可能一部分继承 v1.4 的三维绕过，一部分只实现功能绕过。

最后一名超管被设置 `is_active=false` 时，有效超管计数应归零；但若该字段变更未走同一把锁，保护可被绕过。现有会话中间件又不检查 is_active，旧会话仍可能以只按角色判断的超管身份继续请求。

**最低修订要求**

1. 恢复唯一三维矩阵：超管功能恒 allow、数据恒 all、字段恒 editable；2.5 的业务门禁仍不得绕过。
2. 建立唯一的 `isEffectiveSuperAdmin()`，由运行时授权、最后超管统计和会话检查共同调用。
3. 明确 is_active=false 与 is_disabled=true 都进入同一 advisory lock、审计、epoch 和会话撤销事务。
4. 请求中间件同时校验两个状态，避免只阻止新登录却保留旧会话。
5. 增加最后超管 is_active 变更以及三维规则冲突测试。

### V15-05 [P1] 删除旧表后的回滚门禁不覆盖数据库兼容性和 allow 变化

**设计定位**

- 第 58～62 行依赖保留 `permission_role` 保证切换前版本可安全回滚。
- 第 110～113 行只在存在有效 deny/readonly/hidden/masked 时阻止回滚到缺少 Resolver 的版本。
- 第 147～148 行 Phase D 将删除 `permission_role`。

**代码依据**

- 当前旧代码通过角色关系读取 `permission_role`：`ipms-backend/app/Models/User.php:88-94`、`ipms-backend/app/Models/Role.php:21-24`。
- 旧表是独立物理表：`ipms-backend/database/migrations/2026_08_03_000004_create_permission_role_table.php:7-16`。

**失败场景**

Phase C 中管理员删除旧角色 allow，新表不再授权，但旧表仍是只读历史快照。若没有显式 deny，当前“有效限制规则”预检可能允许回滚到读取旧表的版本，旧 allow 随即复活。

Phase D 删除旧表后，即使系统没有 deny/readonly/hidden/masked，回滚到任何仍查询 `permission_role` 的构建都会直接发生数据库错误。当前能力矩阵只描述 Resolver 能力，没有把 schema 版本和 allow/默认语义纳入兼容性。

**最低修订要求**

1. Phase C 开放配置后，永久禁止回滚到读取 `permission_role` 的版本，不能以“当前没有限制规则”为例外。
2. 回滚能力矩阵必须包含 schema 版本、全部规则类型、默认语义和旧表读取能力。
3. 旧表只能在明确关闭旧构建回滚窗口后删除；或提供可验证的反向迁移和 permission_rules → permission_role 数据恢复步骤。
4. 明确回填与切换之间的写冻结或增量追平，避免旧系统在回填后新增授权而新表漏记。
5. 增加 allow 删除、无 deny 场景和 Phase D 表已删除场景的回滚演练。
