## 4. 详细发现与修改建议

### V18-01 [P1] 权限缓存边界未冻结，业务对象状态变化可能继续命中旧授权

**设计定位**

- 第 91～98 行的数据可见性依赖项目负责人、供应商组织、需求与项目关系、任务/缺陷所属项目、上传人等业务字段。
- 第 103 行的 epoch 触发源只覆盖权限规则/关系表及部分用户、组织字段。
- 第 107 行缓存键包含 `arguments_hash`，但未定义其规范化内容，也未说明是否允许缓存最终 `data_visible` 或 `action_qualified` 结果。

**失败场景**

用户因 `task.project_id=P1` 获得可见并缓存 allow。随后任务被转移至 P2，或用户被移出 P1，但权限规则表和 epoch 均未变化。如果缓存保存最终资源判定，原用户在最长 TTL 内仍可能读取或操作该任务。同类问题还覆盖项目负责人、供应商组织、需求项目关系、缺陷项目、文档项目/上传人及版本负责人变化。

此外，`permissions(code,module,action)` 和 `roles(code,user_type,is_system)` 会改变授权含义，却不在第 103 行冻结的配置 epoch 清单内。

**建议修改条文**

1. 冻结 `decision_kind` 封闭枚举和缓存边界：默认只缓存功能权限解析结果、scope 描述和字段规则；**禁止缓存最终 `data_visible`、动作特定资格及资源级 allow/deny 布尔值**。
2. 资源可见性和动作资格必须基于主库当前记录计算。若确需缓存最终结果，资源增加单调递增 `authz_version`，缓存键加入规范化 `dependency_fingerprint`；所有授权相关业务字段和关系变更必须与版本递增同事务提交。
3. `arguments_hash` 使用版本化的规范序列化和抗碰撞哈希，必须覆盖 permission、resource type/id、ability args、scope anchor 及依赖版本；禁止调用方自行选择性拼接。
4. 配置 epoch 增加 `permissions(code,module,action)`、`roles(code,user_type,is_system)` 以及后续所有会改变授权语义的注册元数据；触发事件明确包含 INSERT/UPDATE/DELETE/TRUNCATE。

**验收补充**

项目负责人/供应商组织变更、需求项目关系替换、任务/缺陷换项目或负责人、文档换项目/上传人、版本负责人变化后，旧 allow 必须立即失效。增加哈希字段遗漏、顺序差异、碰撞模拟和直接 SQL 修改权限元数据用例。

### V18-02 [P1] 构建状态机缺少数据库级单 current 与并发转换约束

**设计定位**

- 第 128～134 行只有 `(resource, closure, build_id)` 主键。
- 第 137 行描述 promote/rollback 的目标状态，但没有唯一 current、回滚窗口、锁顺序、期望代次或条件更新约束。

**失败场景**

主键只能阻止同一 build 重复，不能阻止同一 `resource + closure` 出现两个 `current`。B、C 两个候选并发 promote 时，若都先读到 A=current，可能分别把自身改成 current；两个构建随后均可通过 gate。直接 SQL 也可以插入第二个 current，或把 revoked 构建无条件改回 current。

**建议修改条文**

```sql
status NOT NULL CHECK (status IN ('candidate','current','retiring','revoked'));
CREATE UNIQUE INDEX ux_resource_auth_one_current
  ON resource_auth_builds(resource, closure)
  WHERE status = 'current';
```

若产品只支持单一回滚目标，再对 `retiring` 增加同维度部分唯一索引。状态记录增加 `generation bigint`、`transition_id uuid`、`status_changed_at`、`rollback_until`。

冻结转换事务：取得部署 advisory lock → 按 `resource, closure, build_id` 排序 `FOR UPDATE` → 验证 A=current、B=candidate、代次匹配且 B 的全部读/写闭包齐全 → 条件更新 A/B 并递增 generation → 校验影响行数 → 提交后切流。rollback 仅允许 B=current、A=retiring 且尚在窗口内；revoked 不得直接复活。

同时冻结流量与状态映射：normal 只接受 current；candidate 验证入口只接受指定 candidate；retiring 仅服务受控排空/回滚窗口，窗口结束后强制 revoked。

**验收补充**

直接插入第二个 current 被数据库拒绝；B/C 并发 promote 仅一个成功；中途故障不产生半切换；缺少任一闭包时拒绝；错误流量入口、过期 retiring 和窗口关闭后 rollback 均被拒绝。

### V18-03 [P1] 后台重新授权与领域写入之间存在 TOCTOU 窗口

**设计定位**

- 第 144 行固定顺序为“完整授权 → 领域事务”，明确把授权放在领域事务之外。
- 第 113 行 epoch 双读只保护权限计算与缓存写入，不能保护授权完成到领域写入开始之间的状态变化。

**失败场景**

后台任务完成当前权限检查后、开始领域事务前，另一事务禁用账户、撤销权限、移出项目、改变资源所属项目或改变动作资格。后台任务仍会使用刚刚得到的 allow 执行写入。长时间导出也可能在首批授权后持续输出随后已无权访问的数据。

**建议修改条文**

固定顺序改为：stale gate → 开启领域事务 → 取得作用域明确的授权 fence → 按统一顺序锁账户、目标资源及动作资格关系 → 从主库执行完整授权 → 领域写入与审计 → 提交。所有撤权、禁用、成员关系和授权相关资源变更事务必须取得同一对象/主体 fence 的排他锁，避免授权后被并发改写。

作业信封增加 `operation`、`ability_args_hash`、`payload_hash`、`expected_resource_version`；审计记录 `authorized_epoch`、资源版本和 `attempt_id`。长导出按 chunk 重新授权并锁定一致快照，不得用一次授权覆盖整个长任务。

**验收补充**

在“授权完成、写入开始前”设置并发屏障，分别执行撤权、禁用、移出项目、资源换项目和状态变化；领域写入及后续导出 chunk 必须被拒绝。增加统一锁顺序的死锁回归测试。

### V18-04 [P1] inactive 组织退出解析后可能通过默认回退反向放宽权限

**设计定位**

- 第 29、178 行规定 inactive 组织不贡献主体规则。
- 第 37～42 行在无有效组织规则时会继续使用其他主体或用户类型默认。

**失败场景**

组织原有功能 deny、数据 `none/projects` 或字段 hidden/masked 限制。组织停用后这些限制被整体移除，算法可能回退到类型默认 allow/all/editable，出现“停用组织反而增加权限”。inactive 中间节点截断子树只能收窄 `org_subtree`，不能消除此回退问题。

**建议修改条文**

增加“组织 active→inactive 单调不扩权”不变量，并冻结各维度行为：

- 功能权限：忽略 inactive 组织的 allow，保留其有效 deny；
- 数据范围：inactive 组织已有显式 scope 时按 `none` 参与组织层，防止回退到更宽类型默认；
- 字段权限：忽略 editable，保留 readonly/masked/hidden；
- 重新启用后才恢复其 allow、原 scope 和 editable 参与解析。

停用事务应锁组织、直接成员、规则和受影响子树，推进 epoch，并在提交前验证停用后的授权包络是停用前的子集。不满足单调性时整体拒绝并审计。

**验收补充**

覆盖“组织 deny + 类型默认 allow”“组织 none/projects + 类型默认 all”“组织 hidden + 默认 editable”、多组织并集、停用中间节点及重新启用；每个 active→inactive 用例都必须证明权限不扩大。

### V18-05 [P1] break-glass 只定义凭证消费，未冻结签发信任链和恢复后置不变量

**设计定位**

- 第 158～163 行定义恢复凭证绑定、过期、哈希存储和消费，但没有定义谁能签发、如何在零超管状态下安全写入凭证。
- 条文未规定 `super_admin` 系统角色缺失/损坏、目标账户 inactive/disabled/非内部类型时的修复或拒绝顺序，也未要求消费前验证最终有效超管数。

**失败场景**

有效超管为零且 `super_admin` 角色被删除、改码或类型损坏。命令可能先消费凭证，再因角色绑定失败而退出；系统仍无有效超管且凭证已失效。若目标是供应商账户，简单绑角色还会触发类型不变量。当前设计也无法判断一个凭证记录由可信离线主体签发还是由已失陷应用路径伪造。

**建议修改条文**

1. 冻结离线签发信任链：仅维护模式下由 root-only 工具或外部签名凭据签发；记录 `credential_id`、issuer、`issued_at`、expires_at、target、deployment_uuid、nonce、hash/signature、consumed_at、outcome。应用 HTTP、queue 和普通 CLI 无签发权限。
2. 给系统角色增加不可变 `system_key='super_admin'` 和数据库唯一约束；名称可展示修改，system_key、内部类型和系统标志不可降级。明确角色缺失/损坏时是按规范原子修复还是拒绝并走数据库恢复流程。
3. 恢复事务顺序：验证维护 fence → advisory lock → 凭证 `FOR UPDATE` → 校验签名/绑定/有效期/未消费 → 锁目标和系统角色 → 非内部目标拒绝且不消费 → 启用目标、解除 disabled、绑定角色、设置强制改密、递增 `session_epoch` → 重算有效超管数 ≥ 1 → 写审计并标记 consumed → 提交。
4. 任何失败必须整笔回滚且不得消费凭证；成功后必须存在可登录的有效超管，旧会话全部失效。

**验收补充**

覆盖未授权签发、角色缺失/改码/类型损坏、目标 inactive/disabled、外部目标、修复中途故障、并发双恢复和并发角色修改；失败事务不得消费凭证，成功事务必须建立有效登录路径。

## 5. 建议修改顺序

1. **先收紧运行时授权一致性**：V18-01、V18-03，冻结缓存边界及授权与领域操作的同事务/fence 协议。
2. **再补发布状态机数据库不变量**：V18-02，确保任何并发和直接 SQL 路径都不能产生双 current。
3. **冻结停用单调性**：V18-04，防止组织停用触发更宽默认权限。
4. **完成 break-glass 闭环**：V18-05，补签发信任链、系统角色身份和成功后置条件。
5. 修订为 v1.9 后再次静态复审；实现后分别执行缓存依赖、并发撤权、A/B 发布、组织停用和离线恢复演练。

## 6. 批准前门槛

1. 明确哪些授权结果可缓存，并证明业务对象变化不会复用旧 allow。
2. 以数据库约束和串行转换协议保证每个 resource/closure 最多一个 current。
3. 将后台完整授权和领域写入放入同一一致性边界，消除授权后竞态。
4. 保证组织停用在三个授权维度均单调不扩权。
5. 定义恢复凭证的可信签发、原子消费、系统角色修复策略和有效超管后置断言。
6. 完成相应负向、并发和运维演练后再批准开发。
