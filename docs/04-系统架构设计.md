### 1.2 分层架构说明

| 层级 | 名称 | 职责 | 核心组件 |
|:----:|------|------|---------|
| L1 | 用户层 | 用户交互入口，浏览器访问 | Chrome / Edge / Firefox |
| L2 | 接入层 | TLS 终止、反向代理、静态资源服务、请求限流 | Nginx 1.24 |
| L3 | 应用层-前端 | 用户界面渲染、交互逻辑、前端状态管理 | Vue 3 SPA + Element Plus + Pinia |
| L3 | 应用层-后端 | 业务逻辑、权限校验、数据持久化、邮件发送、定时任务 | Laravel 11 + PHP-FPM 8.2 |
| L4 | 数据层 | 业务数据存储、缓存、队列、文件持久化 | PostgreSQL 15 + Redis 7 + 本地文件系统 |

**层间通信方式：**

| 通信路径 | 协议/方式 | 说明 |
|---------|----------|------|
| 浏览器 -> Nginx | HTTPS (TLS 1.3) | 加密传输，公网通信 |
| Nginx -> PHP-FPM | FastCGI (Unix Socket) | 本地回环，比 TCP 更高效 |
| PHP-FPM -> PostgreSQL | TCP (127.0.0.1:5432) | PDO 连接池，持久连接 |
| PHP-FPM -> Redis | TCP (127.0.0.1:6379) | Predis/PhpRedis 扩展 |
| 前端 -> Laravel API | HTTPS + JSON | RESTful API，Sanctum Cookie 认证 |
| Laravel Scheduler -> Queue | Redis List | 定时任务投递到队列异步执行 |
| Laravel Queue Worker -> SMTP | TLS (587) | Outlook 邮件异步发送 |

### 1.3 核心设计原则

| 原则 | 说明 | 实践体现 |
|------|------|---------|
| **务实优先** | 技术选型以满足 MVP 为目标，不过度设计 | 单机部署，不做微服务拆分，不做分布式 |
| **安全内建** | 权限校验贯穿每一层，不依赖前端校验 | 后端三层校验（Middleware + Policy + Query Scope） |
| **数据隔离** | 三方用户数据严格隔离 | Eloquent Query Scope 层自动注入数据范围过滤条件 |
| **可追溯** | 所有关键操作不可篡改地记录 | 操作日志通过 Laravel Observer 自动写入，与业务解耦 |
| **约定优于配置** | 遵循框架最佳实践，减少配置决策 | Laravel 项目结构遵循官方约定，Service 层统一接口规范 |
| **中文优先** | 面向国内用户，所有界面和提示为中文 | Element Plus 中文语言包；Laravel 验证消息中文化 |
| **渐进增强** | MVP 快速交付，架构预留扩展点 | 文件存储接口抽象；队列驱动可替换；模块间低耦合 |

### 2.2 各层选型理由

#### 2.2.1 前端框架：Vue 3 (Composition API)

**选择理由：**

| 考量维度 | 分析 |
|---------|------|
| 学习曲线 | Vue 3 中文文档完善，上手速度快，适合国内团队。Composition API 提供比 Options API 更好的逻辑复用能力，便于在 8 个功能模块间共享权限校验、分页查询、表单验证等组合式函数（composables） |
| 生态匹配 | Element Plus 是 Vue 3 生态中最成熟的企业级 UI 组件库，Table / Tree / Form / Timeline 等组件直接覆盖 IPMS 的全部 UI 需求（需求列表、组织架构树、动态表单、状态流转时间线），且中文社区活跃度远高于 React 生态的 Ant Design |
| 构建效率 | Vite 提供亚秒级 HMR（热模块替换），开发体验明显优于 Webpack，对 <50 并发场景下的小型 SPA 项目编译速度和包体积均优于 CRA |
| 项目匹配 | IPMS 是典型的表单+列表密集型管理后台，Vue 响应式系统与 Element Plus 表单组件的双向绑定机制天然契合，代码量比 React 同类实现少 30%-40% |

**补充说明：** 如果团队原本熟悉 React，选择 Vue 3 的迁移成本也较低 -- Composition API 的设计理念与 React Hooks 高度相似，包含 ref/reactive (对应 useState)、computed (对应 useMemo)、watch (对应 useEffect)，团队可在 1-2 周内完成技术切换。

#### 2.2.2 构建工具：Vite

**选择理由：**

- Vite 基于原生 ES Module，开发服务器冷启动 <1 秒，HMR 几乎即时响应，极大提升开发体验
- 生产构建基于 Rollup，Tree-shaking 效果优于 Webpack，SPA 首屏加载体积更小
- Vue 3 官方推荐，create-vue 脚手架默认集成，配置简洁无需额外调优
- 对于 IPMS 这样的中小规模 SPA，Vite 的开箱即用特性减少了脚手架维护成本

#### 2.2.3 UI 组件库：Element Plus

**选择理由：**

- 国内最成熟的 Vue 3 企业级 UI 组件库，中文文档和维护活跃度在 Vue 生态中最高
- Table 组件（排序、筛选、分页、行选择、展开行）直接覆盖需求列表、任务列表、缺陷列表、日志查询页的复杂交互需求；Tree 组件原生支持组织架构树的拖拽和节点编辑；Timeline 组件完美呈现需求状态流转历史
- 内置中文语言包，无需额外国际化配置；表单验证规则丰富，覆盖 IPMS 所有表单场景
- 对 <50 并发的 PC Web 端管理后台，组件渲染性能和包体积完全匹配

#### 2.2.4 状态管理：Pinia

**选择理由：**

- Vue 3 官方推荐的状态管理库，TypeScript 支持完善，API 比 Vuex 简洁 60% 以上
- 模块化设计天然支持按功能域拆分 Store（authStore / projectStore / requirementStore 等），与 IPMS 的 8 大模块一一对应
- 内置 devtools 支持，便于开发阶段调试复杂的三方权限状态切换
- 对于管理后台的常规状态管理需求（用户信息、权限列表、当前项目上下文），Pinia 的轻量化恰到好处，无需引入更复杂的状态方案

#### 2.2.5 路由：Vue Router 4

**选择理由：**

- Vue 3 官方路由，与 Composition API 深度集成，支持路由级权限守卫（Navigation Guards）
- 动态路由添加（addRoute）机制允许根据用户角色（超管/项目经理/项目成员/供应商/系统用户）动态注入不同路由表，实现菜单和页面级的权限隔离
- 嵌套路由完美匹配 IPMS 的侧边栏+内容区布局结构

#### 2.2.6 后端框架：Laravel 11

**选择理由：**

| 考量维度 | 分析 |
|---------|------|
| 开发效率 | Laravel Eloquent ORM + API Resource + Form Request Validation 三层模型使得标准 CRUD 接口以极少量代码完成。对于 IPMS 这类以数据管理为核心的系统，Laravel 的 Artisan 命令行（生成 Model/Controller/Migration/Policy）可自动化大部分样板代码，开发效率高于 Django 约 30% |
| 认证与权限 | Laravel Sanctum 原生支持 SPA Cookie 认证，无需像 Django 那样依赖第三方 JWT 包；Laravel Policy + Gate 体系可直接实现功能权限和行级对象权限的组合校验，比 Django Guardian 更简洁且与框架深度绑定 |
| 任务调度 | Laravel Scheduler 仅需 1 条系统 cron 即可管理所有定时任务（到期扫描、邮件发送、数据清理），无需像 Celery Beat 那样额外维护独立的调度器进程和持久化 Broker |
| 队列系统 | Laravel Queue 原生支持 Redis 驱动，与 Scheduler 无缝集成，到期提醒扫描后直接 dispatch Job 到队列异步发送邮件，比 Celery 的配置和运维复杂度低一个数量级 |
| 社区生态 | Laravel 中文社区活跃（Laravel China、LearnKu），中文文档完善，团队遇到问题可快速检索解决 |
| 规模匹配 | 对于 <50 并发用户、<20 个项目的规模，PHP-FPM + Laravel 单体架构完全胜任。Nginx + PHP-FPM 的进程模型在这种低并发场景下比 Gunicorn + Django 更节省服务器内存（动态 worker 按需创建） |

**与 Django 方案的对比：**

| 维度 | Laravel 11 | Django 4.2 (旧方案) |
|------|-----------|-------------------|
| API 开发速度 | Eloquent API Resource + FormRequest，样板代码极少 | DRF ModelViewSet，需额外 Serializer |
| 认证集成 | Sanctum 内置，SPA 模式零配置 | 需安装 Simple JWT，手动配置 |
| 定时任务 | Laravel Scheduler (1 条 cron) | Celery Beat (独立进程+Broker) |
| 队列运维 | Supervisor 管理 Worker，配置简单 | Celery Worker + Beat，运维节点更多 |
| 部署复杂度 | Nginx + PHP-FPM，技术栈更单一 | Nginx + Gunicorn + Celery，进程更多 |
| 内存占用 | 动态 worker，空闲时内存极低 | Gunicorn 常驻 worker，固定内存占用 |

#### 2.2.7 API 认证：Laravel Sanctum (SPA 模式)

**选择理由：**

- Sanctum SPA 模式使用基于 Cookie 的 Session 认证，前端无需手动管理 Token，Axios 自动携带 Cookie，比 JWT 方案更安全（HttpOnly Cookie 防 XSS）
- 前后端同域部署时（Nginx 代理前端静态文件和 API），Cookie 自动工作，无需配置 CORS 复杂策略
- 内置 CSRF 保护（Laravel 自动为 SPA 提供 CSRF Cookie），安全性开箱即用
- 如未来需要对外开放 API（如移动端），Sanctum 也支持 API Token 模式，一套方案覆盖多种场景

#### 2.2.8 数据库：PostgreSQL 15（不变）

**选择理由：**

- 数据完整性：IPMS 有严格的数据隔离需求，PostgreSQL 原生 Row-Level Security 可作为应用层权限的最后一道防线
- JSONB 支持：操作日志的"变更详情"字段、接口文档的结构化元数据、组织架构树的路径存储，这些半结构化数据适合 JSONB 索引和高效查询
- Eloquent 兼容性：Laravel Eloquent 支持 PostgreSQL 的 JSONB、Array、Full-Text Search 等高级特性
- 复杂查询：跨模块关联查询（需求多系统关联、任务按供应商过滤）在 PostgreSQL 查询优化器下表现优异
- 许可证：完全免费的 PostgreSQL License，无商业风险
- 规模适用性：<20 个项目、万级数据量，PostgreSQL 在此规模下资源消耗极小

#### 2.2.9 缓存/队列：Redis 7

**选择理由：**

- 三大用途：Laravel Session 驱动 + Laravel Queue 驱动 + 热点数据缓存（如用户权限列表、组织架构树）
- Laravel Queue 官方推荐 Redis 驱动，吞吐量远高于 database 驱动，且管理工具（Laravel Horizon）提供可视化队列监控
- <50 并发场景下，Redis 资源消耗极低（<100MB 内存）
- 后续如需引入实时通知（WebSocket），Redis 可作为 Pub/Sub 通道，Laravel Broadcasting 原生支持

#### 2.2.10 定时任务：Laravel Scheduler

**选择理由：**

- Laravel Scheduler 仅需在服务器添加 1 条系统 cron（`* * * * * php artisan schedule:run`），所有定时任务逻辑（到期扫描频率、邮件发送时间）通过代码定义在 `routes/console.php` 中，无需像 Celery Beat 那样单独维护调度器配置文件
- 到期扫描任务是日级频率（每天早上 9:00），Scheduler 的 `->dailyAt('09:00')` 链式调用简洁直观
- Scheduler 内部将扫描到期的任务 dispatch 到 Laravel Queue（Redis 驱动）异步发送邮件，与业务逻辑解耦
- 运维简单：不需要额外的 Celery Beat 服务、不需要维护 Beat 调度数据库、不需要担心 Beat 进程挂掉

#### 2.2.11 文件存储：Laravel Filesystem

**选择理由：**

- Laravel Filesystem 提供统一的存储抽象（`Storage` Facade），默认使用 `local` 磁盘
- 文件量极小（<2000 个文件），单机本地存储完全满足需求，运维成本为零
- Nginx X-Accel-Redirect 机制：Laravel 鉴权通过后，由 Nginx 直接发送文件，不占用 PHP-FPM worker
- **扩展预留**：Laravel Filesystem 内置 S3 Driver，仅需修改 `.env` 中的 `FILESYSTEM_DISK=s3` 即可切换至对象存储，业务代码完全不需要修改

#### 2.2.12 API 规范：RESTful JSON

**选择理由：**

- Laravel API Resource 可将 Eloquent Model 自动转换为标准 JSON 响应，支持嵌套关联、条件属性、分页元数据
- RESTful 路由使用 Laravel 的 `apiResource` 一条语句即可生成全套 CRUD 路由
- 对管理后台的列表/表单/详情场景，RESTful 是自然匹配；MVP 无实时需求，无需引入 WebSocket/GraphQL
- JSON 响应格式使用 Laravel 的统一封装：`{ data: ..., message: ..., errors: ... }`

#### 2.2.13 Web 服务器：Nginx + PHP-FPM

**选择理由：**

- Nginx 是事实上的工业标准，功能覆盖 TLS 终止、静态文件、Gzip、限流、文件代理全部需求
- PHP-FPM 是 PHP 标准 FastCGI 进程管理器，与 Nginx 通过 Unix Socket 通信，性能优异
- `ondemand` 进程管理模式允许空闲时释放 worker 进程，对于 IPMS 这种工作时间使用的系统，可显著节省内存
- Ubuntu 22.04 官方源直接提供 Nginx 1.24 和 PHP 8.2，`apt` 一键安装

**Service 层设计说明：**

每个核心业务模块拆分为独立的 Service 类，Controller 仅负责接收请求和返回响应，所有业务逻辑在 Service 中实现。这种设计的优势：

- Controller 保持轻量（通常 <50 行），只做参数接收和响应格式化
- Service 类可被多个 Controller 复用（如 RequirementService 被 RequirementController 和 TaskController 调用）
- Service 类可独立进行单元测试，不依赖 HTTP 请求上下文
- 业务逻辑集中管理，避免散落在 Controller 和 Model 中

**依赖规则说明：**

| 依赖方向 | 关系说明 |
|---------|---------|
| UserService -> 所有模块 | 所有业务模块依赖用户认证和角色信息 |

### 5.2 服务进程规划

| 服务 | 进程模型 | 端口/路径 | 资源预期 | 管理方式 |
|------|:------:|:--------:|---------|---------|
| Nginx | 1 master + 2 worker | 80, 443 | ~50MB 内存 | systemd: nginx.service |
| PHP-FPM | ondemand, max 20 child | Unix Socket | 空闲 ~50MB, 满载 ~400MB | systemd: php8.2-fpm.service |
| Laravel Queue Worker | 3 进程（Supervisor） | -- | ~30MB/进程，总计 ~100MB | Supervisor: ipms-worker |
| PostgreSQL | 1 postmaster + workers | 5432 (127.0.0.1) | ~200MB | systemd: postgresql.service |
| Redis | 单线程 | 6379 (127.0.0.1) | ~50MB | systemd: redis-server.service |

**总内存估算：** 空闲 ~450MB，满载 ~800MB（建议服务器配置 2GB+ 内存，留足余量）

> 相比旧 Django 方案（Gunicorn 常驻 4 worker ~800MB + Celery Worker ~200MB + Celery Beat ~50MB，总计 ~1.5GB），Laravel 方案利用 PHP-FPM ondemand 模式在空闲时释放 worker，内存占用节省约 40%-50%。

### 5.3 Nginx Site 配置要点

```nginx
# /etc/nginx/sites-available/ipms.conf
# 核心配置要点（非完整配置代码）

server {
    listen 443 ssl http2;
    server_name 116.62.44.192;  # 暂用 IP，后续绑定域名

    # TLS 证书（Let's Encrypt Certbot 自动管理）
    ssl_certificate     /etc/letsencrypt/live/ipms.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/ipms.example.com/privkey.pem;

    # 安全头
    add_header Strict-Transport-Security "max-age=31536000" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "DENY" always;

    # 客户端最大上传体积（与 BR-5-01 一致：50MB）
    client_max_body_size 50m;

    # Laravel 应用根目录
    root /var/www/ipms/public;
    index index.php;

    # ================================================================
    # 前端 SPA 静态资源（Vite build 产物部署到 Laravel public/ 目录）
    # ================================================================
    location /assets/ {
        # Vite 构建产物（JS/CSS/images）
        expires 30d;
        add_header Cache-Control "public, immutable";
    }

    # ================================================================
    # 认证文件下载（内部重定向，不可直接 URL 访问）
    # ================================================================
    location /storage/download/ {
        internal;          # 仅允许 X-Accel-Redirect
        alias /var/www/ipms/storage/app/public/;
        expires 1h;
    }

    # ================================================================
    # Laravel API 请求 -> PHP-FPM
    # ================================================================
    location /api/ {
        try_files $uri /index.php?$query_string;
    }

    # ================================================================
    # Laravel Sanctum CSRF Cookie 端点
    # ================================================================
    location /sanctum/ {
        try_files $uri /index.php?$query_string;
    }

    # ================================================================
    # 前端 SPA（所有非 /api/ 路径返回 index.html）
    # ================================================================
    location / {
        try_files $uri /index.html;
    }

    # ================================================================
    # PHP-FPM FastCGI 处理
    # ================================================================
    location ~ \.php$ {
        fastcgi_pass unix:/run/php/php8.2-fpm.sock;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        include fastcgi_params;

        # 超时配置
        fastcgi_read_timeout 60s;
        fastcgi_send_timeout 60s;

        # 安全：阻止直接访问 .php 以外的文件
        fastcgi_param PATH_INFO $fastcgi_path_info;
    }

    # ================================================================
    # 安全：阻止访问敏感文件
    # ================================================================
    location ~ /\. {
        deny all;
        access_log off;
        log_not_found off;
    }
    location ~ \.(env|log|md|yml|xml)$ {
        deny all;
    }
}

# HTTP -> HTTPS 强制跳转
server {
    listen 80;
    server_name 116.62.44.192;
    return 301 https://$host$request_uri;
}
```

**配置要点说明：**

| 要点 | 说明 |
|------|------|
| SPA 路由 | 所有非 `/api/` 路径由 `try_files $uri /index.html` 返回 SPA 入口，Vue Router 接管前端路由 |
| API 代理 | `/api/` 路径直接转发给 PHP-FPM 处理，不在 Nginx 层缓存 |
| 文件下载 | `X-Accel-Redirect` 机制：Laravel 鉴权后返回 `X-Accel-Redirect` 头，Nginx 直接发送文件，避免 PHP 进程被文件 IO 阻塞 |
| 安全加固 | 禁止访问 `.env`、`.log` 等敏感文件和隐藏目录 |
| 上传限制 | `client_max_body_size 50m` 与 PRD BR-5-01 保持一致 |

### 5.4 PHP-FPM 进程池配置

```ini
; /etc/php/8.2/fpm/pool.d/ipms.conf
[ipms]
user = www-data
group = www-data

listen = /run/php/php8.2-fpm.sock
listen.owner = www-data
listen.group = www-data
listen.mode = 0660

; ondemand 模式：空闲时释放 worker，工作时间低并发场景最优选择
pm = ondemand
pm.max_children = 20
pm.process_idle_timeout = 60s
pm.max_requests = 500

; 安全：限制 PHP 脚本仅可访问项目目录
php_admin_value[open_basedir] = /var/www/ipms:/tmp

; 上传文件大小限制（与 Nginx client_max_body_size 一致）
php_admin_value[upload_max_filesize] = 50M
php_admin_value[post_max_size] = 52M
; 执行时间限制
php_admin_value[max_execution_time] = 60
```

**进程管理模式选择 `ondemand` 的理由：**

| 模式 | 特点 | 适用场景 |
|------|------|---------|
| static | 固定数量的 worker，始终占用内存 | 高并发、稳定的流量 |
| dynamic | 按负载动态调整 worker 数量 | 中等并发 |
| **ondemand** | **空闲时释放所有 worker，请求到来时按需创建** | **IPMS 适用：工作时间 <50 并发，非工作时间几乎无请求** |

### 5.5 Laravel Scheduler Cron 配置

```bash
# 在服务器上添加 1 条系统 cron（编辑 crontab -e）
* * * * * cd /var/www/ipms && php artisan schedule:run >> /dev/null 2>&1
```

**Scheduler 任务定义（`routes/console.php`）：**

```php
// 每天早上 9:00 扫描到期任务并发送提醒
Schedule::call(function () {
    // 1. 扫描即将到期和已逾期的任务
    // 2. 对每个到期任务 dispatch SendReminderEmail Job 到队列
    app(TaskService::class)->scanAndSendDueReminders();
})->dailyAt('09:00');

// 每天早上 9:00 扫描需求期望完成日期并提醒
Schedule::call(function () {
    app(RequirementService::class)->scanAndSendDueReminders();
})->dailyAt('09:00');

// 每天凌晨 2:00 清理回收站中超过 30 天的文档
Schedule::call(function () {
    app(DocumentService::class)->cleanTrash(30);
})->dailyAt('02:00');
```

**Scheduler 相比 Celery Beat 的优势：**

| 维度 | Laravel Scheduler | Celery Beat (旧方案) |
|------|------------------|---------------------|
| 系统依赖 | 仅需 1 条系统 cron | 需要独立的 Celery Beat 进程 + Redis/RabbitMQ Broker |
| 运维复杂度 | 无额外进程需要守护 | 需 Systemd 守护 Beat 进程，Beat 挂掉则所有定时任务停止 |
| 任务定义 | PHP 代码，定义在 `routes/console.php` | Python 代码 + Celery 配置文件 |
| 监控 | 通过 Laravel Log | 需额外 Flower 监控面板 |
| 故障恢复 | cron 每分钟触发 `schedule:run`，天然无单点 | Beat 进程需监控和自动重启 |

### 5.6 Supervisor Queue Worker 配置

```ini
; /etc/supervisor/conf.d/ipms-worker.conf
[program:ipms-worker]
process_name=%(program_name)s_%(process_num)02d
command=php /var/www/ipms/artisan queue:work redis --sleep=3 --tries=3 --max-time=300
autostart=true
autorestart=true
stopasgroup=true
killasgroup=true
user=www-data
numprocs=3
redirect_stderr=true
stdout_logfile=/var/www/ipms/storage/logs/worker.log
stopwaitsecs=3600

; 可选的 Laravel Horizon 面板（如需要队列可视化监控）
; [program:ipms-horizon]
; command=php /var/www/ipms/artisan horizon
; ...
```

**Queue Worker 参数说明：**

| 参数 | 值 | 说明 |
|------|:--:|------|
| numprocs | 3 | 启动 3 个 Worker 进程并行处理队列任务 |
| --sleep | 3 | 队列空闲时 sleep 3 秒后重新检查，降低 CPU 占用 |
| --tries | 3 | 单个 Job 最多尝试 3 次，失败后记录 failed_jobs 表 |
| --max-time | 300 | 单个 Worker 最多存活 300 秒后优雅重启（防内存泄漏） |
| stopwaitsecs | 3600 | 停止信号后等待 1 小时让当前 Job 执行完毕 |

### 6.2 权限校验执行层级

权限校验在**三个层级**执行，形成纵深防御：

| 层级 | 位置 | 校验内容 | 实现方式 |
|:----:|------|---------|---------|
| **L1: 前端路由层** | Vue Router Navigation Guards | 菜单/路由是否可见、操作按钮是否显示 | 根据用户角色动态注入路由表（router.addRoute），`v-permission` 指令控制按钮显隐。不依赖此层做安全防护，仅为提升用户体验 |
| **L2: API 视图层** | Controller + Policy + Global Scope | 功能权限：Policy 定义角色能否执行此操作；行级权限：Global Scope 自动过滤查询范围 | Sanctum 认证 + `$this->authorize()` Policy 调用 + Eloquent Global Scope 自动注入过滤条件 |
| **L3: 数据库层** | PostgreSQL RLS（可选） | 防止应用层 Bug 导致数据泄漏的最后一道防线 | 按 user_type + 项目归属配置 RLS 策略（安全加固阶段启用，MVP 可暂不配置） |

**权限校验流程图：**

```
请求进入
    |
    v

    |No -> 401 Unauthorized
    |Yes
    v
[Policy: 该角色能否执行此操作?]
    |No -> 403 Forbidden
    |Yes
    v
[Global Scope: 自动注入数据过滤条件]
    |
    v
```

| **状态** | 已确认 |

| **备选方案** | Laravel Passport (OAuth2) / JWT (tymon/jwt-auth) / Laravel Session (非 API) |
| **背景** | IPMS 是前后端分离的 SPA，需要安全的 API 认证方案。当前无移动端和第三方 API 接入需求，但需预留扩展能力 |
| **决策理由** | 1) Sanctum SPA 模式使用 HttpOnly Cookie 存储 Session，前端无需手动管理 Token，安全性优于 JWT 方案（防止 XSS 窃取 Token）；2) 前后端同域部署时，Cookie 自动工作，Axios `withCredentials: true` 零配置；3) 无需像 JWT 那样处理 Token 刷新逻辑，Session 生命周期由 Laravel 服务端统一管理；4) 如未来需要对外开放 API（如移动端），Sanctum 同时支持 API Token 模式，一套方案覆盖多种场景；5) 对于内部企业系统，Session 认证的用户体验（登录超时自动登出、管理员可强制下线）优于无状态 JWT |
| **代价** | Session 认证需要服务端存储（Redis），但 IPMS 本身就需要 Redis 做队列和缓存，不引入额外依赖。如未来部署负载均衡，需要配置 Session 共享（Redis 集中存储） |
| **后续承诺** | 如需对接企业 SSO（如 Azure AD），Laravel Socialite + Sanctum 可无缝集成 OAuth2 登录流程 |

### ADR-005：定时任务与队列方案选择 Laravel Scheduler + Laravel Queue

| 项目 | 内容 |
|------|------|
| **决策日期** | 2026-08-03 |
| **状态** | 已确认 |
| **决策** | 使用 Laravel Scheduler（系统 cron 驱动）+ Laravel Queue（Redis 驱动） |
| **备选方案** | Celery + Celery Beat (旧 Django 方案) / 独立 Go 定时任务服务 |
| **背景** | IPMS 需要每天早上 9:00 扫描到期任务并发送 Outlook 邮件提醒。邮件发送需异步化，避免阻塞扫描进程 |
| **决策理由** | 1) Scheduler 仅需 1 条系统 cron（`php artisan schedule:run`），所有定时任务逻辑在 `routes/console.php` 中以 PHP 代码定义，比 Celery Beat 少维护 2 个独立进程（Beat + Worker）；2) Queue Worker 由 Supervisor 守护（3 进程），配置简单，比 Celery 的 `celery multi start` 更标准化；3) Redis 同时作为队列驱动和缓存，一份基础设施覆盖两个场景，减少运维节点；4) 到期提醒是日级频率（非秒级），Scheduler 的 `->dailyAt('09:00')` 完全满足需求，不需要 Celery 的 crontab 语法和时区配置；5) 技术栈统一为 PHP 生态，开发者无需在 Python（Celery 任务代码）和 PHP（Web 业务代码）之间切换 |
| **代价** | Scheduler 的 cron 每分钟触发 `schedule:run`，每分钟有一次极轻量的 PHP 进程启动开销（约 5-10ms）。对于单机部署，此开销可忽略。Queue Worker 需要 Supervisor 管理，但 Supervisor 是 Ubuntu 标准包，运维成本极低 |
| **后续承诺** | 如需更复杂的队列监控，Laravel Horizon 提供可视化面板（Redis 驱动专属），可在 P1 阶段集成。如需秒级定时精度，可增加 cron 频率或引入 Swoole 常驻进程 |

### 8.2 HTTPS 配置方案

#### 8.2.1 技术方案

使用 **Let's Encrypt + Certbot + Nginx** 实现免费 HTTPS。

#### 8.2.2 前提条件

需要一个可公开解析的域名（如 `ipms.example.com`），其 DNS A 记录指向云服务器 IP `116.62.44.192`。如暂无域名：

- **开发/内测阶段**：可使用自签名证书或仅 HTTP（仅内网访问）
- **上线前**：必须配置正式域名和 HTTPS

#### 8.2.3 配置流程

```bash
# 1. 域名 DNS A 记录解析 -> 116.62.44.192（在域名服务商处配置）

# 2. 安装 Certbot
sudo apt update
sudo apt install certbot python3-certbot-nginx

# 3. 确保 Nginx 已配置 server_name 域名
#    server_name ipms.example.com;

# 4. Certbot 自动获取证书并配置 Nginx
sudo certbot --nginx -d ipms.example.com

# 5. 验证证书自动续期（Systemd timer 已自动配置）
sudo systemctl status certbot.timer

# 6. 手动测试续期
sudo certbot renew --dry-run
```

#### 8.2.4 安全加固 Nginx 配置

| 配置项 | 推荐值 | 说明 |
|--------|--------|------|
| TLS 版本 | TLS 1.2, TLS 1.3 | 禁用 TLS 1.0/1.1 |
| 加密套件 | ECDHE + AES-GCM 优先 | 前向安全性 |
| HSTS | max-age=31536000 | 强制浏览器一年内使用 HTTPS |
| OCSP Stapling | on | 加速证书状态验证 |
| SSL Session Cache | shared:SSL:10m | 复用 TLS 会话减少握手 |

### 8.3 Redis 缓存策略

#### 8.3.1 Redis 用途分配

| 用途 | Redis DB | 数据类型 | 过期策略 | 说明 |
|------|:-----:|---------|---------|------|
| Laravel Session | DB 0 | String | `SESSION_LIFETIME`（默认 120min） | 用户登录 Session，超时自动清理 |
| Laravel Queue | DB 0 | List + ZSet | 消费即删 | 到期提醒邮件队列，Job 消费后自动清除 |
| 用户权限缓存 | DB 1 | String (JSON) | TTL 30min | 缓存用户权限列表和角色，减少重复查询 |
| 组织架构树缓存 | DB 1 | String (JSON) | TTL 60min，修改时主动失效 | 三类用户的组织架构树结构 |
| 热点数据缓存 | DB 1 | String | TTL 10min | 项目列表、需求状态统计等频繁查询 |
| 限流计数器 | DB 2 | String + TTL | TTL 1min | API 请求频率限制（登录接口防暴力破解） |

#### 8.3.2 缓存策略细节

**用户权限缓存策略：**

```
读取权限流程：
    请求 -> Cache::get('user_permissions:' . $userId)
              |
        +-----+-----+
        |           |
    [命中缓存]  [未命中]
        |           |
        v           v
    直接返回   查询 DB 获取权限列表
               -> Cache::put(key, value, 30min)
               -> 返回权限列表

权限变更时：
    User 角色修改 -> Permission 变更 ->
    Cache::forget('user_permissions:' . $userId)
    下次请求自动重建缓存
```

**组织架构树缓存策略：**

```
读取树结构：
    Cache::remember('org_tree:' . $userType, 3600, function() {
        return OrgService::buildTree($userType);
    });

树结构变更时（新增/编辑/删除节点）：
    OrgService::updateNode() ->
    Cache::forget('org_tree:' . $userType)  // 主动失效
```

## 9. 扩展性预留

### 9.1 当前约束

| 维度 | 当前状态 | 设计上限 |
|------|---------|---------|
| 部署模式 | 单机（1 台云服务器） | 可通过增加服务器横向扩展 |
| 并发用户 | < 50 | PHP-FPM ondemand 模式 20 worker 可支撑 200+ |
| 项目数量 | < 20 | 无硬编码限制 |
| 文件存储 | 本地文件系统 | Laravel Filesystem 抽象，可切换至 S3/OSS |
| 数据量 | 万级记录 | PostgreSQL 单表百万级无性能问题 |
| 队列吞吐 | 日级任务（<100 封邮件/天） | Redis Queue 可支撑秒级万条吞吐 |

### 9.2 未来扩展路径

| 场景 | 当前设计预留 | 扩展方案 |
|------|------------|---------|
| **用户量增长（>500 并发）** | PHP-FPM ondemand 可增加 max_children；Nginx 可做负载均衡 | 增加服务器实例，Nginx upstream 到多台后端，Session/Queue 使用集中 Redis |
| **文件量增长（>100GB）** | Laravel Filesystem Storage Facade 抽象 | 修改 `FILESYSTEM_DISK=s3` 环境变量，切换至阿里云 OSS/AWS S3/MinIO，业务代码零修改 |
| **数据库读写瓶颈** | Eloquent ORM 抽象，无手写 SQL | 引入读写分离（Laravel 内置 read/write 连接配置），主库写入 + 只读副本查询 |
| **实时通知需求（浏览器推送）** | 独立 NotificationService，模块解耦 | 引入 Laravel Broadcasting + Redis Pub/Sub + Laravel Echo（WebSocket 客户端），前端监听实时事件 |
| **微服务拆分** | Service 层物理隔离，接口明确 | 按业务模块拆分为独立 Laravel 实例，API 网关（如 Traefik/Kong）统一路由，数据库按服务拆分 |
| **CI/CD** | 标准 Laravel 项目结构 | 引入 GitHub Actions / GitLab CI，`deploy/deploy.sh` 脚本自动化部署 |
| **容器化** | 标准项目目录 + .env 配置 | 编写 Dockerfile + docker-compose.yml，部署至 Docker Swarm / K8s |
| **监控告警** | Laravel Logging 标准输出 | 引入 Laravel Telescope（开发调试）+ Sentry（生产异常监控）+ Prometheus + Grafana（服务器性能监控） |
| **CDN 加速** | 前端静态资源在 public/assets/ | 配置 Vite `base` 为 CDN URL，构建产物上传至 CDN，Nginx 静态文件配置改为 CDN 引用 |
| **SSO 集成** | Sanctum + Laravel Socialite | 对接企业 Azure AD/OAuth 2.0 Provider，Socialite 驱动实现 OAuth 登录，Sanctum 签发 SPA Session |

### 9.3 为后续迭代预留的具体扩展点

| 迭代内容 | 优先级 | 架构预留策略 |
|---------|:------:|------------|
| 甘特图 | P1 | Task 模型已包含 `start_date` / `due_date` 字段，前端仅需引入 Gantt 图表库（如 dhtmlx-gantt 或 v-gantt-chart） |
| 数据报表/看板 | P2 | 独立 ReportService + ReportController，通过 Eloquent 聚合查询实现，不影响现有模块 |
| 移动端 | P2 | 现有 RESTful API 可直接复用，Sanctum API Token 模式开箱即用；移动端仅需开发新前端（uni-app / React Native） |
| 工时填报 | P2 | Task 模型预留 `estimated_hours` / `actual_hours` 字段，P2 阶段实现 UI 录入和统计聚合即可 |
| SSO 集成 | 未来 | Sanctum + Socialite 架构天然支持 OAuth 2.0 扩展，仅需增加 Socialite Provider 回调和 Session 绑定 |
| 多语言 | 未来 | Laravel `lang/` 目录已预留中文包，前端 Element Plus 国际化可扩展。架构上无阻塞 |
| 操作日志导出 CSV | P1 | AuditService 预留 `exportCsv()` 方法，P1 阶段仅需实现前端下载按钮 |
| 邮件通知扩展 | P1 | NotificationService 中的 `send()` 方法接受 `NotificationType` Enum，新增通知类型仅需添加新 Mail 类 + Mail 模板 |

## 附录 B：与旧方案（React + Django）的关键差异

| 维度 | 旧方案 (v1.0) | 新方案 (v2.0) | 变更理由 |
|------|-------------|-------------|---------|
| 前端框架 | React 18 + Ant Design 5 | Vue 3 + Element Plus | 中文生态更成熟，学习曲线更低，代码量更少 |
| 前端构建 | Webpack (CRA) | Vite | 开发体验提升（HMR <1s），构建产物更小 |
| 状态管理 | Zustand | Pinia | Vue 3 官方推荐，模块化设计更清晰 |
| 后端框架 | Django 4.2 | Laravel 11 | 开发效率更高，认证/队列/调度内置 |
| API 认证 | JWT (Simple JWT) | Sanctum SPA Cookie | HttpOnly Cookie 更安全，无需手动管理 Token |
| 定时任务 | Celery + Celery Beat | Laravel Scheduler | 少维护 2 个进程，运维复杂度大幅降低 |
| 消息队列 | Celery + Redis | Laravel Queue + Redis | 技术栈统一为 PHP，无 Python/PHP 混合维护负担 |
| 应用服务器 | Gunicorn 4 worker | PHP-FPM ondemand | 空闲时释放内存，节省 40%-50% 内存 |
| 文件下载 | X-Accel-Redirect | X-Accel-Redirect | 不变（Nginx 核心机制） |
| 数据库 | PostgreSQL 15 | PostgreSQL 15 | 不变 |
