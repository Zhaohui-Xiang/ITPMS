# IPMS 核心业务闭环重设计

**日期：** 2026-08-17  
**状态：** 已确认  
**目标环境：** Ubuntu 22.04 云端主机，首期使用公网 IP，同源部署  
**现有技术栈：** Vue 3、Vue Router、Pinia、Element Plus、Axios、Vite、Laravel 11、Sanctum、PostgreSQL、Redis

## 1. 决策摘要

本设计在现有代码基础上分阶段重构，不重新搭建前后端工程。保留可用的 Laravel 模型、迁移、权限 Scope、Policy 和控制器业务规则，统一前后端 API 契约，补齐测试、通知、多角色流程和项目发布版本。

首个可验收里程碑覆盖完整多角色闭环：

1. 系统用户提交跨系统需求。
2. 内部 IT 项目经理审核需求并为每个关联项目规划目标发布版本。
3. 内部 IT 或供应商项目经理拆分并分配任务。
4. 开发人员执行任务，测试人员提交并验证缺陷。
5. 内部 IT 项目经理通过质量门禁发布项目版本。
6. 系统用户查看上线和验收结果。

已确认的产品与技术约束：

- 云端没有必须保留的真实数据，允许重建数据库和初始化演示数据。
- 第一里程碑实现完整多角色权限，不采用单一管理员演示模式。
- 工作方式采用运营控制台：跨项目待办、风险和下一步操作优先。
- UI 采用浅色蓝白流程型语言，并融入 Voltage 完整字标、V 图标和深蓝品牌色。
- 通知采用站内通知加关键 Outlook 邮件。
- 暂无域名，先通过公网 IP 验收；架构与配置必须支持后续不修改业务代码即可切换域名和 HTTPS。
- 项目发布版本是独立项目级实体，项目内自定义编号，采用完整七阶段发布流程。

## 2. 目标与非目标

### 2.1 目标

- 消除前端 Mock 数据，核心页面全部使用真实 API。
- 统一前后端路径、HTTP 方法、字段命名、分页结构和错误结构。
- 让菜单、数据范围和操作权限随用户类型与角色变化。
- 让需求、任务、缺陷和项目发布版本形成可追溯闭环。
- 保证跨系统需求可以在不同项目中独立排期、开发、上线和验收。
- 为关键业务规则建立自动化测试和端到端验收。
- 在 Ubuntu 22.04 上形成可重复部署、重置、备份和回滚的运行方式。

### 2.2 首个里程碑不包含

- 甘特图、工时填报、移动端专用体验、数据分析报表和知识库。
- CI/CD 编排、生产环境部署执行、环境矩阵和自动回滚平台。
- 全局跨项目发布列车；发布版本只归属于单个项目。
- 多目标版本；一个需求在一个关联项目中最多只有一个目标版本。
- 普通文件的完整版本历史。保留现有 `version` 字段，但文件替换和快照属于后续文档模块补全范围。

## 3. 总体架构

### 3.1 前端

继续使用 Vue 3、Vue Router、Pinia、Element Plus、Axios、SCSS 和 Vite，不引入第二套组件库。

前端按以下边界组织：

- `components/layout`：Voltage 品牌导航、顶部栏、面包屑和页面框架。
- `components/common`：状态标签、用户选择器、空状态、错误状态和确认操作。
- `components/releases`：版本状态条、发布门禁、需求规划器和状态历史。
- `views`：只负责页面编排、路由参数和页面级数据加载。
- `api`：每个业务域一个 API 模块，路径与后端路由一一对应。
- `stores`：只保存跨页面状态；列表筛选和弹窗表单保留在页面或组合函数中。
- `composables`：权限、分页查询、冲突刷新和状态转换等可复用行为。

现有超过 600 行的页面在被修改时按职责拆分，不进行与核心闭环无关的全量重构。

### 3.2 后端

继续使用 Laravel 11、Sanctum、PostgreSQL 和 Redis。

控制器只负责请求验证、授权、调用领域服务和返回响应。新增或重构以下领域服务：

- `RequirementWorkflowService`：审核、项目侧交付状态、聚合状态和需求版本记录。
- `ProjectVersionService`：项目版本 CRUD、规划需求、状态流转和乐观锁。
- `ReleaseGateService`：计算发布条件并返回结构化检查结果。
- `ProjectReleaseService`：执行锁定、门禁、发布快照和状态更新事务。
- `NotificationService`：创建站内通知并分派邮件队列任务。

所有资源仍通过 Policy 做操作授权，通过现有 Scope 做行级数据过滤。超级管理员只在带原因强制发布时绕过发布门禁，仍受数据完整性、并发锁和允许来源状态约束，并写入审计日志。

### 3.3 同源认证

首期由同一 Nginx 站点提供前端静态文件和 `/api`、`/sanctum` 后端入口，继续采用 Sanctum SPA 会话认证：

1. 前端请求 `/sanctum/csrf-cookie`。
2. 前端提交 `/api/login`。
3. 后续 API 使用 HttpOnly 会话 Cookie 和 CSRF Token。

不在 `localStorage` 保存长期访问令牌。当前 API 客户端中 `/api/sanctum/csrf-cookie` 路径和备用 Bearer Token 逻辑应被移除或改正。

公网 IP 验收阶段使用同源 HTTP 和非 Secure 会话 Cookie。绑定域名后启用 HTTPS、`SESSION_SECURE_COOKIE=true`、HSTS 和 TLS 1.2/1.3，无需修改前端业务代码。

- 工作台按角色显示不同的待办统计和优先处理队列。

## 5. 多角色核心闭环

### 5.1 角色职责

| 角色 | 核心职责 |
|---|---|
| 系统用户 | 提交需求和缺陷，查看本人需求的项目版本、上线与验收结果 |
| 内部 IT 项目经理 | 审核需求、规划版本、分配负责人、推进状态、执行发布和验收 |
| 内部 IT 项目成员 | 编辑获授权需求、拆分任务、协作测试和处理缺陷 |
| 供应商项目经理 | 管理供应商侧任务和进度，查看版本范围与门禁，不改变版本状态 |
| 供应商开发人员 | 认领和执行任务、修复缺陷 |
| 供应商测试人员 | 提交测试结果、确认和复测缺陷 |
| 超级管理员 | 全局治理、用户与组织管理、审计和带原因的发布例外处理 |

### 5.2 需求状态

需求创建后进入 `PENDING_REVIEW`。审核通过时，为每个 `requirement_project` 关联初始化项目侧 `delivery_status=ASSIGNED`。审核驳回时仍保持 `PENDING_REVIEW`，但保存审核意见和驳回审计，提交人修改后可重新提交。

跨系统需求的全局 `requirements.status` 是列表兼容字段，由项目侧状态聚合计算：

- 审核前固定为 `PENDING_REVIEW`。
- 审核后取所有项目侧交付状态中的最低进度。
- 只有所有项目侧均 `DEPLOYED` 时，全局状态才是 `DEPLOYED`。
- 只有所有项目侧均 `ACCEPTED` 时，全局状态才是 `ACCEPTED`。

业务写入必须修改项目侧状态，再由服务层原子重算全局状态。前端不能直接写全局聚合状态。

### 5.3 任务与缺陷

任务和缺陷继续同时关联 `requirement_id` 与 `project_id`。它们通过对应的 `requirement_project` 记录推导目标项目版本，不重复保存 `project_version_id`，避免需求换版后产生不一致。

任务状态保持待开始、进行中、已完成、已挂起。缺陷状态保持待确认、已确认、修复中、待复测、已关闭、重新打开。项目版本门禁读取最新任务和缺陷状态，不使用缓存统计作为发布依据。

## 6. 项目发布版本

### 6.1 归属与编号

- 一个项目拥有多个发布版本。
- 版本编号由项目内自定义，例如 `v2.3`、`2026.08` 或 `R2026-Q3`。
- `project_id + code` 在数据库层唯一。
- 一个需求在每个关联项目中最多指定一个目标版本。
- `project_version_id` 允许为空，表示需求处于该项目的未规划池。

### 6.2 数据模型

#### `project_versions`

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `project_id` | 所属项目 |
| `code` | 项目内自定义且唯一的版本编号 |
| `name` | 版本名称 |
| `description` | 版本目标和范围说明 |
| `status` | 七阶段状态 |
| `owner_id` | 内部 IT 项目经理 |
| `planned_start_date` | 计划开始日期，可空 |
| `planned_release_date` | 计划发布日期 |
| `released_at` | 实际发布时间，可空 |
| `released_by_id` | 发布人，可空 |
| `release_notes` | 发布说明 |
| `lock_version` | 乐观锁整数，初始为 1 |
| `created_by_id` | 创建人 |
| `created_at` / `updated_at` | 创建与更新时间 |

#### `requirement_project` 补充字段

| 字段 | 说明 |
|---|---|
| `project_version_id` | 目标项目版本，可空 |
| `delivery_status` | 该需求在该项目中的交付状态 |
| `version_assigned_by_id` | 最近规划人，可空 |
| `version_assigned_at` | 最近规划时间，可空 |

#### `project_version_histories`

记录 `project_version_id`、`event_type`、可空的 `from_status` 与 `to_status`、`actor_id`、`reason`、`metadata` 和 `created_at`。`event_type` 区分状态推进、状态回退、需求加入、需求移出和需求换版。范围调整、回退和状态推进都写入历史，不允许通过普通业务接口删除。

#### `project_version_release_snapshots`

记录 `project_version_id`、发布时的需求范围、任务统计、缺陷统计、每项门禁结果、发布说明、`is_override`、`override_reason`、`released_by_id` 和 `released_at`。一个项目版本最多有一个正式发布快照，快照在发布后不可修改。

### 6.3 七阶段状态机

`DRAFT → PLANNED → IN_DEVELOPMENT → IN_TESTING → READY_TO_RELEASE → RELEASED → ARCHIVED`

允许的回退：

- `PLANNED → DRAFT`：撤回计划。
- `IN_DEVELOPMENT → PLANNED`：重新排期。
- `IN_TESTING → IN_DEVELOPMENT`：测试不通过。
- `READY_TO_RELEASE → IN_TESTING`：取消发布。

禁止跳级。所有回退必须填写原因。`RELEASED` 和 `ARCHIVED` 不允许回退；生产回滚由新建修复版本处理，部署记录作为后续扩展。

唯一的状态跳级例外是超级管理员带原因强制发布：只允许从 `IN_TESTING` 或 `READY_TO_RELEASE` 进入 `RELEASED`，并必须保存失败门禁、强制原因、发布快照和审计记录。草稿、已规划、开发中和已归档版本不能强制发布。

### 6.4 范围锁定

- 草稿、已规划和开发中允许项目经理自由规划需求。
- 测试中允许项目经理带原因换入或移出需求，并写入状态历史和审计日志。
- 待发布禁止范围调整，必须先回退到测试中。
- 已发布和已归档的版本范围、说明和关联需求全部只读。
- 仅没有关联需求且没有历史事件的草稿版本允许删除；其他版本只能按状态机推进或归档。

### 6.5 质量门禁

| 转换 | 强制条件 |
|---|---|
| 草稿 → 已规划 | 编号项目内唯一；负责人和计划发布日期完整 |
| 已规划 → 开发中 | 至少包含一个已审核需求；每个需求已分配执行负责人 |
| 开发中 → 测试中 | 项目侧需求状态均至少达到测试中；进入后冻结版本范围 |
| 测试中 → 待发布 | 项目侧需求全部待上线；任务全部完成；致命和严重缺陷全部关闭；发布说明完整 |
| 待发布 → 已发布 | 在事务中重新执行全部发布门禁 |
| 已发布 → 已归档 | 项目侧需求全部验收；无未关闭缺陷 |

超级管理员可绕过业务门禁，但不能绕过外键、唯一约束或并发锁。强制发布必须填写原因，保存失败检查项和发布快照，并发送高优先级站内通知。

### 6.6 正式发布事务

1. 锁定 `project_versions` 行和相关 `requirement_project` 行。
2. 验证 `lock_version` 和当前状态。
3. 从数据库重新加载任务、缺陷和项目侧需求状态。
4. 运行 `ReleaseGateService`。
5. 门禁失败则整体回滚并返回结构化阻断项。
6. 门禁通过或合法强制发布后，将相关项目侧状态更新为已上线。
7. 重算受影响需求的全局聚合状态。
8. 更新版本为已发布，写入实际时间、发布人和说明。
9. 保存发布快照、状态历史和审计日志。
10. 提交事务后创建站内通知并分派 Outlook 邮件队列任务。

同一版本的重复发布请求具有幂等结果：第一次成功后，后续请求返回当前已发布状态，不重复发送发布通知。

## 7. 前端页面与路由

### 7.1 工作台

工作台按角色显示待审核需求、临期任务、待确认缺陷、发布风险和优先处理队列。项目版本临近发布日期、门禁失败或被强制发布时进入风险队列。

### 7.2 项目与版本

- 项目详情增加“发布版本”页签，展示当前版本、未来计划、历史版本和未规划需求数。
- 版本列表支持状态、负责人、计划发布日期和关键词筛选。
- 版本详情集中展示七阶段流程条、版本范围、任务完成度、严重缺陷、发布就绪度、发布说明和历史。
- 规划需求使用抽屉或对话框，从当前项目的未规划需求池选择。
- 测试阶段换版必须填写原因；待发布和已发布版本不显示可编辑入口。

建议新增路由：

- `/projects/:projectId/versions`
- `/project-versions/:id`

### 7.3 需求详情

跨系统需求按项目显示：项目名称、项目侧交付状态、目标版本、负责人、任务进度和缺陷状态。全局聚合状态作为概览，不替代项目侧状态。

### 7.4 其他核心页面

- 需求列表、任务列表和缺陷列表保留一致的筛选、分页和批量清空筛选方式。
- 项目详情移除 Mock 数据并使用真实项目、需求和版本统计。
- 顶栏通知数字来自真实未读站内通知，不保留固定数字。
- 个人信息入口必须指向存在的页面或对话框，不保留失效的 `/profile` 路由。
- 首期移除没有后端契约的全局系统设置编辑页和虚假“已保存”操作；个人提醒偏好通过真实后端接口保存在个人资料对话框中，部署与邮件凭据只由云端受保护环境管理。

## 8. API 契约

### 8.1 通用响应

成功响应：

```json
{
  "code": 200,
  "message": "success",
  "data": {}
}
```

失败响应：

```json
{
  "code": 409,
  "error_code": "RELEASE_GATE_FAILED",
  "message": "发布门禁未通过",
  "errors": [],
  "trace_id": "server-generated-request-id"
}
```

分页请求统一使用 `page` 和 `page_size`，分页响应统一返回 `items`、`page`、`page_size`、`total` 和 `total_pages`。前端不再同时兼容多个分页结构。

### 8.2 项目版本接口

| 方法与路径 | 用途 |
|---|---|
| `GET /api/projects/{projectId}/versions` | 查询项目版本 |
| `POST /api/projects/{projectId}/versions` | 创建项目版本 |
| `GET /api/project-versions/{id}` | 获取版本详情 |
| `PUT /api/project-versions/{id}` | 编辑可修改字段 |
| `DELETE /api/project-versions/{id}` | 删除没有范围和历史的草稿版本 |
| `POST /api/project-versions/{id}/status` | 推进或回退状态 |
| `GET /api/project-versions/{id}/gate-check` | 获取实时门禁结果 |
| `POST /api/project-versions/{id}/release` | 正式或强制发布 |
| `GET /api/project-versions/{id}/history` | 获取状态与范围历史 |
| `PUT /api/requirements/{requirementId}/projects/{projectId}/version` | 规划或调整目标版本 |
| `DELETE /api/requirements/{requirementId}/projects/{projectId}/version` | 移回未规划池 |

版本编辑、状态转换和发布请求必须携带 `lock_version`。成功写入后返回递增后的 `lock_version`。

### 8.3 现有接口对齐

实现阶段以 Laravel 路由作为契约源，逐项修复当前差异：

- 项目归档统一为 `POST /projects/{id}/archive`。
- 需求审核、状态转换、任务状态和缺陷动作统一使用后端已有的 `POST`。
- 文档和接口文档使用项目级路径，不保留不存在的全局列表路径。
- 通知配置统一为 `/notification-configs`，日志统一为 `/notification-logs`。
- 删除未实现的前端 API，或在明确纳入范围后补充后端路由和测试。

## 9. 错误、并发和恢复

| `error_code` | HTTP | 前端行为 |
|---|---:|---|
| `VERSION_CODE_EXISTS` | 422 | 标记版本编号字段并保留表单内容 |
| `INVALID_VERSION_TRANSITION` | 409 | 刷新状态和允许操作，不自动重试 |
| `RELEASE_GATE_FAILED` | 409 | 展示全部阻断项并定位到门禁页签 |
| `STALE_VERSION` | 409 | 提示数据已更新，重新加载后由用户再次确认 |
| `VERSION_LOCKED` | 409 | 切换为只读视图 |
| `FORCE_REASON_REQUIRED` | 422 | 标记强制原因字段 |
| `FORBIDDEN` | 403 | 隐藏无权限操作并显示统一无权限页或提示 |
| `UNAUTHENTICATED` | 401 | 清理本地用户状态并跳转登录 |

网络超时不自动重放状态转换或发布命令。用户可刷新详情确认服务器最终状态。发布接口依靠状态和快照保证重复提交不产生第二次发布。

邮件发送失败不回滚已提交的业务事务。失败任务进入 Laravel 失败队列和通知日志，支持管理员重试。

## 10. 通知

### 10.1 站内通知

以下事件创建站内通知：需求提交、审核和分配，任务分配和临期，缺陷指派、修复和复测，版本状态变化、测试阶段换版、门禁失败、正式发布和强制发布。

顶栏提供未读数量、最近通知、单条已读和全部已读。通知必须链接到用户有权限访问的业务对象。

### 10.2 Outlook 邮件

关键邮件事件：

- 需求审核结果和负责人分配。
- 任务临期或超期。
- 缺陷指派、修复完成和复测结果。
- 项目版本进入测试、进入待发布、正式发布和强制发布。

邮件通过 Redis 队列异步发送。生产环境使用 Microsoft Graph `sendMail` 和 Microsoft Entra OAuth 2.0 应用身份；不使用 Exchange Online SMTP Basic Authentication。租户 ID、客户端 ID、客户端密钥和发件邮箱只存储在云端环境变量或受保护的配置中，不写入代码、日志、设计文档或前端。该选择遵循 [Microsoft 关于 Exchange Online Basic Authentication 退役的说明](https://learn.microsoft.com/en-us/exchange/clients-and-mobile-in-exchange-online/deprecation-of-basic-authentication-exchange-online)。

### 11.3 端到端

1. 系统用户提交关联两个项目的需求。
2. IT 项目经理审核并为两个项目选择不同目标版本。
3. 供应商项目经理分配任务，开发人员完成任务。
4. 测试人员提交严重缺陷，验证门禁阻断。
5. 开发人员修复，测试人员复测并关闭缺陷。
6. IT 项目经理进入待发布并正式发布其中一个项目版本。
7. 验证另一个项目仍保持独立开发状态，全局需求状态正确聚合。
8. 验证站内通知、邮件队列记录和审计日志。

## 12. 云端部署设计

目标主机使用 Ubuntu 22.04。同一 Nginx Server Block 提供前端和 API：

- `/` 指向 Vite 构建产物，并回退到 `index.html`。
- `/api` 与 `/sanctum` 代理或转发至 Laravel/PHP-FPM。
- PostgreSQL 保存业务数据，Redis 承担队列和缓存。
- Supervisor 或 systemd 保持 Laravel Queue Worker 运行。
- Laravel Scheduler 每分钟触发到期提醒扫描。

部署过程包括：

1. 备份当前配置和数据库，即使当前无真实数据也保留恢复点。
2. 安装锁定依赖并构建前端。
3. 设置环境变量和目录权限。
4. 执行数据库重建、迁移和演示数据初始化。
5. 重启 PHP-FPM、队列和定时任务。
6. 校验健康检查、登录、核心闭环和静态资源。
7. 验收通过后再清理旧构建，保留上一版本用于快速回滚。

正式上线前必须更换已在会话中暴露的高权限密码，使用 SSH 密钥和非 root 部署账号。设计和代码中不得保存服务器密码。

## 13. 验收标准

- 六类业务角色和超级管理员使用独立账号完成权限隔离。
- 登录、项目、需求、任务、缺陷、版本和通知页面不再使用 Mock 数据。
- 前端 API 与 Laravel 路由没有已知路径或 HTTP 方法不一致。
- 跨系统需求可按项目指定不同版本和不同项目侧交付状态。
- 已发布版本不可修改，所有状态、换版和强制发布可追溯。
- 门禁能阻止未完成需求、任务及未关闭致命或严重缺陷发布。
- 站内通知和关键 Outlook 邮件按规则触发，邮件失败不破坏业务事务。
- 后端核心 Feature Tests、前端组件测试和 Playwright 多角色闭环全部通过。
- Ubuntu 云端环境可通过脚本重复部署和重置，且不依赖本地个人路径或明文凭据。

## 14. 风险与控制

- **现有 API 契约分裂：** 先建立接口清单和契约测试，再逐页面接入。
- **跨系统需求只有全局状态：** 新增项目侧状态，服务层统一聚合，禁止前端直接写全局状态。
- **页面文件过大：** 只拆分本里程碑触及的页面，按业务组件而非任意行数切分。
- **无现有自动化测试：** 每个行为变更先建立失败测试，再实现最小代码。
- **公网 IP 无 HTTPS：** 仅用于阶段验收；获取域名后立即启用 HTTPS 和 Secure Cookie。
- **根目录不是 Git 仓库：** 设计文档可以写入，但在建立或指定仓库前无法形成可审计提交。
