**文档版本**: v1.8
**创建日期**: 2026-09-29
**文档状态**: 修订稿（已回应六次复审 V17-01~08，待七次复审）
**修订历史**:
- v1.0：初稿；v1.1：字段级权限与可扩展性约定（D18）
- v1.2：初审（PA-01~09）；v1.3：复审（V12-01~06）；v1.4：二次复审（V13-01~06）；v1.5：三次复审（V14-01~05）；v1.6：四次复审（V15-01~05）；v1.7：五次复审（V16-01~06）

**背景**: 走查发现超管无用户管理界面（P8）、角色权限只能靠改 Seeder 代码调整、数据可见范围硬编码在用户类型上。目标是把权限体系重构为可按 **组织架构 / 角色 / 账户** 三级自定义配置的形式。

---

## 1. 现状盘点

- 功能权限：`permissions`（35 码）+ `permission_role`（仅可授予）+ `role_user`（无类型一致性约束）；`User::hasPermission()` 300s 缓存；矩阵写死在 Seeder（I15）；
- 数据权限：4 个 Scope 按 `user_type` 硬编码；列表（Scope）与详情/写（Policy）两套独立判定；
- 模型事实（实施以真实列名为准）：Task/Defect 各自持有独立 `project_id`；Requirement 经 `requirement_project` 关联多项目；Document 上传人字段为 `uploaded_by_id`；`EnsureUserIsActive` 当前只校验 `is_disabled`；`organizations.parent_id` 仅自引用 FK + cascade，无环约束；
- 部署事实：candidate/current 两阶段发布共享数据库与缓存；queue 用 Redis（`after_commit=false`），存在 FPM/queue/scheduler/CLI 多类写入者与执行者；
- 管理界面：无用户/角色/权限配置界面。

---

## 2. 目标架构

### 2.1 三级主体与三维度

主体三级：**组织 → 角色 → 账户**；兜底为用户类型内置默认（现有硬编码规则原样保留）。组织候选集（冻结）= 用户**直接所属**组织，不含祖先、不向下继承；多组织归属各组织规则平等参与。**inactive 组织不贡献主体规则**（见 2.13）。

### 2.2 三维度解析真值表（冻结）

**功能权限**（组织/角色/账户规则全部参与，无遮蔽）：

| 条件 | 结果 |
|------|------|
| 任一主体存在该权限码未过期 deny（超管除外，见 2.10） | **deny** |
| 否则任一主体存在未过期 allow | allow |
| 无任何规则 | 用户类型内置默认 |

**数据范围**（层级覆盖，同层并集）：账户 > 角色 > 组织 > 类型默认；同层多主体取并集。
**字段权限**（全局最严格）：`hidden > masked > readonly > editable`；无配置 = editable。

### 2.3 操作资格公式

```
操作资格 = 功能权限 ∧ 数据可见 ∧ 动作特定资格
```

数据范围扩大永不替代动作资格。**不可配置覆盖清单**（维护于注册表 `non_overridable` 字段 + Policy 测试矩阵）：① 发布门禁完整性（全量数据计算）；② 缺陷复测资格；③ 项目版本负责人关系；④ 强制发布例外流程（独立、带原因、入审计）。配置只能收紧；超管同样不绕过（仅可经 ④）。

### 2.4 权限规则存储（v1.8 定稿）

三可空外键：`user_id?/role_id?/organization_id?` + XOR CHECK + 部分唯一索引。

- `permission_rules`（subject, permission_id, effect, reason, granted_by_id, expires_at?）
- `data_scopes`（subject, module, scope_type, org_id?）+ `data_scope_projects`（明细）
- `field_permissions`（subject, resource, field, effect）

**约束（全部数据库级可执行）**：
- 一主体一模块至多一条 data_scopes（唯一索引）；
- 同行 CHECK：`(scope_type='org_subtree') = (org_id IS NOT NULL)`；
- **module × scope_type 完整封闭矩阵（回应 V17-01）**，两列均 NOT NULL：

```sql
CHECK (
  (module IN ('project','requirement','task','defect','document')
   AND scope_type IN ('all','own','org_subtree','projects','none'))
  OR
  (module = 'audit' AND scope_type IN ('all','own','none'))
)
```

  新增模块/范围类型必须先经 migration 更新矩阵，未更新时数据库拒绝写入，禁止"未知值回退默认"；
- projects 最小基数：延迟约束（INITIALLY DEFERRED）保证提交时至少一条明细；删最后一条明细必须同事务改 none/删规则/被拒；
- 明细归属：延迟触发器保证父规则 scope_type='projects'；
- scope_type 切换单事务完成，中间态 fail closed；
- **锚点 `org_id` → `ON DELETE RESTRICT`**（先同事务改 none 或换锚）；主体删除级联删规则；`granted_by_id` nullOnDelete；项目删除级联删明细；规则硬删除；
- 验收：直接 SQL 插未知 module/拼错 scope_type/audit 非法组合、删最后明细、删锚点且下层默认更宽。

**主体类型数据库不变量（v1.8 新增，回应 V17-06）**：
- `roles` 增加 `user_type` 列；不变量：`role_user` 要求 `users.user_type = roles.user_type`；`organization_user` 要求 `users.user_type = organizations.org_type`；`super_admin` 角色只能绑定内部用户类型；
- 实现对 role_user/organization_user 的 INSERT/UPDATE 及 users/roles/organizations 的类型字段 UPDATE 加 DEFERRABLE constraint trigger；
- 类型变更事务：锁用户 → 锁关联角色与组织 → 校验或迁移全部绑定 → 改类型 → 推 epoch → 提交；不能完整迁移则整体拒绝；
- Phase A 先扫描存量错配；验收：直接 SQL 跨类型插入、带绑定改类型、并发改类型/加角色、超管改非内部类型。

### 2.5 数据范围逐模块集合函数（不变）

| module | all | own | org_subtree | projects | none |
|--------|-----|-----|-------------|----------|------|
| project | 全表 | manager_id=我 ∪ 我提交需求所关联项目 | supplier_org_id ∈ org_id 子树 | id ∈ 明细 | 空集 |
| requirement | 全表 | submitter_id=我 | EXISTS 关联项目 ∈ S(project, org_subtree) | EXISTS 关联项目 ∈ 明细 | 空集 |
| task | 全表 | assignee_id=我 | task.project_id ∈ S(project, org_subtree) | task.project_id ∈ 明细 | 空集 |
| defect | 全表 | reporter_id=我 | defect.project_id ∈ S(project, org_subtree) | defect.project_id ∈ 明细 | 空集 |
| document | 全表 | uploaded_by_id=我 | document.project_id ∈ S(project, org_subtree) | document.project_id ∈ 明细 | 空集 |
| audit | 全表 | actor_id=我 | 不支持 | 不支持 | 空集 |

Task/Defect 锚定自身 `project_id`；需求多项目可见性不向下扩散。

### 2.6 缓存失效、epoch 与一致性读取协议（v1.8 修订，回应 V17-04/V17-05）

1. **TTL 截断** = min(300s, 最近 expires_at − now)，可控时钟边界测试；
2. **epoch**：单行 `permission_epoch` 全局计数器，数据库触发器递增；触发字段全清单（冻结）：六张规则/关系表 + `organizations(parent_id, org_type, is_active)` + `users(user_type, is_active, is_disabled)`；
3. **缓存键（冻结，回应 V17-04）**：

```text
perm:{deployment_uuid}:{accepted_auth_digest}:{epoch}:{decision_kind}:{subject}:{arguments_hash}
```

   - `deployment_uuid` 每次部署生成；数据库恢复/反向迁移/epoch 重建必须原子更换 UUID 或清空全部权限缓存；
   - `accepted_auth_digest` 由**当前进程根据自身 build_id 计算且已通过 stale gate**（见 2.8），禁止用可变 current 别名；不同摘要之间不得预热/复制/读取缓存；retiring 构建只用自身命名空间；
   - 验收：A/B 构建同 Redis 同 epoch 产生相反判定，按 A→B、B→A、B 失败回滚 A 三种顺序验证零交叉命中；
4. **一致性读取协议（冻结，回应 V17-05）**：① 主库读 e1 → ② 按 e1 查缓存；未命中时**从主库**计算完整权限（禁止只读副本）→ ③ 主库再读 e2 → ④ 仅当 e1=e2 才返回并写入 e1 键，否则丢弃重试 → ⑤ 有界重试仍不稳定则 fail closed 且不写缓存；缓存命中返回前同样校验 epoch 未变。验收：并发屏障卡在关键四点，证明旧结果不进入新 epoch 键。

### 2.7 字段级权限（读/写闭包分离，不变）

`editable` 随时可配；`readonly` 需写入闭包激活；`hidden/masked` 需读+写闭包激活。masked 默认不可写，脱敏回写 422 `FIELD_FORBIDDEN`。

### 2.8 授权注册表与切换状态（v1.8 修订，回应 V17-02）

**注册表**（`config/authorization.php`）：route、ability、phase、route_models、body_models、ability_args、outputs、channel、auth_only、non_overridable。

**激活摘要**：SHA-256(注册表该资源条目 + 授权消费者文件清单哈希)；消费者清单按资源显式登记并指定 owner。

**构建级状态子表（回应 V17-02，替代单行双摘要）**：

```text
resource_auth_builds(
  resource, closure,      -- closure: read | write
  build_id, digest,
  status,                 -- candidate | current | retiring | revoked
  activated_at, activated_by,
  PRIMARY KEY(resource, closure, build_id)
)
```

**状态机（冻结）**：① prepare：B 以 candidate 插入，仅供候选验证流量；② promote 单事务：A current→retiring、B candidate→current；③ rollback 单事务逆转换；④ 关闭回滚窗口：A retiring→revoked；⑤ gate 校验必须同时匹配 resource、closure、当前进程 build_id、digest、允许状态。**每个 build 分别完成读/写闭包激活，禁止继承另一 build 的闭包证明。**

**stale gate 全通道**：校验下沉共享 Resolver/服务边界——HTTP 503 `AUTH_STATE_STALE`；queue 可重试失败；scheduler/CLI/导出 fail closed 并告警；任何通道不得回退 editable/allow。长驻 worker 未重启、候选失败回滚纳入演练。

### 2.9 后台任务执行时重新授权（v1.8 新增，回应 V17-07）

- **作业信封契约**：`actor_user_id`、`permission_code`、`resource_type/resource_id`、`correlation_id`、`enqueued_at`；**禁止序列化 `authorized=true`**；
- **handle 固定顺序**：stale gate → 加载当前账户状态 → 重新执行"功能权限 ∧ 数据可见 ∧ 动作资格"完整公式 → 领域事务；
- 失败分类：`AUTH_STATE_STALE` 可重试；`AUTH_REVOKED`/账户失效/资源越权——终止并审计，不得重试后重获权限；
- scheduler 用最小权限 service principal；CLI 默认拒绝，必须显式 actor；
- 依赖事务结果的任务：`after_commit=true` 或 `DB::afterCommit`；
- 验收：入队后撤权/禁用/移出项目/scope 收窄/stale 与 revoked 重试分类。

### 2.10 超管治理不变量（不变 + 恢复凭证契约重写，回应 V17-03）

**三维矩阵**：功能恒 allow、数据恒 all、字段恒 editable；2.3 不可绕过清单对超管同样有效。

**唯一判定**：`isEffectiveSuperAdmin()` = `isSuperAdmin()` && `is_active` && `!is_disabled`——运行时授权、最后超管统计、会话检查共同调用。

**保护路径**：禁用、降权、删除、角色解绑、批量角色同步、is_active=false、super_admin 角色实体变更——同一 `pg_advisory_xact_lock` 事务，锁内重算，归零即拒绝。**部署前置断言：有效超管 ≥ 1，否则中止部署。**

**离线恢复命令契约（v1.8 重写，回应 V17-03）**：`ipms:recover-superadmin`
- **执行条件**：仅当有效超管数 = 0；执行前验证 nginx 维护锁存在且 FPM/queue/scheduler 均已停止；
- **凭证**：绑定 `deployment_uuid + target_user_id + nonce`，有效期 ≤ 15 分钟；系统只持久化凭证哈希、expires_at、used_at；在同一 advisory-lock 事务内原子标记 used_at，过期/重放立即拒绝；
- **审计**：记录 operator、target、before/after、build_id，**不记录原始凭证**；
- **执行后**：撤销目标账户全部旧会话并强制修改密码；
- 验收：在线执行拒绝、非零超管拒绝、过期、重放、并发双执行、审计脱敏。

**会话**：`EnsureUserIsActive` 同时校验 `is_disabled` 与 `is_active`；降权/禁用/停用撤销既有会话，重启用不恢复。

### 2.11 回滚契约（不变）

Phase C 起永久禁止回滚到读取 `permission_role` 的构建；能力矩阵 = schema 版本 + 规则类型 + 默认语义 + 旧表读取能力；旧表在回滚窗口显式关闭后删除；三场景演练。

### 2.12 单事实源切换的完整停写顺序（不变，V16-06 已关闭）

nginx 维护页 → 停 FPM/queue/scheduler/CLI → `permission_role` DB 触发器写保护 → 回填核对 → 切流重启 → 验证 → 开放流量；不能全停用双写+对账。

### 2.13 组织图合法性与 inactive 语义（v1.8 新增，回应 V17-08）

- **图不变量**：按 org_type 分区的有根森林——`parent_id <> id`、父子 org_type 相同、禁止任何祖先环；
- **inactive 语义（冻结）**：inactive 组织不贡献主体规则；`org_subtree` 仅包含从 active 锚点出发且**整条路径均 active** 的节点——inactive 中间节点截断全部后代；
- **重挂事务**：按 org_type 固定 key 取 advisory xact lock → 锁节点与候选祖先链 → 递归校验类型与环 → 更新 parent_id → epoch 触发 → 提交；
- 验收：自环、两节点环、跨类型父节点、并发 A→B/B→A、停用锚点、停用中间节点、重新启用。

### 2.14 可扩展性约定（不变）

permissions 表注册中心；注册表单一事实源；新资源敏感字段随 migration 登记；前端 `v-perm` / `v-field-perm`。

### 2.15 管理界面（不变）

系统管理菜单组（仅超管）：用户管理 / 角色管理 / 权限审计画像。配置开放受 `resource_auth_builds` 分阶段激活的服务端强制。
