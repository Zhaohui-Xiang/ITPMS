**文档版本**: v1.7
**创建日期**: 2026-09-29

- v1.2：初审（PA-01~09）；v1.3：复审（V12-01~06）；v1.4：二次复审（V13-01~06）；v1.5：三次复审（V14-01~05）；v1.6：四次复审（V15-01~05）

**背景**: 走查发现超管无用户管理界面（P8）、角色权限只能靠改 Seeder 代码调整、数据可见范围硬编码在用户类型上。目标是把权限体系重构为可按 **组织架构 / 角色 / 账户** 三级自定义配置的形式。

---

## 1. 现状盘点

- 功能权限：`permissions`（35 码）+ `permission_role`（仅可授予）+ `role_user`；`User::hasPermission()` 300s 缓存；矩阵写死在 Seeder（I15）；
- 数据权限：4 个 Scope 按 `user_type` 硬编码；列表（Scope）与详情/写（Policy）两套独立判定；
- 模型事实（实施以真实列名为准）：Task/Defect 各自持有独立 `project_id`；Requirement 经 `requirement_project` 关联多项目；Document 上传人字段为 `uploaded_by_id`；`EnsureUserIsActive` 当前只校验 `is_disabled`；
- 部署事实：`ops/prepare-demo.sh` 先在共享库执行迁移并建 candidate，`ops/promote-demo.sh` 之后才切 current；queue 用 Redis（`after_commit=false`），存在 FPM/queue/scheduler/CLI 多类写入者；
- 管理界面：无用户/角色/权限配置界面。

## 2. 目标架构

### 2.1 三级主体与三维度

主体三级：**组织 → 角色 → 账户**；兜底为用户类型内置默认（现有硬编码规则原样保留）。组织候选集（冻结）= 用户**直接所属**组织，不含祖先、不向下继承；多组织归属各组织规则平等参与。

### 2.2 三维度解析真值表（冻结）

**功能权限**（组织/角色/账户规则全部参与，无遮蔽）：

| 条件 | 结果 |
|------|------|
| 任一主体存在该权限码未过期 deny（超管除外，见 2.9） | **deny** |
| 否则任一主体存在未过期 allow | allow |
| 无任何规则 | 用户类型内置默认 |

**数据范围**（层级覆盖，同层并集）：账户 > 角色 > 组织 > 类型默认；同层多主体取并集。
**字段权限**（全局最严格）：`hidden > masked > readonly > editable`；无配置 = editable。

### 2.3 操作资格公式（v1.7 恢复，回应 V16-01）

```
操作资格 = 功能权限 ∧ 数据可见 ∧ 动作特定资格
```

数据范围扩大永不替代动作资格。**不可配置覆盖清单（权威清单，维护于注册表 `non_overridable` 字段并配 Policy 测试矩阵）**：

1. 发布门禁完整性检查（必须用全量业务数据计算）；
2. 缺陷复测资格（提交人或项目成员测试 + defect.retest）；
3. 项目版本负责人关系（普通版本管理）；
4. 强制发布例外流程（独立、带原因、入审计）。

配置系统只能收紧、不能放松以上约束；超管同样不绕过，仅可经既定例外流程（第 4 项）操作。

### 2.4 权限规则存储（v1.7 定稿，回应 V16-03）

三可空外键：`user_id?/role_id?/organization_id?` + XOR CHECK + 部分唯一索引。

- `permission_rules`（subject, permission_id, effect, reason, granted_by_id, expires_at?）
- `data_scopes`（subject, module, scope_type, org_id?）+ `data_scope_projects`（明细）
- `field_permissions`（subject, resource, field, effect）

**基数与约束（全部数据库级可执行）**：
- 一主体一模块至多一条 data_scopes（唯一索引）；
- 同行 CHECK：`(scope_type='org_subtree') = (org_id IS NOT NULL)`；
- **module × scope_type 合法矩阵冻结为 CHECK**：`CHECK (module <> 'audit' OR scope_type IN ('all','own','none'))`（随模块扩展增补）；
- projects 最小基数：延迟约束（INITIALLY DEFERRED）保证提交时 scope_type=projects 的规则至少一条明细；删除最后一条明细必须同事务改为 none、删除规则或被触发器拒绝；
- 明细归属：延迟触发器保证明细的父规则必须 scope_type='projects'；
- scope_type 切换单事务完成主表+明细，中间态 fail closed；
- **锚点删除策略**：`data_scopes.org_id` → `ON DELETE RESTRICT`（必须先同事务将引用规则改为 none 或换锚）；其余 FK：主体删除级联删规则，`granted_by_id` nullOnDelete，项目删除级联删明细；规则硬删除；
- 验收含：绕过 API 的直接 SQL、删最后明细、删锚点且下层默认更宽的反向测试。

**`permission_role` 迁移**：回填+停读停写，切换顺序见 2.11（不再裸依赖"维护模式"）。

### 2.5 数据范围逐模块集合函数（不变）

| module | all | own | org_subtree | projects | none |
|--------|-----|-----|-------------|----------|------|
| project | 全表 | manager_id=我 ∪ 我提交需求所关联项目 | supplier_org_id ∈ org_id 子树 | id ∈ 明细 | 空集 |
| requirement | 全表 | submitter_id=我 | EXISTS 关联项目 ∈ S(project, org_subtree) | EXISTS 关联项目 ∈ 明细 | 空集 |
| task | 全表 | assignee_id=我 | task.project_id ∈ S(project, org_subtree) | task.project_id ∈ 明细 | 空集 |
| defect | 全表 | reporter_id=我 | defect.project_id ∈ S(project, org_subtree) | defect.project_id ∈ 明细 | 空集 |
| document | 全表 | uploaded_by_id=我 | document.project_id ∈ S(project, org_subtree) | document.project_id ∈ 明细 | 空集 |
| audit | 全表 | actor_id=我 | 不支持 | 不支持 | 空集 |

Task/Defect 锚定自身 `project_id`；需求多项目可见性不向下扩散。

### 2.6 缓存失效与 epoch（v1.7 修订，回应 V16-02）

1. **TTL 截断** = min(300s, 最近 expires_at − now)，可控时钟边界测试；
2. **epoch**：单行 `permission_epoch` 全局计数器；由数据库触发器递增；
3. **触发字段全清单（冻结）**：六张规则/关系表（permission_rules、data_scopes、data_scope_projects、field_permissions、role_user、organization_user）**以及** `organizations(parent_id, org_type, is_active)`、`users(user_type, is_active, is_disabled)` 的 UPDATE——影响授权判定的字段无一遗漏；
4. **缓存命名空间不可复用**：缓存键 = `perm:{deployment_uuid}:{epoch}:...`；`deployment_uuid` 每次部署生成写入；数据库恢复、反向迁移、epoch 重建必须**原子更换 UUID 或清空全部权限缓存**——旧备份恢复后缓存键永不复用；
5. 验收：组织重挂父节点、数据库恢复、epoch 重建后的反向授权测试。

### 2.7 字段级权限（读/写闭包分离，不变）

`editable` 随时可配；`readonly` 需写入闭包激活；`hidden/masked` 需读+写闭包激活。masked 默认不可写，脱敏回写 422 `FIELD_FORBIDDEN`。

### 2.8 授权注册表与切换状态（v1.7 修订，回应 V16-04）

**注册表**（`config/authorization.php`）字段契约不变，新增 `non_overridable` 标记（对应 2.3 清单）。

**激活摘要**：SHA-256(注册表该资源条目 + 授权消费者文件清单哈希)——消费者清单按资源显式登记（Policy/Resolver/Resource/导出器/服务层写入口）并指定 owner。

**`resource_auth_states`（恢复并扩展为双版本握手）**：

| 字段 | 说明 |
|------|------|
| resource | 资源标识 |
| read_activated / write_activated | 读/写闭包各自的激活时间与验证者 |
| current_digest / current_build | 现行构建的摘要 |
| candidate_digest / candidate_build | 候选构建的摘要（预激活态） |
| state | active / pre_activation / retiring |

**两阶段协议**（适配现有 candidate/current 发布）：
1. prepare：登记 candidate_digest（current_digest 继续有效，现行构建不受影响）；
2. 候选验证通过后切流 promote；
3. 验证期通过 → 关闭回滚窗口 → current_digest 更新为新值，旧摘要进入 retiring；
4. 旧摘要仅在回滚窗口关闭后废止；候选失败回滚时 current_digest 未变，现行构建无感。

**stale gate 全通道（修订）**：失活校验放在共享 Resolver/服务边界而非路由中间件——HTTP 映射 503 `AUTH_STATE_STALE`；queue worker 进入可重试失败态；scheduler/CLI/导出同样 fail closed 并告警；**任何通道都不得回退 editable/allow**。长驻 worker 未重启、候选失败回滚均纳入演练。

### 2.9 超管治理不变量（v1.7 修订，回应 V16-05）

**三维矩阵**：功能恒 allow、数据恒 all、字段恒 editable；2.3 不可绕过清单对超管同样有效（仅可经强制发布例外流程）。

**唯一判定**：`isEffectiveSuperAdmin()` = `isSuperAdmin()` && `is_active` && `!is_disabled`——运行时授权、最后超管统计、会话检查共同调用。

**保护路径**：禁用、降权、删除、角色解绑、批量角色同步、is_active=false、super_admin 角色实体变更——同一 `pg_advisory_xact_lock` 事务，锁内重算，归零即拒绝。

**启用前置断言（新增）**：Phase A 部署预检必须断言有效超管数 ≥ 1，否则中止部署。

**零超管离线恢复（新增）**：artisan 命令 `ipms:recover-superadmin`——仅控制台可执行，一次性恢复凭证从部署环境变量读取（不落库不落日志），全程强审计；使用同一把 advisory lock，原子修复 super_admin 角色实体、账户状态（is_active/is_disabled）、角色绑定，并撤销全部相关会话。部署阻断演练与恢复演练均为验收项。

**会话**：`EnsureUserIsActive` 同时校验 `is_disabled` 与 `is_active`；降权/禁用/停用撤销既有会话，重启用不恢复。

### 2.10 回滚契约（不变 + 引用修正）

Phase C 配置开放后永久禁止回滚到读取 `permission_role` 的构建；回滚能力矩阵 = schema 版本 + 规则类型 + 默认语义 + 旧表读取能力；旧表只在回滚窗口显式关闭后删除；三场景演练（有 allow 删除、无 deny、Phase D 后）。

### 2.11 单事实源切换的完整停写顺序（v1.7 新增，回应 V16-06）

不再假设"维护模式开即无并发写"。冻结顺序：

1. **关闭入口**：nginx 层维护页（非仅 app 内 down flag，阻断一切 HTTP）；
2. **停止并排空**：FPM（systemctl stop php8.2-fpm）、queue worker（`queue:restart` 后停止进程并确认排空）、scheduler（暂停 cron）、确认无 CLI 任务；
3. **数据库级旧表写保护**：对 `permission_role` 加触发器 `RAISE EXCEPTION`（或回收应用角色写权限），任何残留写入者立即报错而非静默丢授权；
4. 回填 + 行数/哈希核对；
5. 切换 current，重启全部长驻进程；
6. 新构建验证通过 → 开放流量 → 撤除写保护；
7. 任一步失败：按能力矩阵前向恢复或受控回滚（触发器写保护使回滚也安全）。

无法完全停写的环境（如有外部写入者）改用**双写 + 增量追平 + 最终一致性校验**：切换前最后一轮对账 `permission_role` vs `permission_rules` 一致方可切流。部署脚本按本顺序改造并演练。

### 2.12 可扩展性约定（不变）

permissions 表注册中心；注册表单一事实源；新资源敏感字段随 migration 登记；前端 `v-perm` / `v-field-perm`。

### 2.13 管理界面（不变）

系统管理菜单组（仅超管）：用户管理 / 角色管理 / 权限审计画像。配置开放受 `resource_auth_states` 分阶段激活的服务端强制。

## 3. 实施计划（v1.7）

### Phase A：基础设施（无配置开放）
迁移（五张新表 + roles.is_system + permission_epoch + deployment_uuid + 全部约束/触发器/合法矩阵 CHECK）；注册表全量登记（含 non_overridable）+ 完整性测试；Resolver 骨架（默认=现状）；超管保护锁 + 恢复命令；epoch 触发器 + TTL 截断 + UUID 命名空间；EnsureUserIsActive 补 is_active；**部署前置断言：有效超管 ≥ 1**；permission_role 按 2.11 顺序切换。
**验收**：现有后端测试零改动全绿 + 真值表参数化 + 到期可控时钟 + 并发撤超管 + 回填核对 + DB 约束测试 + 级联反向授权 + 零超管部署阻断演练。

### Phase B：按资源依赖闭包逐资源切换（读/写闭包分别激活）
双版本摘要握手 + 全通道 stale gate；验收含候选失败回滚、长驻 worker 未重启演练与"只改序列化器不改注册表"负向用例。

### Phase C：管理界面
三页 + 前端指令；本阶段起永久禁止回滚到 permission_role 读取构建。

### Phase D：收口与复审
回滚窗口显式关闭后删除 permission_role；清除硬编码角色判定；角色×端点回归矩阵；全量验收 + 静态复审 + 代码审计 + 并发 + 三场景回滚演练 + 多角色反向验收。
