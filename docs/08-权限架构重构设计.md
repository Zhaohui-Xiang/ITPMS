# 权限架构重构设计 — 多级可配置权限体系

**文档版本**: v1.2
**创建日期**: 2026-09-24
**文档状态**: 修订稿（已回应独立审计 PA-01~09，待复审）
**修订历史**:
- v1.0：初稿（三级模型 + 解析服务 + 三阶段计划）
- v1.1：补字段级权限与可扩展性约定（D18）
- v1.2：按独立审计报告（docs/qa/2026-09-24-permission-architecture-review.md）修订——阶段门禁调整、输出通道收敛、masked 写入语义、超管保护收敛、禁用撤会话、组织主体补齐、缓存到期闭合；唯一产品取舍见 PA-02 回应（v1 字段权限不含历史/快照/导出通道）

**背景**: 走查发现超管无用户管理界面（P8）、角色权限只能靠改 Seeder 代码调整、数据可见范围硬编码在用户类型上。目标是把权限体系重构为可按 **组织架构 / 角色 / 账户** 三级自定义配置的形式。

---

## 1. 现状盘点

### 1.1 功能权限（页面/操作级）

- `permissions` 表：35 个权限码，`module.action` 格式，带中文名与描述；
- `roles` / `role_user` / `permission_role`：7 个内置角色，用户-角色多对多；
- 判定入口：`User::hasPermission(code)`（300s 缓存）+ `CheckPermission` 中间件 + 各 Policy；
- 痛点：角色-权限矩阵写死在 `RolePermissionSeeder.php`，调整需改代码且不同步存量库（I15）。

### 1.2 数据权限（行级可见性）

- 4 个 Scope（Project/Requirement/Task/Defect）按 `user_type` 硬编码三套规则：内部 IT=项目经理或项目成员；供应商=组织子树（CTE 递归）；系统用户=自己提交需求关联的项目；
- 行级操作判定散落在各 Policy；
- 痛点：规则不可配置，且**列表（Scope）与详情/写（Policy）是两套独立判定**（审计 PA-01 实证：ProjectController 列表走 Scope、详情走 Policy）。

### 1.3 管理界面

- 无用户管理、无角色管理、无权限配置界面。

## 2. 目标架构

### 2.0 权限的三个正交维度

| 维度 | 控制什么 | 例子 |
|------|---------|------|
| **功能权限** | 能不能做某个操作（页面/按钮/API） | 供应商不能"审核需求" |
| **数据权限** | 能看见哪些行（行级范围） | 供应商只看本组织子树的项目 |
| **字段权限** | 看见的行里能不能看/改某个字段 | 供应商看不到需求内部备注；手机号脱敏 |

三级主体（组织/角色/账户）作用于每一个维度。

### 2.1 三级主体模型与解析优先级（v1.2 修订：补齐组织主体，回应 PA-08）

```
账户级覆盖（user_permissions / 用户行 data_scopes / 用户行 field_permissions）
    ↓ 覆盖
角色级（role ↔ permission 矩阵 / 角色行 data_scopes / 角色行 field_permissions）
    ↓ 覆盖
组织级默认（组织行 data_scopes / field_permissions，成员继承）
    ↓ 缺省
用户类型内置默认（现有三套硬编码规则，作为兜底保留）
```

**统一解析规则**（功能/数据/字段三维度共用）：

1. 有效配置 = 第一条命中的主体层级（账户 > 角色 > 组织 > 类型默认）；
2. 多角色、多组织归属：取**并集**（可见范围相加、功能权限相加）；
3. **deny 恒优先**：任何层级的显式 deny 高于一切 allow（防止"角色给了就挡不住"）；
4. 组织级语义：组织节点上的配置是该节点**成员的默认配置**，成员有更上两级配置时不继承；`org_subtree` 是数据筛选范围，与"组织主体配置"是两个概念，不得混用；
5. 超级管理员恒定全量（见 2.7 的收敛保护规则），不参与配置。

**判定服务**：`PermissionResolver`（功能权限）、`DataScopeResolver`（数据范围）、`FieldFilter`（字段权限）。

### 2.2 操作资格组合公式（v1.2 新增，回应 PA-04）

```
操作资格 = 功能权限（module.action）∧ 数据可见（DataScopeResolver）∧ 动作特定资格
```

- **动作特定资格**指工作流关系约束（如"复测=提交人或项目成员测试"、"发布=项目负责人"），**永远不能被数据范围配置替代或扩大**——把某用户的数据范围调大，不会让他获得复测/发布等他本无资格的动作；
- 设计明确列出**不可配置覆盖的业务约束**：发布门禁的完整性检查、缺陷复测资格、版本负责人关系、强制发布的例外流程。配置系统只能收紧，不能放松这些约束；
- 超管例外（如强制发布）必须走独立、带原因、入审计的专用路径，"超管全量"不构成绕过业务约束的语义。

### 2.3 功能权限判定

- `user_permissions` 表（新增）：`user_id, permission_id, effect(allow|deny), reason, granted_by_id, expires_at?`
- `PermissionResolver`：角色并集 ⊕ 账户覆盖（deny 优先）→ 替换 `User::hasPermission` 实现；
- 缓存与到期（回应 PA-09）：缓存 TTL 截断到"参与判定规则中的最近 expires_at"，到期即失效，不靠固定 300s；写路径（role_user/permission_role/user_permissions/data_scopes/field_permissions）变更主动失效全部相关缓存。

### 2.4 数据权限

`data_scopes` 表（新增）：`subject_type(user|role|organization)`、`subject_id`、`module`、`scope_type(all|org_subtree|projects|own|none)`、`org_id?`、`project_ids?(JSON)`。

**关联数据与统计的出口规则（v1.2 新增，回应 PA-03）**：

1. **计算与展示分离**：发布门禁、统计数字等业务计算必须使用**全量业务数据**（操作者看不到某条严重缺陷，门禁依然要拦）；面向用户的展示按读取者有效权限裁剪；
2. 版本详情、需求详情等聚合页中的**关联列表**（范围内需求、关联任务、缺陷计数）按对应模块的可见范围过滤；统计若要对无权限者公开，必须显式设计为授权例外并在界面注明口径；
3. 跨项目需求：每个关联项目按各自项目侧可见性判定。

### 2.5 字段级权限

`field_permissions` 表（新增）：`subject_type(role|user|organization)`、`subject_id`、`resource`、`field`、`effect(hidden|masked|readonly|editable)`。多规则冲突取最严格（hidden > masked > readonly > editable）。

**输出通道清单（v1.2 新增，回应 PA-02）**：字段权限可能的泄露通道 = ① 列表 ② 详情 ③ 嵌套摘要（如任务卡片内嵌需求标题）④ 修订历史 ⑤ 发布快照 ⑥ 导出（CSV/接口文档） ⑦ 直返模型的原始 JSON 端点。

**v1 范围（产品取舍，待确认）**：字段权限 v1 只覆盖 ①②③ 三个通道（列表/详情/嵌套摘要，全部经 Resource 基类收口，嵌套字段映射到源字段判定）；④⑤⑥⑦ 在 v1 **显式声明不支持字段级隐藏**，管理界面在配置时提示该限制，历史与快照作为不可变记录保持原样（绝不为了过滤展示去修改历史存储）。后续版本再扩展副本映射。

**写入语义（v1.2 新增，回应 PA-05）**：

- `hidden`：不可读不可写；`masked`：**默认不可写**，请求层校验入包——值为脱敏形态（含 `*`）或对 masked 字段的任何写入均拒绝（422 `FIELD_FORBIDDEN`），防止"整表提交把脱敏串回写成真实值"；
- 确需替换 masked 字段值的场景（如改绑手机号）走独立权限码（如 `user.change_phone`），属盲写授权，请求契约单独定义；
- `readonly`：可读不可写；`editable`：默认。前端禁用控件只是体验，拦截必须在请求层。

### 2.6 可扩展性约定（v1.1 内容保留）

1. `permissions` 表即注册中心：新功能必须经 migration 声明权限码，管理界面矩阵动态渲染；
2. 路由权限覆盖完整性测试：扫描路由表，受保护路由漏挂权限码/Policy 即红；
3. 字段权限：新资源敏感字段随 migration 登记默认值，未登记默认 editable；
4. 前端统一 `v-perm` / `v-field-perm` 指令，清除角色白名单硬编码。

### 2.7 安全与一致性约束（v1.2 修订，回应 PA-06/PA-07）

- **超管保护收敛**：只保护"最后一名有效（未禁用）超管"——存在两名及以上有效超管时，允许禁用/降权任一其他超管；最后一名校验与变更必须在**同一事务**内完成（防并发撤到零）；取消基于固定用户名（admin）的永久豁免；
- **禁用即撤权**：禁用用户后其全部既有会话立即失效（请求级 `is_disabled` 校验 + 禁用时主动撤销会话），重新启用**不恢复**旧会话，必须重新登录（与 U-1 修复对齐）；
- 权限相关表写操作全部入审计日志；
- 超管恒定全量仅指功能/数据/字段三维度的读取与配置能力，**不构成**对 2.2 不可覆盖业务约束的绕过；
- Seeder 保留为初始默认值，上线后权限以数据库配置为准（解决 I15）。

### 2.8 管理界面（吸收 W3-P8）

新增"系统管理"菜单组（仅超管）：

1. **用户管理**：列表、建号（初始密码+强制改密）、启用/禁用（禁用即撤会话）、分配角色、数据范围、账户级权限覆盖（含 expires_at）；
2. **角色管理**：功能权限矩阵（动态渲染）、字段权限配置（界面标注 v1 不支持的通道）、数据范围默认、角色成员；系统角色可改权限不可删；
3. **权限审计**：权限画像（来源追溯）、数据范围预览、字段视角预览；
4. **配置开放的模块门禁（回应 PA-01）**：某模块的配置入口仅在其"授权入口统一"批次完成后开放（见 3.2），未开放的模块在界面置灰并标注"配置未生效"。

## 3. 数据库变更与实施计划

### 3.1 数据库变更

| 表 | 类型 | 说明 |
|----|------|------|
| `user_permissions` | 新增 | 账户级功能权限覆盖（allow/deny，含 expires_at） |
| `data_scopes` | 新增 | 数据范围配置（subject=user/role/organization） |
| `field_permissions` | 新增 | 字段级权限（hidden/masked/readonly/editable） |
| `roles` | 扩展 | `is_system`、`description` |
| `permissions` | 不变 | 注册中心，新功能经 migration 声明 |
| `permission_role` / `role_user` | 不变 | 改为 UI 可维护 |

### 3.2 实施计划（v1.2 重构：按模块分批切换，回应 PA-01）

**Phase A：基础设施（纯后端，无配置开放）**
1. 迁移：三张新表 + `roles.is_system`；
2. `PermissionResolver` / `DataScopeResolver` / `FieldFilter` 骨架（默认规则=现状，行为等价）；
3. 缓存 TTL 截断与主动失效；禁用即撤会话（U-1 落地件并入）；
4. 路由权限覆盖完整性测试；
5. **验收**：现有后端测试零改动全绿 + 新增解析优先级/deny 优先/到期失效/字段过滤默认放行的测试。**本阶段不开放任何配置入口。**

**Phase B：逐模块切换（每个模块一个批次，可并行推进但按批验收）**
每个批次 = 该模块的 Scope + Policy + 控制器详情/写/关联/导出**全部入口**统一接入解析服务 → 该模块配置入口才开放。批次顺序建议：需求 → 任务 → 缺陷 → 项目/版本 → 文档 → 审计。
- **验收（每批次必过）**：同一配置分别验证列表、详情直访 ID、写接口、关联入口四通道——收紧同步拒绝、扩大一致生效；关联数据与统计按 2.4 规则裁剪，门禁计算不受展示过滤影响。

**Phase C：管理界面**
1. 系统管理三页（用户/角色/权限审计）+ 前端指令落地；
2. **验收**：超管 UI 全链路（建角色→配权限→配字段管控→建号→分配→配数据范围→以该用户验证可见性与字段呈现）；新增演示权限码自动出现在矩阵。

**Phase D：收口与复审**
1. 清除残留硬编码角色判定；权限矩阵回归用例表（角色 × 端点）；
2. 全量验收 + 独立复审（对照本文件 PA 回应逐条核验）。

### 3.3 测试策略（回应审计验收门槛）

- 反向用例优先：跨角色、账户覆盖、跨项目、关联字段、到期瞬间（可控时钟）、撤权后旧凭证，每类都要有"应该被拒绝"的断言；
- 现有回归测试全绿是必要条件而非充分条件；行为等价以"默认配置下四通道判定抽样比对旧实现"补充证明；
- 任何"配置已保存"不等于"配置已生效"，验收只认四通道实测。

## 5. 风险与对策

| 风险 | 对策 |
|------|------|
| 行为等价破坏 | Phase A 全绿硬门槛 + 默认配置四通道抽样比对 |
| 批次切换中间态越权 | 配置门禁：模块未整批切完不开放配置（2.8-4） |
| 缓存不一致/到期续命 | TTL 截断 + 写路径主动失效 + 可控时钟测试 |
| 超管失陷无法处置 / 误删全部超管 | 只保护最后一名 + 同事务校验 + 禁用即撤会话 |
| 字段权限副本泄露 | v1 收敛三通道并界面明示；扩展时先建副本映射表 |
| 配置复杂度超出使用能力 | "从角色继承再微调"快捷路径；默认值即现状 |
