# 权限架构重构设计 — 多级可配置权限体系

**文档版本**: v1.1
**创建日期**: 2026-09-24
**文档状态**: 草案（待评审）
**v1.1 补充**: 新增字段级权限维度（2.0/2.4，hidden/masked/readonly/editable 四级）与可扩展性约定（2.5，权限注册中心 + 路由覆盖完整性测试 + 前端指令约定），确保后续新增功能天然可配置。
**背景**: 走查发现超管无用户管理界面（P8）、角色权限只能靠改 Seeder 代码调整、数据可见范围硬编码在用户类型上。目标是把权限体系重构为可按 **组织架构 / 角色 / 账户** 三级自定义配置的形式。

---

## 1. 现状盘点

### 1.1 功能权限（页面/操作级）

- `permissions` 表：35 个权限码，`module.action` 格式（如 `requirement.approve`、`defect.retest`），带中文名与描述；
- `roles` / `role_user` / `permission_role`：7 个内置角色，用户-角色多对多；
- 判定入口：`User::hasPermission(code)`（300s 缓存）+ `CheckPermission` 中间件 + 各 Policy；
- **痛点**：角色-权限矩阵写死在 `RolePermissionSeeder.php`，调一次权限要改代码、跑 Seeder、还不能增量同步到现有库（I15）。

### 1.2 数据权限（行级可见性）

- 4 个 Scope（Project/Requirement/Task/Defect）按 `user_type` 硬编码三套规则：
  - 内部 IT：项目经理或项目成员（`project_members`）
  - 供应商：组织子树（`organization_user` + WITH RECURSIVE CTE）
  - 系统用户：仅自己提交需求关联的项目
- 行级操作判定散落在各 Policy（如 `DefectPolicy::verify` 的项目成员判定）；
- **痛点**：规则不可配置。想给某个用户单独放开一个项目、或让某角色"只看本部门"，都要改代码。

### 1.3 管理界面

- 无用户管理（建号/禁用/角色分配）、无角色管理、无权限配置界面。

## 2. 目标架构

### 2.0 权限的三个正交维度

本设计中的"权限"分解为三个可独立配置、可组合的维度，三级主体（组织/角色/账户）作用于每一个维度：

| 维度 | 控制什么 | 例子 |
|------|---------|------|
| **功能权限** | 能不能做某个操作（页面/按钮/API） | 供应商不能"审核需求"；成员不能"归档项目" |
| **数据权限** | 能看见哪些行（行级范围） | 供应商只看本组织子树的项目；提出人只看自己的需求 |
| **字段权限** | 看见的行里能不能看/改某个字段 | 供应商看不到需求的内部备注；成员不能改"预计工时"；手机号对非管理员脱敏 |

### 2.1 三级权限模型

```
                    ┌─────────────────────────────────┐
                    │         权限解析服务              │
                    │  PermissionResolver（功能权限）    │
                    │  DataScopeResolver（数据范围）     │
                    └──────────────┬──────────────────┘
           ┌───────────────────────┼───────────────────────┐
     ① 组织级（数据范围）      ② 角色级（功能权限）       ③ 账户级（覆盖）
     用户挂在组织节点上，      角色持有权限码集合，        对单个用户的
     数据范围 = 可见组织子树   用户继承其所有角色的       权限与数据范围
     ∪ 指定项目集            权限并集                  做 allow/deny 覆盖
```

**判定优先级**：账户级覆盖 > 角色级 > 组织级/用户类型默认值。超级管理员恒定全量，不参与配置（防锁死）。

### 2.2 功能权限判定（重构 hasPermission）

```
effective = (角色权限并集 ⊕ 账户覆盖)   # 覆盖支持 allow / deny 两种
```

- `user_permissions` 表（新增）：`user_id, permission_id, effect(allow|deny), reason, granted_by_id, expires_at?`
- `User::hasPermission` 改为查询 PermissionResolver；缓存键不变，权限变更时主动失效（监听 role_user / permission_role / user_permissions 写入）。

### 2.3 数据权限（核心新增）

新增 `data_scopes` 配置表，每行是一条数据范围规则：

| 字段 | 说明 |
|------|------|
| `subject_type` | `user` / `role` |
| `subject_id` | 用户或角色 ID |
| `module` | `project` / `requirement` / `task` / `defect` / `document` / `audit` |
| `scope_type` | `all`（全部）/ `org_subtree`（本组织及以下）/ `projects`（指定项目集）/ `own`（仅本人相关）/ `none`（不可见） |
| `org_id` | scope_type=org_subtree 时的根组织 |
| `project_ids` | scope_type=projects 时的项目集（JSON） |

**解析规则**（DataScopeResolver）：某用户某模块的有效范围 = 用户级配置 > 其角色配置（多角色取并集）> 用户类型默认值（现状三套规则作为内置默认值保留，保证不配置时行为与今天完全一致）。

4 个现有 Scope 改为从 DataScopeResolver 取范围；Policy 中的"项目成员/供应商子树"判定逐步统一到同一服务。

### 2.4 字段级权限（新增维度）

新增 `field_permissions` 配置表，对"某个资源的某个字段"配置访问级别：

| 字段 | 说明 |
|------|------|
| `subject_type` / `subject_id` | 作用主体：`role` / `user`（组织级通过数据范围表达，字段级不做组织维度） |
| `resource` | 资源类型：`requirement` / `task` / `defect` / `project` / `user` 等 |
| `field` | 字段键：如 `internal_note`、`estimated_hours`、`phone` |
| `effect` | `hidden`（接口不返回）/ `masked`（返回脱敏值，如 138****1234）/ `readonly`（可读不可写）/ `editable`（默认，可读写） |
| `priority` | 多规则冲突时取最严格（hidden > masked > readonly > editable） |

**执行点（后端兜底，前端只做体验）**：

1. **序列化收口**：所有 API Resource 输出前经过 `FieldFilter` 服务，按当前用户的有效字段权限剔除/脱敏字段——前端永远收不到无权的字段值；
2. **写入拦截**：Form Request / Request 校验层拒绝向 `readonly/hidden` 字段写入（返回 422 `FIELD_FORBIDDEN`），防止绕过界面直接调 API；
3. **前端呈现**：`/api/user` 或各资源 meta 接口下发当前用户的字段权限表，前端据此禁用/隐藏对应表单项和表格列（`v-field-perm` 指令统一实现）。

解析优先级与功能权限一致：账户级 > 角色级 > 系统默认（默认全部 editable，不配置即现状）。超管恒定 editable。

### 2.5 可扩展性：新增功能的权限配置约定（制度 + 机制）

目标：**后续任何新功能上线即自动出现在权限配置界面，无需额外开发**。

1. **权限注册约定**：`permissions` 表即注册中心。新功能开发时必须通过 migration（或 Seeder）声明其权限码（`module.action` + 中文名 + 描述），禁止代码内硬编码新权限码；管理界面的权限矩阵按 `permissions` 表动态渲染，新权限码自动出现；
2. **强制检查约定**：所有新 API 路由必须挂 Policy 或 `permission` 中间件；新增一个"权限覆盖完整性测试"——扫描路由表，断言每条受保护路由都有权限码或 Policy 覆盖，漏挂则测试失败（CI 兜底）；
3. **字段权限同理**：新资源类型的敏感字段在 migration 中登记默认值，未登记的字段按 `editable` 默认放行（向后兼容），需要管控时管理员在界面配置即可；
4. **前端约定**：新页面/按钮统一用 `v-perm`（功能）与 `v-field-perm`（字段）指令声明权限依赖，禁止手写角色判断（现有 `CREATE_MODULE_ROLES` 之类的角色白名单硬编码在重构中全部清除）。

### 2.6 管理界面（吸收 W3 的 P8）

新增"系统管理"菜单组（仅超管）：

1. **用户管理**：用户列表（搜索/按组织筛选）、建号（初始密码+强制改密）、启用/禁用、分配角色、配置数据范围、账户级权限覆盖（勾选权限码 + allow/deny + 理由）；
2. **角色管理**：角色列表、功能权限矩阵勾选（按模块分组的权限码表格，**随 permissions 表动态渲染**）、字段权限配置（选资源→选字段→选级别）、角色成员列表；内置 7 角色标记为"系统角色"可改权限但不可删除；
3. **权限审计**：任一用户的"权限画像"页——每个权限码的来源追溯（来自哪个角色/哪条账户覆盖）、有效数据范围预览（"以该用户视角能看到哪些项目"）、字段权限预览（"该用户看到的需求表单/详情长什么样"）。

### 2.7 安全与一致性约束

- 权限相关表的写操作全部进审计日志（现有 AuditLogger 中间件扩展 action 类型）；
- `user_permissions` 的 deny 优先级高于一切 allow（防止"角色给了就挡不住"）；
- 权限缓存变更即失效（不用等 300s TTL）；
- 超管账号不允许被禁用/降权（防锁死）；最后一名超管不可移除角色；
- Seeder 保留为"初始默认值"，系统上线后权限变更以数据库配置为准（解决 I15）。

## 3. 数据库变更

| 表 | 类型 | 说明 |
|----|------|------|
| `user_permissions` | 新增 | 账户级功能权限覆盖（allow/deny） |
| `data_scopes` | 新增 | 组织级/角色级/账户级数据范围配置 |
| `field_permissions` | 新增 | 字段级权限（hidden/masked/readonly/editable） |
| `roles` | 扩展 | 加 `is_system`（内置角色保护）、`description` |
| `permissions` | 不变 | 作为权限注册中心，新功能经 migration 声明新权限码 |
| `permission_role` / `role_user` | 不变 | 仅改为可由 UI 维护 |

## 4. 分阶段实施计划

### Phase A：解析服务与数据模型（后端，无 UI）
1. 迁移：`user_permissions`、`data_scopes`、`field_permissions`、`roles.is_system`；
2. `PermissionResolver`（角色并集 + 账户覆盖 + deny 优先）替换 `hasPermission` 实现，公开行为不变；
3. `DataScopeResolver` + 4 个 Scope 改造（无配置时回落到现有 user_type 默认规则）；
4. `FieldFilter` 服务骨架：Resource 序列化收口 + Form Request 写入拦截（默认全 editable，行为等价）；
5. **权限覆盖完整性测试**：扫描路由表，断言每条受保护路由都有权限码或 Policy 覆盖，漏挂即红（CI 兜底，保证后续新功能强制可配置）；
6. 权限缓存主动失效；
7. **验收标准**：现有 401 个后端测试零改动全绿（行为等价证明）+ 新增覆盖解析优先级、deny 优先、字段过滤、缓存失效的测试。

### Phase B：管理界面（前后端）
1. 系统管理菜单 + 用户管理页（建号/禁用/角色分配/数据范围/账户覆盖）；
2. 角色管理页（功能权限矩阵 + 字段权限配置，均动态渲染）；
3. 权限画像/审计页（功能来源追溯 + 数据范围预览 + 字段视角预览）；
4. 前端 `v-perm` / `v-field-perm` 指令落地，清除角色白名单硬编码；
5. API：users/roles/permissions/data-scopes/field-permissions 的 CRUD + 画像查询，全部过 Policy + 审计；
6. **验收标准**：超管可在 UI 完成"新建角色→勾选权限→配置字段级管控→建号→分配角色→配置数据范围→以该用户身份验证可见性与字段呈现"全链路；新增一个演示权限码能自动出现在矩阵中。

### Phase C：Policy 收口与验收
1. 各 Policy 中散落的行级判定迁移到 DataScopeResolver；
2. 验收测试套件补充权限矩阵用例（每个角色 × 关键端点的 allow/deny 断言表）；
3. 全量验收 + 走查回归。

**建议顺序**：Phase A 先行（风险最大的是行为等价），Phase B 与 W3 其他项（工作台角色化、通知）可并行，Phase C 收尾。

## 5. 与现有决策/问题的关系

- 吸收 W3-P8（无用户管理模块）→ Phase B 用户管理页；
- 解决 I15（Seeder 权限不同步存量库）→ Phase A 后权限以库为准；
- 依赖 D13（组织树 CTE）与 D14（软删除），不冲突；
- 走查中"供应商 PM 可见项目范围疑似过宽"（走查-Q21）在 Phase A 后即可通过配置验证/收紧，无需改代码。

## 6. 风险与对策

| 风险 | 对策 |
|------|------|
| 行为等价破坏（现有权限判定被改坏） | Phase A 以"401 测试零改动全绿"为硬门槛；上线前跑全量验收 |
| 缓存不一致（改了权限不生效） | 写路径主动失效 + 权限画像页可实时验证 |
| 超管把自己锁死 | 超管恒定全量 + 最后一名超管保护 + `admin` 账户不受禁用约束 |
| 配置复杂度超出使用能力 | UI 提供"从现有角色继承再微调"的快捷路径；默认值即现状 |
| 字段过滤漏收口（新 Resource 不过 FieldFilter） | FieldFilter 挂在 Resource 基类统一入口 + 完整性测试断言；宁可默认放行也不能漏执行点 |
| 新功能忘挂权限 | 路由权限覆盖完整性测试（Phase A 第 5 项）+ AGENTS.md 开发约定强制要求 |
