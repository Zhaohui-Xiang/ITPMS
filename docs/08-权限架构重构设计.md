# 权限架构重构设计 — 多级可配置权限体系

**文档版本**: v1.6
**创建日期**: 2026-09-28
**文档状态**: 修订稿（已回应四次复审 V15-01~05，待五次复审）
**修订历史**:
- v1.0：初稿；v1.1：字段级权限与可扩展性约定（D18）
- v1.2：初审（PA-01~09）；v1.3：复审（V12-01~06）；v1.4：二次复审（V13-01~06）；v1.5：三次复审（V14-01~05）
- v1.6：按四次复审（V15-01~05）修订——缓存 epoch 改数据库触发器保证、TTL 截断到最近到期；data_scopes 一主体一模块+CHECK/触发器约束定案；激活摘要扩展到真实授权消费者+失活语义改 503 拒绝服务；恢复超管三维矩阵+isEffectiveSuperAdmin 唯一判定+is_active 纳入保护与中间件；回滚矩阵纳入 schema 版本与旧表读取能力、Phase D 回滚窗口关闭点

**背景**: 走查发现超管无用户管理界面（P8）、角色权限只能靠改 Seeder 代码调整、数据可见范围硬编码在用户类型上。目标是把权限体系重构为可按 **组织架构 / 角色 / 账户** 三级自定义配置的形式。

---

## 1. 现状盘点

- 功能权限：`permissions`（35 码）+ `permission_role`（仅可授予）+ `role_user`；`User::hasPermission()` 300s 缓存；矩阵写死在 Seeder（I15）；
- 数据权限：4 个 Scope 按 `user_type` 硬编码；列表（Scope）与详情/写（Policy）两套独立判定；
- 模型事实（实施以真实列名为准）：Task/Defect 各自持有独立 `project_id`；Requirement 经 `requirement_project` 关联多项目；Document 上传人字段为 `uploaded_by_id`；`EnsureUserIsActive` 中间件当前只校验 `is_disabled` 不校验 `is_active`；
- 管理界面：无用户/角色/权限配置界面。

---

## 2. 目标架构

### 2.1 三级主体与三维度

主体三级：**组织 → 角色 → 账户**；兜底为用户类型内置默认（现有硬编码规则原样保留）。组织候选集（冻结）= 用户**直接所属**组织，不含祖先、不向下继承；多组织归属各组织规则平等参与。

### 2.2 三维度解析真值表（冻结）

**功能权限**（组织/角色/账户规则全部参与，无遮蔽）：

| 条件 | 结果 |
|------|------|
| 任一主体存在该权限码未过期 deny（超管除外，见 2.8） | **deny** |
| 否则任一主体存在未过期 allow | allow |
| 无任何规则 | 用户类型内置默认 |

**数据范围**（层级覆盖，同层并集）：账户 > 角色 > 组织 > 类型默认；同层多主体取并集。
**字段权限**（全局最严格）：`hidden > masked > readonly > editable`；无配置 = editable。

### 2.3 权限规则存储（v1.6 定稿，回应 V15-02）

三可空外键方案：`user_id?/role_id?/organization_id?` + XOR CHECK + 部分唯一索引（COALESCE 表达式）。

- `permission_rules`（subject, permission_id, effect, reason, granted_by_id, expires_at?）
- `data_scopes`（subject, module, scope_type, org_id?）+ `data_scope_projects`（明细）
- `field_permissions`（subject, resource, field, effect）

**基数定案**：一主体一模块**至多一条** data_scopes（唯一索引），不存在同主体多规则合并问题。

**条件约束（可执行实现）**：
- 同行 CHECK：`(scope_type='org_subtree') = (org_id IS NOT NULL)`——org_subtree 必须带且只能带 org_id，其余类型不得携带；
- 明细归属：延迟约束触发器保证 `data_scope_projects` 的父规则必须 `scope_type='projects'`（非 projects 无明细）；projects 规则保存时至少一条明细由 API 422 校验，运行期空明细一律 fail closed（空集）；
- scope_type 切换在单事务内完成主表+明细变更，任何中间态 fail closed；
- 删除策略（不变）：规则硬删除；主体删除级联删规则；`granted_by_id` nullOnDelete；项目删除级联删明细；
- 数据库约束测试 + 并发切换测试为验收项（不只靠 API 422）。

**`permission_role` 单事实源迁移（不变 + 写冻结补充，回应 V15-05-4）**：回填与停读停写切换在**同一部署维护窗口**内完成（维护模式开 → 回填 → 行数/哈希核对 → 切换 → 维护模式关），窗口内无并发写，无需增量追平。

### 2.4 数据范围逐模块集合函数（不变，V14-01 已关闭）

| module | all | own | org_subtree | projects | none |
|--------|-----|-----|-------------|----------|------|
| project | 全表 | manager_id=我 ∪ 我提交需求所关联项目 | supplier_org_id ∈ org_id 子树 | id ∈ 明细 | 空集 |
| requirement | 全表 | submitter_id=我 | EXISTS 关联项目 ∈ S(project, org_subtree) | EXISTS 关联项目 ∈ 明细 | 空集 |
| task | 全表 | assignee_id=我 | task.project_id ∈ S(project, org_subtree) | task.project_id ∈ 明细 | 空集 |
| defect | 全表 | reporter_id=我 | defect.project_id ∈ S(project, org_subtree) | defect.project_id ∈ 明细 | 空集 |
| document | 全表 | uploaded_by_id=我 | document.project_id ∈ S(project, org_subtree) | document.project_id ∈ 明细 | 空集 |
| audit | 全表 | actor_id=我 | 不支持（422 拒绝） | 不支持（422 拒绝） | 空集 |

关键不变量：Task/Defect 锚定自身 `project_id`，需求多项目可见性不向下扩散。

### 2.5 缓存失效与 epoch（v1.6 重写，回应 V15-01）

1. **TTL 截断**：缓存有效期 = min(300s, 参与判定规则的最近 expires_at − now)，到期边界用可控时钟测试覆盖（到期前/瞬间/后）；
2. **epoch 机制**：单行表 `permission_epoch`（全局唯一计数器，缓存键携带 epoch）。规则六表（permission_rules、data_scopes、data_scope_projects、field_permissions、role_user、organization_user）及组织/用户状态字段变更由**数据库触发器**递增 epoch——覆盖 Eloquent、批量 SQL、FK 级联等一切写路径，"业务变更已提交但 epoch 未推进"在数据库层不可能发生；
3. epoch 为全局（简化失效语义），多用户变更（组织移动、角色解绑）天然同事务推进；
4. 验收：到期 allow 边界测试、级联删除后即时反向授权测试。

### 2.6 字段级权限（读/写闭包分离，不变）

读取闭包=七通道；写入闭包=create/update/bulk/import/工作流/服务层写入。`editable` 随时可配；`readonly` 需写入闭包激活；`hidden/masked` 需双闭包激活。masked 默认不可写，脱敏回写 422 `FIELD_FORBIDDEN`。

### 2.7 授权注册表与切换状态（v1.6 修订，回应 V15-03）

**注册表**（`config/authorization.php`，版本控制）字段契约不变：route、ability、phase（middleware/deferred，deferred 声明责任 Policy + 对应 Feature 测试名）、route_models、body_models、ability_args、outputs、channel、auth_only。

**激活摘要覆盖真实代码依赖（修订）**：摘要 = SHA-256(注册表该资源条目 **+ 该资源的授权消费者文件清单哈希**：Policy、Resolver、相关 Resource/序列化器、导出器、服务层写入口)。消费者清单按资源显式登记并指定 owner，代码评审门禁要求改动这些文件必须更新清单；路由枚举无法自动发现的语义依赖（序列化器新字段、服务层 mutation）由**按资源反向测试**兜底——自声明注册表不等于完整性证明。

**失活语义（修订，明确 fail closed 方向）**：
- 部署预检发现摘要不匹配 → **中止部署**（首选路径）；
- 运行期检测到不匹配（防御层）→ 该资源相关端点返回 **503 `AUTH_STATE_STALE`**，**保持既有限制配置继续生效**（绝不回退 editable/allow）；统一错误码、监控告警、重新核验激活步骤冻结为运维手册；
- 负向测试：只改序列化器/服务实现不改注册表 → 完整性测试红 + 预检阻断。

### 2.8 超管治理不变量（v1.6 重写，回应 V15-04）

**三维矩阵（恢复并冻结）**：超管功能恒 allow（deny 不生效）、数据恒 all、字段恒 editable；2.5 业务约束（门禁完整性、复测资格等）不绕过。

**唯一判定**：`isEffectiveSuperAdmin()` = `isSuperAdmin()`（角色绑定）`&& is_active && !is_disabled`——运行时授权、最后超管统计、会话检查**共同调用同一实现**，禁止复制近似公式。

**保护路径**：禁用、降权、删除、角色解绑、批量角色同步、**is_active=false**、super_admin 角色实体变更（code/is_system/删除）——全部走同一 `pg_advisory_xact_lock` 事务，锁内以 `isEffectiveSuperAdmin` 重算有效数，归零即拒绝；锁、重算、变更、审计、epoch 递增同事务同连接提交。

**会话**：`EnsureUserIsActive` 中间件同时校验 `is_disabled` 与 `is_active`（修复现有缺口）；降权/禁用/停用均撤销既有会话，重启用不恢复。

### 2.9 回滚契约（v1.6 重写，回应 V15-05）

1. **Phase C 配置开放后，永久禁止回滚到读取 `permission_role` 的构建**——无"当前没有限制规则"例外（旧表只读快照会让被删 allow 复活）；
2. 回滚能力矩阵 = schema 版本 + 全部规则类型 + 默认语义 + 旧表读取能力；预检脚本逐项比对，不兼容即中止（fail closed）；
3. `permission_role` 只能在**旧构建回滚窗口显式关闭**（登记于部署元数据）后删除；或提供经验证的反向迁移（permission_rules → permission_role 数据恢复步骤）；
4. 回填与切换同窗完成（2.3 维护窗口），无并发写间隙；
5. 回滚演练三场景：有 allow 删除的场景、无 deny 的场景、Phase D 旧表已删的场景——全部验证限制连续生效或回滚被阻断。

### 2.10 可扩展性约定（不变）

permissions 表注册中心；注册表单一事实源；新资源敏感字段随 migration 登记；前端 `v-perm` / `v-field-perm`。

### 2.11 管理界面（不变）

系统管理菜单组（仅超管）：用户管理 / 角色管理 / 权限审计画像。配置开放受 `resource_auth_states` 分阶段激活的服务端强制。

## 3. 实施计划（v1.6）

### Phase A：基础设施（无配置开放）
迁移（五张新表 + roles.is_system + permission_epoch + 全部约束与触发器）；维护窗口内回填 permission_role 并停读停写；注册表全量登记 + 完整性测试；三个 Resolver 骨架（默认=现状）；超管保护锁（含角色实体与 is_active）；epoch 触发器 + TTL 截断；EnsureUserIsActive 补 is_active 校验。
**验收**：现有后端测试零改动全绿 + 真值表参数化测试 + 到期可控时钟 + 并发撤超管 + 回填核对 + 数据库约束测试 + 级联反向授权测试。

### Phase B：按资源依赖闭包逐资源切换（读/写闭包分别激活）
摘要含授权消费者文件清单；预检阻断优先；验收含"只改序列化器不改注册表"负向用例与 503 AUTH_STATE_STALE 行为。

### Phase C：管理界面
三页 + 前端指令；**本阶段起永久禁止回滚到 permission_role 读取构建**；验收含灰度开放界面验证。

### Phase D：收口与复审
回滚窗口显式关闭后删除 permission_role（或提供反向迁移验证）；清除硬编码角色判定；角色×端点回归矩阵；全量验收 + 静态复审 + 代码审计 + 并发 + **三场景回滚演练** + 多角色反向验收。
