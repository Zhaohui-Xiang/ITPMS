# 权限架构重构设计 — 多级可配置权限体系

**文档版本**: v1.4
**创建日期**: 2026-09-28
**文档状态**: 修订稿（已回应二次复审 V13-01~06，待三次复审）
**修订历史**:
- v1.0：初稿
- v1.1：补字段级权限与可扩展性约定（D18）
- v1.2：按初审（PA-01~09）修订
- v1.3：按复审（V12-01~06）修订——真值表、灰度开放、串行化锁、依赖闭包、表约束、注册表
- v1.4：按二次复审（V13-01~06）修订——组织继承语义按维度冻结、主体表定案（三可空 FK + XOR）、读/写闭包分离、超管治理不变量、逐模块数据范围集合函数、注册表可执行契约与切换状态载体

**背景**: 走查发现超管无用户管理界面（P8）、角色权限只能靠改 Seeder 代码调整、数据可见范围硬编码在用户类型上。目标是把权限体系重构为可按 **组织架构 / 角色 / 账户** 三级自定义配置的形式。

---

## 1. 现状盘点

- 功能权限：`permissions`（35 码）+ `permission_role`（仅可表达授予）+ `role_user`；`User::hasPermission()` 300s 缓存；矩阵写死在 Seeder（I15）；
- 数据权限：4 个 Scope 按 `user_type` 硬编码；列表（Scope）与详情/写（Policy）两套独立判定（PA-01）；
- 管理界面：无用户/角色/权限配置界面。

---

## 2. 目标架构

### 2.1 三级主体与三维度

主体三级：**组织 → 角色 → 账户**，外加用户类型内置兜底（现有硬编码规则原样保留）。维度三个：**功能权限 / 数据权限 / 字段权限**。

**组织候选集（v1.4 冻结，回应 V13-01）**：参与某用户权限计算的组织 = 该用户**直接所属**的组织（`organization_user` 中的行），**不含祖先、不向子组织成员继承**。多组织归属时各组织规则平等参与。组织配置的语义按维度分别定义（见 2.2），不存在跨维度通用的"组织默认"。

### 2.2 三维度解析真值表（v1.4 冻结为可直接转参数化测试的表格，回应 V13-01）

**功能权限**（组织/角色/账户规则全部参与，无遮蔽）：

| 条件 | 结果 |
|------|------|
| 任一主体（直接组织/任一角色/账户）存在该权限码的未过期 deny | **deny** |
| 否则任一主体存在未过期 allow（含存量 permission_role 授予） | allow |
| 无任何规则 | 用户类型内置默认 |

**数据范围**（层级覆盖，同层并集）：取最高配置层级（账户 > 角色 > 组织 > 类型默认）的规则；同层多主体命中取并集。组织级在此维度即"组织默认"——成员有角色或账户配置时不再继承组织规则。

**字段权限**（全局最严格，组织/角色/账户规则全部参与）：`hidden > masked > readonly > editable`；无配置 = editable。

**冲突真值表（复审要求的用例）**：

| 场景 | 功能权限 | 字段权限 |
|------|---------|---------|
| 组织 deny + 角色 allow | deny（veto） | — |
| 组织 allow + 账户 deny | deny（veto） | — |
| 组织 hidden + 账户 editable | — | hidden（最严格） |
| 多组织一 allow 一 deny | deny（veto） | 最严格 |
| 父子组织各有一规则 | 两条都参与（仅直接所属组织；父组织规则仅当用户直属父组织时参与） | 同左 |

### 2.3 权限规则存储（v1.4 定案，回应 V13-02：不再保留多选项）

采用**三可空外键 + XOR CHECK + 活跃行部分唯一索引**方案：

```
permission_rules / data_scopes / field_permissions 共同结构：
  id, user_id?, role_id?, organization_id?,  -- 三个可空 FK
  CHECK (num_nonnulls(user_id, role_id, organization_id) = 1),  -- XOR
  + 各表规则键（permission_id / module+scope_type / resource+field）
  UNIQUE(规则键, user_id, role_id, organization_id)  -- 部分唯一索引：WHERE true（FK 可空时 PG 唯一索引将 NULL 视为不相等，
                                                     需用 COALESCE 表达式索引，迁移中写清）
```

- **规则不软删除**：删除即硬删除，历史由审计日志承载（复审指出的软删除唯一键占用问题随之消解）；
- 级联策略（唯一答案）：主体（user/role/organization）删除 → **cascade 删其规则**；`data_scope_projects.project_id` → 项目删除时 cascade 删明细；`granted_by_id` → `nullOnDelete`（授权人离职不影响规则效力）；
- `data_scope_projects` 为空 = 空集合（等同于该模块不可见），API 层在保存时提示确认，不回退默认。

### 2.4 数据范围逐模块集合函数（v1.4 新增，回应 V13-05）

每个 `module × scope_type` 的集合定义 `S(module, scope_type, actor, org_id, project_ids)`：

| module | all | own | org_subtree | projects | none |
|--------|-----|-----|-------------|----------|------|
| project | 全表 | manager_id=我 ∪ 我提交需求关联项目 | supplier_org_id ∈ 子树 ∪ 内部成员归属（按现状规则） | id ∈ 明细 | 空集 |
| requirement | 全表 | submitter_id=我 | 关联项目 ∈ S(project, org_subtree) | 关联项目 ∈ 明细 | 空集 |
| task | 全表 | assignee_id=我 | 所属需求 ∈ S(requirement, org_subtree) | 所属需求关联项目 ∈ 明细 | 空集 |
| defect | 全表 | reporter_id=我 | 同 task 路径 | 同 task 路径 | 空集 |
| document | 全表 | uploader=我 | 所属项目 ∈ S(project, org_subtree) | 所属项目 ∈ 明细 | 空集 |
| audit | 全表 | actor_id=我 | 不支持（拒绝写入） | 不支持（拒绝写入） | 空集 |

约束：org_subtree 必须且只能带 org_id；projects 必须且只能有明细行；all/own/none 不得携带锚点；不支持的组合由 API 422 + DB CHECK 双重拒绝。

### 2.5 操作资格公式（不变）

`操作资格 = 功能权限 ∧ 数据可见 ∧ 动作特定资格`；不可配置覆盖清单：发布门禁完整性、缺陷复测资格、版本负责人关系、强制发布例外流程。

### 2.6 字段级权限（v1.4 修订，回应 V13-03：读/写闭包分离）

- 资源闭包拆为**读取闭包**（七通道：列表/详情/嵌套摘要/历史/快照/导出/原始 JSON）与**写入闭包**（create/update/bulk/import/工作流流转/服务层写入的全部入口）；
- 开放条件：`editable` 任何资源随时可配（不增加限制）；**`readonly` 需写入闭包完成**（防 /settings/profile 类旁路）；**`hidden/masked` 需读取+写入闭包均完成**；
- masked 默认不可写；脱敏形态值回写 → 422 `FIELD_FORBIDDEN`；合法替换走独立权限码盲写契约。

### 2.7 授权注册表与切换状态（v1.4 重写，回应 V13-06）

**声明式注册表**（版本控制内，如 `ipms-backend/config/authorization.php`），每路由条目至少包含：

| 字段 | 说明 |
|------|------|
| route | name/method/path |
| ability | 权限码或 Policy 方法 |
| phase | `middleware`（路由参数可解析）/ `deferred`（控制器内，需声明责任 Policy 方法 + 对应 Feature 测试名） |
| route_models | 路由参数→模型绑定解析（当前多为数字 ID，显式声明解析方式） |
| body_models | 请求体派生模型（如 createTask 的 project_id）及解析字段 |
| ability_args | 多模型 ability 的参数构造规则 |
| outputs | 输出资源及字段列表 |
| channel | read / write / export |
| auth_only | 是否仅需登录（true 时需显式理由） |

**消费者**：运行时授权中间件、路由完整性测试、资源依赖闭包检查、切换激活——四方共同消费同一份注册表。deferred 路由不得退化为"控制器里悄悄 authorize"：注册表必须声明其 Policy 方法与验证测试，完整性测试断言该测试存在且引用对应路由。

**资源切换状态载体**：新表 `resource_auth_states`（resource, read_closure_done, write_closure_done, switched_at）。原子激活规则：artisan 命令校验该资源全部注册依赖满足（读/写闭包各自核验）后同事务置位；Resolver 只对 `switched_at` 非空的资源应用配置规则，配置写路径对未切换资源 422。回滚要求：代码回滚必须伴随 `resource_auth_states` 回退（运维手册步骤），旧代码不读该表故天然忽略配置——但**数据库里的配置保留**，重新上线即恢复。

### 2.8 超管治理不变量（v1.4 重写，回应 V13-04）

**超管三维度矩阵（冻结）**：功能权限——绕过 allow/deny 判定（恒 allow，deny 对超管不生效）；数据范围——恒 all；字段权限——恒 editable。但 2.5 的业务约束不被绕过（强制发布仍走例外路径）。

**最后超管保护（从"角色计数"升级为"实际恢复能力"）**：

1. 定义**保留恢复权限集**：`user.manage`、`role.assign`、权限规则配置权（permission_rules 写）；
2. 所有可能使"保有恢复能力的有效超管数"归零的写路径——禁用、降权、删除、角色解绑、批量角色同步、**对超管角色/超管所属组织/超管账户写 deny 恢复权限集的 permission_rules**——全部走同一保护路径：
   - `DB::transaction` + `pg_advisory_xact_lock(固定 key)`（事务级锁，随事务提交释放，避免会话级锁在连接复用下泄漏生命周期）；
   - 锁内重算：有效超管 = `is_active=true AND is_disabled=false AND 绑定 super_admin 角色 AND 未被 deny 保留恢复权限集`；操作后为零则拒绝；
   - 锁、重算、变更、审计、认证 epoch 递增在同一连接同一事务提交；
3. 降权/禁用均撤销既有会话；重新启用不恢复旧会话；
4. 并发降权、权限 deny、组织迁移、旧会话复用均配回归测试。

### 2.9 可扩展性约定（保留 v1.3 2.6 前三条）

permissions 表注册中心；注册表为授权单一事实源（2.7）；新资源敏感字段随 migration 登记；前端 `v-perm` / `v-field-perm` 指令。

### 2.10 管理界面（不变）

系统管理菜单组（仅超管）：用户管理 / 角色管理 / 权限审计画像。配置开放受 `resource_auth_states` 服务端强制（未切换资源配置写入 422）。

## 3. 实施计划（v1.4）

### Phase A：基础设施（无配置开放）
迁移（三张规则表 + data_scope_projects + resource_auth_states + roles.is_system，含全部约束）；注册表建立（现有路由全量登记）+ 完整性测试；三个 Resolver 骨架（默认=现状）；超管保护锁；禁用撤会话（已上线，U-1）；缓存失效与 TTL 截断。
**验收**：现有后端测试零改动全绿 + 真值表全组合参数化测试 + 到期可控时钟测试 + 并发撤超管测试。

### Phase B：按资源依赖闭包逐资源切换（读/写闭包分离核验）
每资源完成读/写闭包 → artisan 原子激活 → 配置开放。验收：全通道（含工作台/导出/嵌套摘要/选项接口）正反向用例；门禁计算不受展示过滤影响。

### Phase C：管理界面
三页 + 前端指令；验收含"旁路资源禁选 hidden/masked""readonly 需写闭包"的界面验证。

### Phase D：收口与复审
清除硬编码角色判定；角色×端点回归矩阵；全量验收 + 静态复审 + 代码审计与多角色反向验收。

| 风险 | 对策 |
