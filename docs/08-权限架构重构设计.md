# 权限架构重构设计 — 多级可配置权限体系

**文档版本**: v1.3
**创建日期**: 2026-09-24
**文档状态**: 修订稿（已回应复审 V12-01~06，待二次复审）
**修订历史**:
- v1.0：初稿
- v1.1：补字段级权限与可扩展性约定（D18）
- v1.2：按初审（PA-01~09）修订——批次切换、字段通道收敛、masked 写入、超管保护收敛、禁用撤会话、组织主体、缓存到期
- v1.3：按复审（V12-01~06）修订——三维度解析真值表消除矛盾、字段权限按资源灰度开放（旁路未收口不开放）、最后超管改串行化锁、切换单元改为"端点依赖闭包"、新表完整性与组织生命周期、路由覆盖测试改声明式注册表

**背景**: 走查发现超管无用户管理界面（P8）、角色权限只能靠改 Seeder 代码调整、数据可见范围硬编码在用户类型上。目标是把权限体系重构为可按 **组织架构 / 角色 / 账户** 三级自定义配置的形式。

---

## 1. 现状盘点

### 1.1 功能权限

- `permissions` 表：35 个权限码（`module.action`）；`permission_role` 只能表达"授予"，无法表达 deny；`role_user` 多对多；
- 判定入口：`User::hasPermission()`（300s 缓存）+ `CheckPermission` 中间件 + 各 Policy；矩阵写死在 Seeder（I15）。

### 1.2 数据权限

- 4 个 Scope 按 `user_type` 硬编码三套规则；列表（Scope）与详情/写（Policy）是两套独立判定（PA-01 实证）。

### 1.3 管理界面

- 无用户管理、无角色管理、无权限配置界面。

---

## 2. 目标架构

### 2.0 三个正交维度 × 三级主体

| 维度 | 控制什么 |
|------|---------|
| **功能权限** | 能不能做某操作（页面/按钮/API） |
| **数据权限** | 能看见哪些行 |
| **字段权限** | 看见的行里能不能看/改某字段 |

主体三级：组织（默认）→ 角色 → 账户；兜底为用户类型内置默认（现有硬编码规则原样保留为兜底）。

### 2.1 解析真值表（v1.3 重写，回应 V12-01：每维度唯一算法，禁止混用语义）

**功能权限**（全局 deny veto + allow 并集）：

| 存在配置 | 结果 |
|---------|------|
| 任一主体层级（组织/角色/账户）存在该权限码的 **deny**（未过期） | **拒绝** |
| 否则任一层级存在 **allow**（未过期；含 permission_role 授予） | 允许 |
| 无任何配置 | 用户类型内置默认 |

**数据范围**（层级覆盖，同层并集）：取最高配置层级（账户 > 角色 > 组织 > 类型默认）；同一层级多个主体（多角色/多组织归属）命中时取**并集**。范围类型：`all / org_subtree / projects / own / none`。

**字段权限**（全局最严格）：跨全部主体层级取最严格级别：`hidden > masked > readonly > editable`；无配置 = `editable`。

组织级语义：组织节点配置是其成员的默认（成员有角色/账户配置时不继承该维度）；`org_subtree` 是数据筛选范围，不等同于组织主体配置。

### 2.2 操作资格组合公式（PA-04 保留）

`操作资格 = 功能权限 ∧ 数据可见 ∧ 动作特定资格`（如复测=提交人或项目成员测试）。数据范围扩大永不替代动作资格。不可配置覆盖的业务约束清单：发布门禁完整性、缺陷复测资格、版本负责人关系、强制发布例外流程。超管例外走独立、带原因、入审计的专用路径。

### 2.3 权限规则存储（v1.3 重写，回应 V12-01/V12-05）

| 表 | 说明 |
|----|------|
| `permission_rules` | 功能权限规则统一表：`subject_type(user\|role\|organization)`、`subject_id`、`permission_id`、`effect(allow\|deny)`、`reason`、`granted_by_id`、`expires_at?`。替代并迁移 `permission_role` 的授予语义（保留兼容视图或迁移脚本） |
| `data_scopes` | 数据范围规则：`subject_type`、`subject_id`、`module`、`scope_type`、`org_id?` |
| `data_scope_projects` | scope_type=projects 的项目明细（外键级联，替代 JSON 悬空引用） |
| `field_permissions` | 字段规则：`subject_type`、`subject_id`、`resource`、`field`、`effect` |

**完整性约束（回应 V12-05）**：

- 每张规则表：`(subject_type, subject_id, 规则键)` 唯一约束（重复写入即冲突，Resolver 永远有唯一解）；
- `effect`、`scope_type`、`subject_type` 用 CHECK 枚举约束；`subject_id` 与 `permission_id`/`org_id`/项目明细全部外键（删除策略：主体删除时级联删规则，项目删除时 restrict 或级联删明细——实现时按引用检查）；
- 软删除与现有 D14 约定一致；
- **缓存失效源**扩展为：permission_rules、data_scopes、field_permissions、`organization_user` 变更、组织移动/禁用/删除、角色变更、用户启禁用——全部主动失效相关缓存；缓存 TTL 截断到参与判定规则的最近 `expires_at`（PA-09）。

### 2.4 数据权限出口规则（PA-03 保留 + V12-04 扩展）

- 计算与展示分离：门禁/统计用全量业务数据计算，展示按读取者权限裁剪；
- 聚合页关联列表按对应模块范围过滤；统计对外公开须显式设计为授权例外并注明口径；
- **端点—资源依赖矩阵（新增）**：建立"端点 → 输出资源 → 权限维度"清单（含 TaskResource 内嵌需求标题、ProjectVersionResource 需求摘要、DashboardController 聚合、选项接口、导出）。某资源的配置开放前提 = **所有输出该资源数据的端点完成迁移**（依赖闭包），不是按控制器目录划分；
- **服务端强制**：Resolver 读取资源的"已切换"标志，未闭环资源的配置写入被 API 拒绝（422 `MODULE_NOT_MIGRATED`）；UI 置灰仅为体验层。

### 2.5 字段级权限（v1.3 修订，回应 V12-02：按资源灰度开放）

四级：`hidden > masked > readonly > editable`。

**通道覆盖要求**：七类输出通道（列表/详情/嵌套摘要/修订历史/发布快照/导出/原始 JSON 直返端点）全部纳入模块切换批次与反向测试。历史/快照属不可变存储，**不修改存储内容，但读取表现层必须执行过滤**。

**灰度开放规则**：

- `readonly`/`editable`：无旁路风险（写拦截在请求层），任何资源随时可配置；
- `hidden`/`masked`：**仅当该资源的全部七通道表现层收口后才开放配置**；存在旁路的资源在配置界面禁止选择这两级并说明原因；
- masked 默认不可写；写入 masked 形态值或无权字段 → 422 `FIELD_FORBIDDEN`；合法替换走独立权限码盲写契约（如 `user.change_phone`）。

### 2.6 可扩展性约定（v1.3 修订，回应 V12-06）

1. `permissions` 表为权限码注册中心：新功能必须经 migration 声明权限码；
2. **声明式"路由—能力"注册表**：建立单一事实源（如 `config/abilities.php` 或 route macro），受保护路由的能力声明（权限码或 Policy 方法）由**运行时授权中间件与完整性测试共同消费**；禁止维护仅供测试的静态白名单。完整性测试断言：每条 auth:sanctum 路由在注册表有条目 ∧ 注册表条目指向真实路由；
3. 字段权限：新资源敏感字段随 migration 登记默认值，未登记默认 editable；
4. 前端统一 `v-perm` / `v-field-perm` 指令，清除角色白名单硬编码。

### 2.7 安全与一致性约束（v1.3 修订，回应 V12-03）

- **最后超管保护（串行化）**：所有可能减少有效超管数量的写路径（禁用、降权、删除、角色解绑、批量角色同步）共用同一把 PostgreSQL advisory lock（固定 key）；锁内重新统计 `is_active=true AND is_disabled=false AND 绑定 super_admin 角色` 的账户数，结果为零则拒绝操作；
- **有效超管定义**纳入 `is_active`（复审补充）；
- 禁用与降权均撤销既有会话（会话撤销或认证 epoch 递增），重新启用不恢复旧会话；
- 权限写操作全部入审计日志；并发撤销回归测试必做；
- Seeder 保留为初始默认值，上线后权限以库为准（I15）。

### 2.8 管理界面（吸收 W3-P8）

"系统管理"菜单组（仅超管）：用户管理（建号/禁用撤会话/角色分配/数据范围/账户覆盖含 expires_at）、角色管理（功能矩阵 + 字段配置 + 数据范围，动态渲染；系统角色可改不可删）、权限审计（画像/范围预览/字段视角预览）。资源配置入口的服务端强制见 2.4。

## 3. 实施计划（v1.3）

### Phase A：基础设施（无配置开放）
1. 迁移：四张新表 + `roles.is_system` + 完整性约束（2.3）；`permission_role` 数据迁移进 `permission_rules`；
2. 三个解析服务骨架（默认=现状，行为等价）+ 声明式路由—能力注册表 + 完整性测试；
3. 最后超管串行化锁；禁用撤会话（U-1 落地件并入）；缓存 TTL 截断与扩展失效源；
4. **验收**：现有后端测试零改动全绿 + 真值表全组合冲突测试（账户/多角色/多组织/类型默认）+ 到期可控时钟测试 + 并发撤超管测试。

### Phase B：按"资源依赖闭包"逐资源切换
切换单元 = 资源及其全部生产端点（含嵌套摘要/工作台/选项/导出/原始 JSON）。每单元完成后该资源配置入口开放（服务端强制）。
- **验收（每单元）**：同一配置在列表/详情/写/关联/嵌套摘要/工作台/导出全通道一致生效；门禁计算不受展示过滤影响；七通道反向用例。

### Phase C：管理界面
系统管理三页 + 前端指令；验收：超管 UI 全链路 + 新演示权限码自动出现在矩阵 + 旁路资源禁止配置 hidden/masked 的界面验证。

### Phase D：收口与复审
清除硬编码角色判定；角色×端点回归矩阵；全量验收 + 独立静态复审 + 实现后的代码审计与多角色反向验收。

## 5. 风险与对策

| 风险 | 对策 |
|------|------|
| 行为等价破坏 | Phase A 全绿 + 默认配置全通道抽样比对旧实现 |
| 切换中间态越权 | 依赖闭包 + 服务端 422 拒绝未闭环资源配置 |
| 真值表实现走样 | 真值表先冻结成测试（全组合冲突用例），再写 Resolver |
| 超管并发撤销 | advisory lock + 并发回归测试（验收依据，非事务包裹） |
| 字段旁路泄露 | 灰度开放：未收口资源禁止 hidden/masked |
| 规则表脏数据 | 唯一约束 + 外键 + CHECK + 级联/限制删除 |
| 完整性测试形同虚设 | 注册表由运行时授权与测试共同消费，禁止静态白名单 |
