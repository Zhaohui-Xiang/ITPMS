# 权限架构重构设计 — 多级可配置权限体系

**文档版本**: v1.0
**创建日期**: 2026-09-24
**文档状态**: 草案（待评审）
**背景**: 走查发现超管无用户管理界面（P8）、角色权限只能靠改 Seeder 代码调整、数据可见范围硬编码在用户类型上。目标是把权限体系重构为可按 **组织架构 / 角色 / 账户** 三级自定义配置的形式。

---

## 1. 现状盘点

### 1.1 功能权限（页面/操作级）

- `permissions` 表：35 个权限码，`module.action` 格式（如 `requirement.approve`、`defect.retest`），带中文名与描述；
- `roles` / `role_user` / `permission_role`：7 个内置角色，用户-角色多对多；
- 判定入口：`User::hasPermission(code)`（300s 缓存）+ `CheckPermission` 中间件 + 各 Policy；
- **痛点**：角色-权限矩阵写死在 `RolePermissionSeeder.php`，调一次权限要改代码、跑 Seeder、还不能增量同步到现有库（I15）。

### 1.2 数据权限（行级可见性）

- 4 个 Scope（Project/Requirement/Task/Defect）按 `user_type` 硬编码三套规则：
  - 内部 IT：项目经理或项目成员（`project_members`）
  - 供应商：组织子树（`organization_user` + WITH RECURSIVE CTE）
  - 系统用户：仅自己提交需求关联的项目
- 行级操作判定散落在各 Policy（如 `DefectPolicy::verify` 的项目成员判定）；
- **痛点**：规则不可配置。想给某个用户单独放开一个项目、或让某角色"只看本部门"，都要改代码。

### 1.3 管理界面

- 无用户管理（建号/禁用/角色分配）、无角色管理、无权限配置界面。

---

## 2. 目标架构

### 2.1 三级权限模型

```
                    ┌─────────────────────────────────┐
                    │         权限解析服务              │
                    │  PermissionResolver（功能权限）    │
                    │  DataScopeResolver（数据范围）     │
                    └──────────────┬──────────────────┘
           ┌───────────────────────┼───────────────────────┐
     ① 组织级（数据范围）      ② 角色级（功能权限）       ③ 账户级（覆盖）
     用户挂在组织节点上，      角色持有权限码集合，        对单个用户的
     数据范围 = 可见组织子树   用户继承其所有角色的       权限与数据范围
     ∪ 指定项目集            权限并集                  做 allow/deny 覆盖
```

**判定优先级**：账户级覆盖 > 角色级 > 组织级/用户类型默认值。超级管理员恒定全量，不参与配置（防锁死）。

### 2.2 功能权限判定（重构 hasPermission）

```
effective = (角色权限并集 ⊕ 账户覆盖)   # 覆盖支持 allow / deny 两种
```

- `user_permissions` 表（新增）：`user_id, permission_id, effect(allow|deny), reason, granted_by_id, expires_at?`
- `User::hasPermission` 改为查询 PermissionResolver；缓存键不变，权限变更时主动失效（监听 role_user / permission_role / user_permissions 写入）。

### 2.3 数据权限（核心新增）

新增 `data_scopes` 配置表，每行是一条数据范围规则：

| 字段 | 说明 |
|------|------|
| `subject_type` | `user` / `role` |
| `subject_id` | 用户或角色 ID |
| `module` | `project` / `requirement` / `task` / `defect` / `document` / `audit` |
| `scope_type` | `all`（全部）/ `org_subtree`（本组织及以下）/ `projects`（指定项目集）/ `own`（仅本人相关）/ `none`（不可见） |
| `org_id` | scope_type=org_subtree 时的根组织 |
| `project_ids` | scope_type=projects 时的项目集（JSON） |

**解析规则**（DataScopeResolver）：某用户某模块的有效范围 = 用户级配置 > 其角色配置（多角色取并集）> 用户类型默认值（现状三套规则作为内置默认值保留，保证不配置时行为与今天完全一致）。

4 个现有 Scope 改为从 DataScopeResolver 取范围；Policy 中的"项目成员/供应商子树"判定逐步统一到同一服务。

### 2.4 管理界面（吸收 W3 的 P8）

新增"系统管理"菜单组（仅超管）：

1. **用户管理**：用户列表（搜索/按组织筛选）、建号（初始密码+强制改密）、启用/禁用、分配角色、配置数据范围、账户级权限覆盖（勾选权限码 + allow/deny + 理由）；
2. **角色管理**：角色列表、权限矩阵勾选（按模块分组的权限码表格）、角色成员列表；内置 7 角色标记为"系统角色"可改权限但不可删除；
3. **权限审计**：任一用户的"权限画像"页——每个权限码的来源追溯（来自哪个角色/哪条账户覆盖）、有效数据范围预览（"以该用户视角能看到哪些项目"）。

### 2.5 安全与一致性约束

- 权限相关表的写操作全部进审计日志（现有 AuditLogger 中间件扩展 action 类型）；
- `user_permissions` 的 deny 优先级高于一切 allow（防止"角色给了就挡不住"）；
- 权限缓存变更即失效（不用等 300s TTL）；
- 超管账号不允许被禁用/降权（防锁死）；最后一名超管不可移除角色；
- Seeder 保留为"初始默认值"，系统上线后权限变更以数据库配置为准（解决 I15）。

## 3. 数据库变更

| 表 | 类型 | 说明 |
|----|------|------|
| `user_permissions` | 新增 | 账户级权限覆盖（allow/deny） |
| `data_scopes` | 新增 | 组织级/角色级/账户级数据范围配置 |
| `roles` | 扩展 | 加 `is_system`（内置角色保护）、`description` |
| `permission_role` / `role_user` | 不变 | 仅改为可由 UI 维护 |

---

## 4. 分阶段实施计划

### Phase A：解析服务与数据模型（后端，无 UI）
1. 迁移：`user_permissions`、`data_scopes`、`roles.is_system`；
2. `PermissionResolver`（角色并集 + 账户覆盖 + deny 优先）替换 `hasPermission` 实现，公开行为不变；
3. `DataScopeResolver` + 4 个 Scope 改造（无配置时回落到现有 user_type 默认规则）；
4. 权限缓存主动失效；
5. **验收标准**：现有 401 个后端测试零改动全绿（行为等价证明）+ 新增覆盖解析优先级、deny 优先、缓存失效的测试。

### Phase B：管理界面（前后端）
1. 系统管理菜单 + 用户管理页（建号/禁用/角色分配/数据范围/账户覆盖）；
2. 角色管理页（权限矩阵）；
3. 权限画像/审计页；
4. API：users/roles/permissions/data-scopes 的 CRUD + 画像查询，全部过 Policy + 审计；
5. **验收标准**：超管可在 UI 完成"新建角色→勾选权限→建号→分配角色→配置数据范围→以该用户身份验证可见性"全链路。

### Phase C：Policy 收口与验收
1. 各 Policy 中散落的行级判定迁移到 DataScopeResolver；
2. 验收测试套件补充权限矩阵用例（每个角色 × 关键端点的 allow/deny 断言表）；
3. 全量验收 + 走查回归。

**建议顺序**：Phase A 先行（风险最大的是行为等价），Phase B 与 W3 其他项（工作台角色化、通知）可并行，Phase C 收尾。

---

## 5. 与现有决策/问题的关系

- 吸收 W3-P8（无用户管理模块）→ Phase B 用户管理页；
- 解决 I15（Seeder 权限不同步存量库）→ Phase A 后权限以库为准；
- 依赖 D13（组织树 CTE）与 D14（软删除），不冲突；
- 走查中"供应商 PM 可见项目范围疑似过宽"（走查-Q21）在 Phase A 后即可通过配置验证/收紧，无需改代码。

## 6. 风险与对策

| 风险 | 对策 |
|------|------|
| 行为等价破坏（现有权限判定被改坏） | Phase A 以"401 测试零改动全绿"为硬门槛；上线前跑全量验收 |
| 缓存不一致（改了权限不生效） | 写路径主动失效 + 权限画像页可实时验证 |
| 超管把自己锁死 | 超管恒定全量 + 最后一名超管保护 + `admin` 账户不受禁用约束 |
| 配置复杂度超出使用能力 | UI 提供"从现有角色继承再微调"的快捷路径；默认值即现状 |
