# 权限架构重构设计 — 多级可配置权限体系

**文档版本**: v1.5
**创建日期**: 2026-09-28
**文档状态**: 修订稿（已回应三次复审 V14-01~05，待四次复审）
**修订历史**:
- v1.0：初稿；v1.1：字段级权限与可扩展性约定（D18）
- v1.2：初审（PA-01~09）；v1.3：复审（V12-01~06）；v1.4：二次复审（V13-01~06）
- v1.5：按三次复审（V14-01~05）修订——数据范围锚点改为各实体自身 project_id 并修正模型字段名、permission_role 单事实源迁移冻结、读/写闭包分阶段激活并绑定注册表摘要、回滚改为权限兼容版本门槛 fail-closed、超管恒 allow 语义统一且角色实体纳入保护

**背景**: 走查发现超管无用户管理界面（P8）、角色权限只能靠改 Seeder 代码调整、数据可见范围硬编码在用户类型上。目标是把权限体系重构为可按 **组织架构 / 角色 / 账户** 三级自定义配置的形式。

---

## 1. 现状盘点

- 功能权限：`permissions`（35 码）+ `permission_role`（仅可表达授予）+ `role_user`；`User::hasPermission()` 300s 缓存；矩阵写死在 Seeder（I15）；
- 数据权限：4 个 Scope 按 `user_type` 硬编码；列表（Scope）与详情/写（Policy）两套独立判定；
- 模型事实（复审实证，实施以真实列名为准）：Task 与 Defect 各自持有独立 `project_id`；Requirement 经 `requirement_project` 关联多项目；Document 上传人字段为 `uploaded_by_id`；
- 管理界面：无用户/角色/权限配置界面。

---

## 2. 目标架构

### 2.1 三级主体与三维度

主体三级：**组织 → 角色 → 账户**，外加用户类型内置兜底（现有硬编码规则原样保留）。维度三个：功能权限 / 数据权限 / 字段权限。

**组织候选集（冻结）**：参与计算的组织 = 用户**直接所属**组织（`organization_user`），不含祖先、不向下继承；多组织归属时各组织规则平等参与。

### 2.2 三维度解析真值表（冻结）

**功能权限**（组织/角色/账户规则全部参与，无遮蔽）：

| 条件 | 结果 |
|------|------|
| 任一主体存在该权限码未过期 deny（超管除外，见 2.8） | **deny** |
| 否则任一主体存在未过期 allow | allow |
| 无任何规则 | 用户类型内置默认 |

**数据范围**（层级覆盖，同层并集）：账户 > 角色 > 组织 > 类型默认；同层多主体取并集。

**字段权限**（全局最严格）：`hidden > masked > readonly > editable`；无配置 = editable。

冲突真值表（参数化测试用例）：组织 deny+角色 allow→deny；组织 allow+账户 deny→deny；组织 hidden+账户 editable→hidden；多组织冲突→deny/最严格；父子组织各一条→仅直接所属组织的规则参与。

### 2.3 权限规则存储（定案）

三可空外键方案：`user_id?/role_id?/organization_id?` + XOR CHECK（`num_nonnulls(...)=1`）+ 部分唯一索引（COALESCE 表达式）。

- `permission_rules`（subject, permission_id, effect allow|deny, reason, granted_by_id, expires_at?）
- `data_scopes`（subject, module, scope_type, org_id?）+ `data_scope_projects`（明细，project_id FK cascade）
- `field_permissions`（subject, resource, field, effect）

删除策略（唯一答案）：规则**硬删除**（历史由审计日志承载）；主体删除→级联删规则；`granted_by_id`→nullOnDelete；项目删除→级联删明细。

**`permission_role` 单事实源迁移（v1.5 新增，回应 V14-02）**：

1. Phase A 迁移步骤：`permission_role` 一次性回填为 `permission_rules`（subject=role, effect=allow），幂等键=唯一约束，迁移后输出**行数与哈希核对**报告；
2. 同一部署中切换：`User::hasPermission` 改为只读 `permission_rules`；`permission_role` **停写停读**（标记 legacy，禁止新代码引用，完整性测试断言无引用）；
3. 切换前旧表保持原样（迁移只增不改），因此回滚到切换前版本是安全的；Phase C 管理界面开放后旧表转只读存档，Phase D 删除；
4. **缓存失效源（全量清单）**：permission_rules、data_scopes、field_permissions、role_user、organization_user、组织移动/禁用/删除、用户启禁用、expires_at 到期；变更事务提交后递增权限 epoch（缓存键携带 epoch），deny/解绑/到期即时生效，验收覆盖这三类即时性。

### 2.4 数据范围逐模块集合函数（v1.5 修订，回应 V14-01：锚点为各实体自身 project_id）

| module | all | own | org_subtree | projects | none |
|--------|-----|-----|-------------|----------|------|
| project | 全表 | manager_id=我 ∪ 我提交需求所关联项目 | supplier_org_id ∈ org_id 子树 | project.id ∈ 明细 | 空集 |
| requirement | 全表 | submitter_id=我 | EXISTS 关联项目 p：p ∈ S(project, org_subtree) | EXISTS 关联项目 p：p.id ∈ 明细 | 空集 |
| task | 全表 | assignee_id=我 | **task.project_id** ∈ S(project, org_subtree) | **task.project_id** ∈ 明细 | 空集 |
| defect | 全表 | reporter_id=我 | **defect.project_id** ∈ S(project, org_subtree) | **defect.project_id** ∈ 明细 | 空集 |
| document | 全表 | **uploaded_by_id**=我 | document.project_id ∈ S(project, org_subtree) | document.project_id ∈ 明细 | 空集 |
| audit | 全表 | actor_id=我 | 不支持（422 拒绝） | 不支持（422 拒绝） | 空集 |

关键修正：Task/Defect 的 org_subtree/projects **直接锚定自身 `project_id`**，不经 Requirement 的多项目关系传递（避免"需求关联了可见项目 A"把属于项目 B 的任务泄露出来）。Requirement 的多项目语义为 EXISTS（任一关联项目可见即可见需求本身），但该可见性**不扩散**到项目 B 名下的任务/缺陷实体。

**projects 空明细语义（唯一答案）**：保存时拒绝空明细（API 422"请至少选择一个项目"）；运行期因项目删除导致明细变空时按**空集 fail closed** 处理。不再声称 DB CHECK 约束子表行数——保存校验在 API 层，运行期语义 fail closed。

### 2.5 操作资格公式（不变）

`操作资格 = 功能权限 ∧ 数据可见 ∧ 动作特定资格`；不可配置覆盖清单：发布门禁完整性、缺陷复测资格、版本负责人关系、强制发布例外流程。

### 2.6 字段级权限（读/写闭包分离）

- 读取闭包 = 七通道（列表/详情/嵌套摘要/历史/快照/导出/原始 JSON）；写入闭包 = create/update/bulk/import/工作流流转/服务层写入全部入口；
- 开放条件：`editable` 随时可配；`readonly` 需**写入闭包激活**；`hidden/masked` 需**读取+写入闭包均激活**；
- masked 默认不可写；脱敏形态回写 → 422 `FIELD_FORBIDDEN`；合法替换走独立权限码盲写契约。

### 2.7 授权注册表与切换状态（v1.5 修订，回应 V14-03/V14-04）

**注册表**（版本控制内 `config/authorization.php`），每路由条目：route(name/method/path)、ability（权限码或 Policy 方法）、phase（middleware/deferred，deferred 必须声明责任 Policy 方法 + 对应 Feature 测试名）、route_models、body_models、ability_args、outputs（资源及字段）、channel（read/write/export）、auth_only（需理由）。

四方共同消费：运行时授权中间件、路由完整性测试、资源依赖闭包检查、切换激活。

**切换状态**（`resource_auth_states` 表，v1.5 拆分）：

| 字段 | 说明 |
|------|------|
| `resource` | 资源标识 |
| `read_activated_at` / `read_activated_by` / `read_registry_digest` | 读取闭包激活时间、验证者、注册表摘要 |
| `write_activated_at` / `write_activated_by` / `write_registry_digest` | 写入闭包同上 |

- 激活 = artisan 命令核验该资源全部注册依赖后同事务置位；Resolver/配置写路径**按 effect 分别检查**：readonly 查 write_activated，hidden/masked 查双激活；
- **摘要绑定（防激活证明过期）**：激活记录注册表该资源条目的规范化摘要（SHA-256）；部署流水线预检重新计算摘要，**摘要变化 → 该资源自动失活（fail closed）**，待人工重新核验激活；
- 完整性测试覆盖：新增路由/输出字段/写入口必须登记注册表，否则测试红——证明历史激活不会被静默沿用。

**回滚策略（v1.5 重写，回应 V14-04，删除"旧代码天然忽略配置"）**：

1. **权限兼容版本下限**：`resource_auth_states`（或部署元数据）记录每个已激活资源要求的最低构建版本；存在有效 deny/readonly/hidden/masked 规则时，**禁止回滚到不含对应 Resolver 的版本**；
2. 回滚路径二选一：a) 前向兼容回滚构建（保留 Resolver，仅回退业务改动）；b) 先经审计流程撤销限制配置，再回滚；
3. 部署/回滚预检脚本读取"有效规则 × 目标版本能力矩阵"，任一不兼容即中止（fail closed）；
4. 回滚演练验收：限制在代码回退前后连续生效（或回滚被预检阻断的证据）。

### 2.8 超管治理不变量（v1.5 重写，回应 V14-05）

**语义定案（二选一已选定）**：**超管恒 allow，deny 对超管不生效，且 deny 不参与超管有效性计算**。剥夺超管特权的唯一途径是保护路径内的降权/禁用——不存在"deny 超管"这种半吊子状态，矛盾消除。

**有效超管判定**（与运行时同一判定，不复制近似公式）：`User::isSuperAdmin()`（角色绑定）`&& is_active && !is_disabled`。因超管恒 allow，该判定天然等价于"保有恢复能力"。

**保留超管角色实体保护**：`super_admin` 角色的 code 不可改、角色不可删、`is_system` 不可变（Policy + DB 层双保险）；这些变更与禁用/降权/角色解绑/批量同步**共用同一把** `pg_advisory_xact_lock(固定 key)`，锁内重算有效超管数，归零即拒绝；锁、重算、变更、审计、epoch 递增在同一事务同一连接提交。降权/禁用撤销既有会话，重启用不恢复。

测试：角色重命名/删除/标志变更、并发 deny/降权、旧会话复用回归。

### 2.9 可扩展性约定（不变）

permissions 表注册中心；注册表为授权单一事实源；新资源敏感字段随 migration 登记；前端 `v-perm` / `v-field-perm`。

### 2.10 管理界面（不变）

系统管理菜单组（仅超管）：用户管理 / 角色管理 / 权限审计画像。配置开放受 `resource_auth_states` 分阶段激活的服务端强制。

## 3. 实施计划（v1.5）

### Phase A：基础设施（无配置开放）
迁移（permission_rules / data_scopes / data_scope_projects / field_permissions / resource_auth_states / roles.is_system，含全部约束）；permission_role 回填+停读停写切换（2.3）；注册表全量登记现有路由 + 完整性测试；三个 Resolver 骨架（默认=现状）；超管保护锁（含角色实体保护）；缓存失效全量清单 + epoch；禁用撤会话（已上线 U-1）。
**验收**：现有后端测试零改动全绿 + 真值表参数化测试 + 到期可控时钟 + 并发撤超管 + 回填行数/哈希核对。

### Phase B：按资源依赖闭包逐资源切换（读/写闭包分别激活）
摘要绑定 + fail closed；验收：全通道正反向用例；门禁计算不受展示过滤影响；新增端点导致摘要变化→自动失活的回归证据。

### Phase C：管理界面
三页 + 前端指令；验收含灰度开放规则的界面验证与版本下限预检演练。

### Phase D：收口与复审
permission_role 删除；硬编码角色判定清除；角色×端点回归矩阵；全量验收 + 静态复审 + 代码审计 + 并发测试 + **回滚演练** + 多角色反向验收。
